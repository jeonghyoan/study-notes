내구성·가용성

용어내용주의·이유
내구성
(Durability)		저장한 데이터가 유실·손상 없이 유지될 확률 — S3는 99.999999999%(11 nines) 설계값이 거의 100%인데 100%가 아닌 것은 확률적 설계 수치이기 때문 — 특정 서비스 중단 사고 탓이 아님
가용성
(Availability)		필요할 때 접근·사용할 수 있는 시간 비율 — S3 Standard 99.99% 설계데이터를 잘 보관했다는 전제 위에서 보관을 얼마나 안정적으로 유지하는가의 지표
판단 기준내구성 = 데이터가 살아 있는가 / 가용성 = 지금 꺼내 쓸 수 있는가두 용어를 바꿔 쓰면 설계 의도를 잘못 설명하게 됨
배우는 이유데이터·파일·로그·백업 파일을 다루는 일이면 두 용어를 알아야 하고 면접·질문에 자주 나옴벡터 DB와 S3를 함께 묶어 이야기하는 경우가 많아 벡터 실습 앞에서 먼저 정리
S3를 많이 쓰는 이유가용성과 내구성을 우선하기 때문용량·가격만 보고 고르는 저장소가 아님
내구성과 가용성 — 내구성은 저장된 데이터가 남아 있을 확률(S3 11 nines), 가용성은 필요할 때 접근할 수 있는 시간 비율(S3 Standard 99.99%). 100%가 아닌 것은 확률 설계값이고 사고 한 번 때문이 아님

클라우드 요금 주의

항목내용주의·이유

피타고라스와 제곱근

항목내용주의·이유
피타고라스a² + b² = c² — 빗변 c = 루트(a² + b²)유사도 검사의 기본 베이스 — 제곱의 합이지 제곱근의 합이 아님
sqrtsquare root(스퀘어 루트)의 줄임말 — 제곱근(루트)을 구하는 명령단어와 기호를 알아야 제곱근을 쓸 수 있음
텍스트 표기$c = \sqrt{a^2 + b^2}$ — 달러로 시작·끝, 역슬래시, sqrt, 중괄호, ^2 제곱표기 요소를 하나씩 맞춰야 수식이 렌더링됨
표기 요소$ … $ 수식 시작·끝 / \sqrt 제곱근 / { } 묶음 / ^2 제곱중괄호를 빼면 제곱이 첫 글자에만 붙는 식으로 깨짐
앞의 식c²·a²도 같은 방식으로 씀뒤의 계산 시연이 이 표기를 기준으로 진행
피타고라스 — a² + b² = c²(제곱)이고 빗변 c는 루트로 구함. 제곱근을 더하는 식(√a + √b = √c)으로 옮겨 쓰면 거리 계산 전체가 틀어짐

기존 방식(FTP 업로드)의 문제

문제내용주의·이유
파일 누적이미지(JPG·PNG·GIF)를 FTP로 올리면 이미지 디렉터리에 계속 쌓임15년 된 이미지도 쓰레기로 남음
표시 방식웹페이지가 이미지 경로를 호출해 표시경로·파일명이 바뀌면 엑스박스(액박)
요구 충돌디자이너의 화질 요구와 경량화 요구가 충돌용량을 줄이면 퀄리티가 떨어져 개발자·인프라·디자인 업체 간 갈등
서버 이전프로그램 소스·HTML·CSS는 300~500MB(일반 쇼핑몰 구축분 60MB 정도)인데 이미지는 2년 운영하면 훨씬 커짐이전 시간·용량이 이미지에서 터짐 (구체 용량은 음성이 불명확)
삭제 위험이미지 파일을 모르고 지우면 액박이 뜨고 인프라 담당자에게 책임이 돌아옴파일과 코드의 참조 관계를 아무도 모르는 상태가 원인

명령하는 일주의·이유
make소스를 컴파일(빌드)환경 정보를 모으는 단계가 아니라 빌드 — PostgreSQL 설치 위치는 pg_config로 알아냄. OS·메모리 같은 환경 수집은 configure의 역할이고 PGXS 문서에 수집 단계가 없음
make install실제 설치이 단계를 하지 않으면 설치 자체가 안 된 것 — 빌드만 된 상태로 끝남
make clean빌드 산출물 삭제설치된 파일은 제거하지 않음 — make install 후 clean이 매우 힘들고 OS가 흔들린다는 근거는 문서에 없음
에러가 났을 때① 에러 코드 확인 → ② 부족한 패키지 설치 → ③ make clean → ④ 설정 → ⑤ 다시 make → 에러 없이 끝나면 make install에러 상태로 make install을 넘기지 않음 — clean은 에러가 났을 때만 하고, 에러가 없으면 하지 않아도 됨
설치 결과vector--0.8.7.sql 등이 /usr/share/pgsql/extension/으로, 헤더가 /usr/include/pgsql/server/extension/vector/로 복사PostgreSQL이 이미 설치되어 있어 make·make install 모두 통과 — 로그의 복사 경로로 설치 확인
실수 사례make install 단계에서 에러 (디스크 공간 부족으로 보임)postgresql.html 11장의 df -m·linux.html 12장 df -h로 여유 확인 후 재시도
소스 설치 3단계 — gcc·git·postgresql-server-devel·make 준비 → make(컴파일) → make install(복사). 에러가 있으면 make clean 후 다시 빌드하고, install 전에 에러를 남기지 않음

-- VectorDB 전용 DB 생성 — 이름은 임의

-- 해당 DB로 접속 전환
\c vector_db
-- vector 확장 등록 — 이미 있으면 건너뜀 (결과 CREATE EXTENSION)

-- 접속한 DB의 확장 목록으로 설치 확인

항목내용주의·이유
결과\c는 접속 DB(vector_db)·사용자(postgres) 안내 메시지, \dx에 vector 0.8.7 / public / vector data type and ivfflat and hnsw access methods와 plpgsql 1.0이 두 줄이 보이면 설치 완료 — 프롬프트도 vector_db=#로 바뀜
확장의 단위DB 단위 — 해당 DB에 접속한 상태에서 실행하고 \dx도 접속한 DB 기준다른 DB에서 \dx하면 vector가 없음
DB 이름vector_db는 임의로 정한 이름README는 vector를 쓸 DB마다 CREATE EXTENSION vector;를 실행하라고만 안내 — DB 이름 규칙은 없음
사용 범위전용 DB라 일반 사용자에게 아직 주지 않음일반 DB와 다른 용도 — 권한 부여는 6장
명령의 의미CREATE EXTENSION은 확장을 현재 DB에 로드(등록)하는 명령패치가 아님 — DB마다 따로 등록하고, pgvector는 control 파일에 trusted 표시가 없어 보통 superuser가 실행
실행 위치DBeaver가 아니라 터미널(psql)에서 바로 실행PostgreSQL로 들어갔지만 접속 DB가 vector_db로 바뀐 것이 확인 포인트
확인 명령\du 사용자(롤) · \dn 스키마 · \dx 확장같은 백슬래시 계열 — 목적별로 골라 확인
확장은 DB 단위 — \dx에 vector가 없으면 그 DB에 CREATE EXTENSION vector를 실행하지 않은 상태. 확장이 지워진 것이 아님

벡터와 차원

항목내용주의·이유
벡터데이터를 숫자 배열로 저장 — 표기 [1,2,3]VectorDB의 기본 단위
차원배열 안 숫자의 개수 → [1,2,3]은 3차원vector(3)은 실수 3개 — 컬럼 개수나 회원정보 구조와 무관
차원의 범위pgvector의 vector 타입은 최대 16,000차원까지 지원차원 수는 쓰는 임베딩 모델이 정함 — 3차원 이상이어야 작동한다는 기준은 문서에 없음
1차원이면일반 PostgreSQL 컬럼으로 처리할 수 있는 값이라 벡터를 쓸 이유가 적음“3차원 이상일 때 벡터를 쓰는 의미가 있다”는 설명은 벡터의 실용 기준 — pgvector 문서에 차원 하한은 없고 차원 수는 임베딩 모델이 정함
1차원 예mid·mname 같은 컬럼에 홍·홍길동처럼 값 하나씩 저장하는 형태컬럼마다 값이 하나면 일반 컬럼과 같아 벡터를 쓸 이유가 적음
3차원 예mid + userinfo(홍길동, 나이 25, 이메일)처럼 회원정보를 한 묶음(배열)로 저장배열 안 값 3개 = 3차원 임베딩 — 묶음의 개수가 아니라 실수 개수가 차원
key 형태key-value(JSON 형태) 배열도 있음JSON 학습 때 필요하고 람다 수식에도 쓰임
차원 — 배열 안 실수(float)의 개수. vector(3)은 값 3개이고, 차원 수는 임베딩 모델이 결정하며 최대 16,000차원

임베딩

항목내용주의·이유
핵심임베딩 모델이 사용자 질문을 배열(벡터)로 변환해 DB에 저장어떤 사용자가 어떤 질문을 했는지 서버에 기록되는 구조
기본 DB이때 쓰는 기본 DB가 PostgreSQL의 pgvector이고, 일반적으로 이것을 VectorDB라 부름이미지 데이터 활용에 많이 쓰이고 그 외 용도도 다양
모델 종류LLM·SLM, LangChain·LlamaIndex 같은 도구와 함께 사용vLLM은 모델을 실행·서빙하는 엔진 — 임베딩 모델도 서빙할 수 있지만 vLLM 자체가 임베딩 모델은 아님
자동 파이프라인LLM(OpenAI·HuggingFace·Ollama 등)으로 텍스트를 벡터로 변환해 DB에 자동 저장하는 구조구축하는 것이 인프라 담당의 일
수치 입력벡터 수치는 사람이 직접 입력하지 않고 변환(러닝) 담당 모델이 넣을 때 쿼리로 정함인프라 담당자는 값 자체를 신경 쓰지 않음 — 저장 구조와 흐름이 담당 범위

유사도

항목내용주의·이유
저장된 값[0.85, 0.12, 0.01] 같은 숫자 배열은 텍스트·이미지를 모델이 변환한 임베딩 값좌표나 유사도 값 자체가 아님
유사도 계산두 벡터를 거리 연산자(<->·<=> 등)로 비교해 얻는 결과값질문도 임베딩 벡터로 변환한 뒤 저장된 벡터와 비교
순위 방식가까운 순서로 가져오는 ORDER BY … LIMIT, HNSW·IVFFlat 인덱스단어(키워드)마다 돌아가며 체킹하는 방식이 아님
실행 예울트라·게이밍으로 검색하면 노트북·삼성 쪽은 유사도가 0.8 정도로 낮아 안 맞고, 0.9 부분(LG 게이밍 PC)에서 맞는 것을 출력하며 나머지는 패스값이 높은 순서로 답이 되는 구조
코사인 유사도범위는 -1~1, 방향이 같은 벡터는 정확히 1완벽하게 1로 떨어지는 경우가 없다는 설명과 달리 1이 최대이지 0.99가 최대는 아님. pgvector README는 코사인 유사도를 1 - 코사인 거리로 계산
프로그램 연결1에 가장 가까운 것들을 찾아 출력하는 것이 AI가 질문에 답하는 방식LLM이 움직이는 것 = 임베딩, 이를 VectorDB가 핸들링
인프라 담당의 이해0.xx 값이 질문에 대해 최대한 1에 가까운 값을 찾아 데이터를 안정적으로 답하기 위한 배열값이라는 수준AI가 만든 실습 데이터의 0.12·0.08 같은 수치도 유사도에 맞게 AI가 정한 값 — 실제로는 이름·이메일도 자연스럽게 나와야 함

# [윈도우 · AI 채팅 — Gemini·ChatGPT] 아래 문장을 그대로 붙여 넣기

-- [vector_db · psql 프롬프트 · postgres]

create table members (
  id serial primary key,                         -- 고유 식별 번호(자동 증가)

  email varchar(100) not null,                    -- 이메일

  created_at timestamp default current_timestamp  -- 가입일시
);
-- AI가 준 INSERT 20건이 16번째 줄에서 에러 → 1건만 직접 입력 (결과 INSERT 0 1)
insert into members (username, email, user_vector)
values ('user15', 'user15@example.com', '[0.33,0.22,0.99]');
-- [vector_db · psql 프롬프트 · postgres]

\dn
-- 테이블 목록(릴레이션 목록) — public / members / 테이블 / 소유자
\dt
-- 테이블 구조 — vector(3) 타입과 members_pkey 확인
\d members
-- 데이터 조회 — 배열 형태로 저장됐는지 확인

유사도 정렬 연산자

-- [mg DB · DBeaver SQL 편집기 · mg]
-- 막대 하나(<->) = 유클리드 거리, 질의 벡터 [1,4] 기준 정렬
select * from test order by emb <-> '[1,4]';
-- equal 두 개(<=>) = 코사인 거리, 같은 질의로 정렬
select * from test order by emb <=> '[1,4]';
연산자표기질의 [1,4] 결과 순서
<->꺾쇠 + 마이너스(막대 하나) + 꺾쇠b [2,4], a [1,2], c [4,1]
<=>꺾쇠 + equal 두 개 + 꺾쇠a [1,2], b [2,4], c [4,1]
<#>꺾쇠 + 샵(내적) + 꺾쇠원리는 10장 — 이 실습에는 실행 화면이 없음
  • 정렬 문법
    벡터는 order by에서 asc·desc 대신 연산자를 쓰고, 뒤에 따옴표로 질의 벡터('[1,4]')를 씀
  • 결과 읽기
    맨 위에 뜬 것이 가장 가까운(가장 유사한) 값 — 기호가 막대 하나냐 둘이냐에 따라 결과가 달라짐
같은 데이터·같은 질의라도 연산자 하나로 순서가 바뀜 — <->는 b, a, c이고 <=>는 a, b, c. 맨 위가 가장 가까운 값

  • 점수 기준

연산자성격주의·이유
<->두 점수가 균형 있게 높을수록 유리데이터가 더 들어가 계산해야 하고, 잘못 쓰면 이상한 결괏값이 나옴

<#>두 점수의 합계가 클수록 유리 (8+8=16, 9+9=18)거리가 아니라 숫자 값(합계)으로 결정 — [9,9]에서 와이드호스나인이 맨 위
<#>의 실제 계산음의 내적 — 쿼리가 [9,9]처럼 두 칸이 같을 때만 합계 순서가 됨쿼리가 [9,1]이면 9×스릴러 + 1×코미디, 즉 질의 벡터로 가중한 합 ([9,1] 결과 폴2, 와이드호스나인, 폭설, 라라랜드, 오디세이와 일치)
연산자를 고르는 기준정수·소수 여부가 아니라 크기를 반영하는지로 고름 — 정수 점수는 <#>, 소수점 점수는 <=>로 나누는 구분이 아님코사인은 방향만, 내적·유클리드는 크기 반영 — 정수 점수도 코사인으로 계산 가능
점수(크기) 반영크기를 반영하려면 코사인이 아니라 내적(<#>)·유클리드(<->)코사인은 두 벡터의 길이를 무시

만점·범위DB·벡터에 만점·범위 개념 없음 — 0~9는 사람이 정한 입력 약속질의 값도 저장 값과 같은 척도로 넣어야 순서가 맞음

차원 384의 정체

항목내용주의·이유
정해지는 곳사용하는 임베딩 모델이 내놓는 벡터 차원 — all-MiniLM-L6-v2와 paraphrase-multilingual-MiniLM-L12-v2 모두 384차원모델 카드에 출력 차원이 적혀 있음
컬럼과 맞춤vector(N)의 N은 모델 출력 차원과 같아야 함다르면 INSERT 단계에서 차원 불일치 에러
한글 조합 수자음 19개(기본 14 + 쌍자음 5) × 모음 21개(기본 10 + 복합모음) × 받침 28개(없는 것 포함) = 11,172자11,172자는 맞는 수치이지만 384와 무관 — 324 + 60 = 384처럼 한글에서 384를 나누는 계산의 근거 없음
한 행의 값한 행에 384개의 유사도 데이터가 들어가고 입력은 모델이 함행이 늘면 데이터가 크게 늘어남
열 개수의 영향모델에 열을 몇 개 주느냐에 따라 결과가 크게 달라짐열 개수 파악이 테이블 설계의 기준
384는 한글 조합 수가 아니라 모델의 출력 차원 — vector(N)의 N을 모델 차원과 맞추지 않으면 INSERT가 실패. 모델을 바꿀 때도 차원을 먼저 확인

# [spark-master 컨테이너 · Jupyter 노트북 img1 · root]
for i in range(1,34):                          # 1 ~ 33 (끝 숫자 미포함)
    filename  = f"travel_{i}.jpg"              # 번호 i가 바뀌며 파일명이 계속 바뀜
    file_path = os.path.join(image_dir, filename)   # 폴더 + 파일명 → 실제 경로
    if not os.path.exists(file_path):          # 그 경로에 파일이 있는지 확인
        continue                               # 없으면 다음 번호로 (break는 반복이 멈춰 금지)
    try:
        image   = Image.open(file_path).convert("RGB")           # 열고 RGB로 보정
        inputs  = processor(images=image, return_tensors="pt")   # pt = pytorch 텐서
        outputs = model.get_image_features(**inputs)             # 특징을 뽑아 임베딩 생성
        vector  = outputs[0].tolist()                            # 파이썬 리스트로 변환
        if len(vector) == 512:                                    # 512차원 값만 사용
            vector_str = str(vector)                              # 512개 숫자 좌표를 문자열로
            insert = (
                "insert into travel_image (file_path,emd) values (%s,%s::vector)"   # emd는 vector로 형변환
            )
            cursor.execute(insert, (file_path, vector_str))       # 이때 INSERT가 실제 실행
            count += 1                                            # 입력 개수 증가
            print(f" 이미지 {count} 번째 이미지 벡터가 정상적으로 저장됨!")
    except Exception as e:
        print(e)                                                  # 에러 메시지 출력

dbcon.commit()                                 # 반복문 밖에서 DB에 반영
cursor.close()                                 # 커서 종료
dbcon.close()                                  # DB 접속 종료

# [spark-master 컨테이너 · Jupyter 노트북 img3 · root]
# import : img2의 SELECT 쪽 + img1의 AI 쪽
from pyspark.sql import SparkSession
import pandas as pd
from sqlalchemy import create_engine, text
from PIL import Image
from transformers import CLIPModel, CLIPProcessor
import os

# Spark 세션과 dbinfo(create_engine)는 img2와 동일하게 준비

image_dir = "/opt/spark/data/user/user.jpg"     # 사용자가 올린 이미지 1장
# 전처리(리사이즈·정규화·텐서 변환)
processor = CLIPProcessor.from_pretrained("openai/clip-vit-base-patch32")
# 임베딩 계산
model     = CLIPModel.from_pretrained("openai/clip-vit-base-patch32")

# 1장이라 반복문·존재 확인 없이 바로 읽음 (RGB 보정은 유지)
image   = Image.open(image_dir).convert("RGB")
inputs  = processor(images=image, return_tensors="pt")   # pt = PyTorch 텐서
outputs = model.get_image_features(**inputs)             # 이미지 임베딩
vector  = outputs[0].tolist()                            # 512개 숫자 리스트
if len(vector) == 512:                                   # 모델 차원 확인 (안쪽은 들여쓰기)
    vector_str = str(vector)                             # SQL 파라미터로 넘길 문자열
    query = """
    select file_path, emd <=> cast(:user_vec as vector) as img
    from travel_image order by img asc
    """
    # :user_vec 자리에 사용자 이미지 벡터를 params로 전달
    pdf = pd.read_sql(text(query), con=dbinfo, params={"user_vec":vector_str})

dbinfo.dispose()
df = spark.createDataFrame(pdf)
df.show(truncate=False)
spark.stop()
