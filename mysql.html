항목내용

실습 모형
  • 로컬 VirtualBox Linux 호스트 위 Docker 컨테이너에서 MySQL 실행 → DBeaver가 호스트 IP의 3306/tcp로 접속
  • 클라우드 관리형 RDS와 Docker 컨테이너는 운영 방식·관리 책임이 다름 → 동일 구조로 단정하지 않음
RDS 내부 구현"RDS 전용 서버에서 Docker로 여러 RDS를 구동" = 교육용 비유. AWS 공개 문서는 관리형 아키텍처를 설명하지만 내부 구현이 Docker라고 밝히지 않음 (참고: AWS RDS 핵심 개념·아키텍처)
실습 위치호스트 Linux 작업 경로 /root/rds, 로그인 계정 apink → root 전환. DB 클라이언트는 DBeaver

항목내용

포트 변경 범위·영향

이미지 인증과 MySQL 컨테이너 실행

한눈에 보기 — 이미지 받기부터 접속까지

① 레지스트리 인증

docker login dhi.io

② 이미지 받기

docker pull dhi.io/mysql:8

③ 컨테이너 실행

-e MYSQL_ROOT_PASSWORD · -p 3306:3306

④ 접속

docker exec -it · mysql -u root -p

항목내용
레지스트리 구분dhi.io/mysql:8 = Docker Hardened Images(DHI) 레지스트리 참조 → Docker Hub 공식 MySQL 이미지와 같은 이미지라고 부르지 않음. DHI Community 이미지 pull에는 레지스트리 인증 필요
tag 관찰값
  • 실습은 :8 사용 → 서버 버전 8.4.13, 이미지 약 461MB, 이미지 목록 화면은 Debian 13 기반 표시
  • tag·용량은 갱신될 수 있음 → 실행 후 SELECT VERSION()으로 확인
dev·정식 tag실습 화면 안내: dev = 개발·테스트용, 정식 8.4 = 안정화 버전 → tag 이름만으로 지원정책을 단정하지 말고 현재 이미지 카탈로그·조직 배포 정책 확인
# [호스트 리눅스 · root]
# DHI 레지스트리 인증 → 성공 시 Login Succeeded
docker login dhi.io
# DHI MySQL tag를 내려받음 → 이미지 이름·tag 일치 확인
docker pull dhi.io/mysql:8
docker images
항목내용
인증 정보로그인 암호·access token은 명령행·노트에 기록하지 않음 (인증·이미지 형식 출처: Docker Hardened Image 사용 안내)

단일 MySQL 서비스 컨테이너

# [호스트 리눅스 · root]
# --name mysql8: 컨테이너 이름 고정 → docker logs mysql8처럼 이름으로 참조
# -e MYSQL_ROOT_PASSWORD: 이미지 초기화 때 MySQL root 암호 전달. a1234는 연습값 → 명령 기록·프로세스 정보에 노출될 수 있어 운영은 안전한 secret 경로로 주입
# -p 3306:3306: 호스트:컨테이너 순서, 호스트 3306 → 컨테이너 3306. 호스트에서 이미 사용 중이면 컨테이너 시작 실패 가능
# -d: 백그라운드 실행
docker run --name mysql8 -e MYSQL_ROOT_PASSWORD=a1234 -p 3306:3306 -d dhi.io/mysql:8
# 실행 상태와 게시 포트 확인
docker ps
# 외부:내부 포트 게시 확인
docker port mysql8
항목내용
--privileged·/sbin/initsystemd가 필요한 OS 연습용 컨테이너 방식(docker.html 3·4장). MySQL 단일 서비스 이미지는 엔트리포인트가 서버를 실행 → 별도 init 권한 불필요
MySQL 단일 서비스 실행 — MYSQL_ROOT_PASSWORD는 초기 설정용, -p 3306:3306은 호스트:컨테이너 순서. 일반 MySQL 컨테이너에는 --privileged·/sbin/init 불필요. dhi.io는 로그인 후 pull, 버전은 tag가 아니라 SELECT VERSION()으로 확인

컨테이너 사용자와 MySQL 프롬프트

# [호스트 리눅스 · root]
# 이미지 기본 사용자(mysql)로 컨테이너 셸 진입
docker exec -it mysql8 /bin/bash
# UID 0(root) 권한으로 컨테이너 셸 진입
docker exec -it -u 0 mysql8 /bin/bash
# [mysql8 컨테이너 · mysql 또는 root(-u 0)]
# MySQL root 계정으로 접속 (-p 뒤 암호는 프롬프트에서 입력)
mysql -u root -p
# [mysql8 컨테이너 · MySQL 프롬프트 · root]
\s
SELECT VERSION();
항목내용
-u 0컨테이너 프로세스를 UID 0으로 실행. 프롬프트가 I have no name!이어도 이름 해석이 안 된 것일 수 있음 → id로 uid=0 확인
최소 이미지DHI는 공격면을 줄이려 최소 구성 → vi·nano·dnf·clear가 없을 수 있음. bash: clear: command not found = clear 프로그램이 없다는 뜻, MySQL 서버 장애와 무관
기동 확인docker ps는 실행 중만 표시 → 안 보이면 docker ps -a에서 종료 상태·exit code 확인
컨테이너 사용자 구분 — docker exec -it는 이미지 기본 사용자, -u 0은 UID 0. 프롬프트 모양이 아니라 id로 권한 확인

docker exec -it mysql8 /bin/bash

항목내용
관찰 결과실습 화면: Server·DB character set utf8mb4, Client character set latin1. \s = 현재 세션·서버 상태를 보는 MySQL 클라이언트 명령
왜 맞추나클라이언트가 어떤 인코딩으로 보내고 서버가 어떻게 변환하는지 = 연결 문자셋이 결정 → 한글 입력 시 변환 오류·깨짐·Incorrect string value 가능 → 클라이언트·서버·DB 문자셋 확인
DBeaver 별도 설정my.cnf의 [client]·[mysql]은 MySQL CLI 클라이언트에 적용. DBeaver는 JDBC 드라이버 설정·연결 properties를 따로 사용 → CLI 설정이 자동 적용된다고 가정하지 않음

설정 파일을 찾고 호스트에서 전달

# [mysql8 컨테이너 · mysql]
# 전체 파일시스템에서 설정 파일 탐색 → Permission denied는 권한 없는 경로라는 뜻
find / -name my.cnf
# [호스트 리눅스 · root]
# 컨테이너 안에서 UID 0으로 전체 경로 탐색
docker exec -it -u 0 mysql8 find -name "my.cnf"
# [mysql8 컨테이너 · root]
# /etc 범위의 설정 파일 존재 여부 확인
find /etc -name "my.cnf"
ls /etc
ls -al /etc
# [호스트 리눅스 · root]
# 컨테이너 파일을 호스트로 복사 → 원본이 없으면 no such file 오류
docker cp mysql8:/etc/my.cnf my.cnf
# 파일이 없으면 호스트에서 작성해 컨테이너로 전달
docker cp my.cnf mysql8:/etc/
항목내용
실습 관찰
  • 사용한 dhi.io/mysql:8 컨테이너에는 /etc/my.cnf가 없었음 → 이미지·버전마다 설정 경로·include 구성이 다를 수 있어 모든 MySQL 8.4 이미지의 규칙으로 확대하지 않음
  • 실습 메모: MySQL 8.0 이미지에는 /etc/my.cnf가 있었고 사용한 8.4 tag에는 없었음 (이미지별 차이로 확인)
파일 없음 판단find /의 Permission denied = 접근 못 한 경로가 있다는 뜻 → 확인 가능한 표준 위치와 서버 시작 옵션을 함께 점검 → 파일이 없으면 호스트에서 만든 설정을 컨테이너에 복사. 없는 파일을 docker cp 컨테이너:/경로/파일 로컬파일로 꺼내면 "no such file" 오류
# [호스트 리눅스 · root]
# 컨테이너에 전달할 설정을 호스트 작업 경로에 작성
cd /root
# 새 작업 디렉터리 (이미 있으면 mkdir 오류 가능)
mkdir rds
cd rds
vi my.cnf

# [호스트 리눅스 · /root/rds/my.cnf 파일 안]
# 공통 클라이언트에 utf8mb4 적용 → MySQL 도구의 송수신 문자셋 지정
[client]
default-character-set = utf8mb4

# mysql CLI 명령에 적용
[mysql]
default-character-set = utf8mb4

# MySQL 서버 기본 문자셋
[mysqld]
character-set-server = utf8mb4
# 유효한 기본 collation (MySQL 8.4 기본값). 문자셋 이름을 collation 값으로 쓰지 않음
collation-server = utf8mb4_0900_ai_ci
항목내용
기본값MySQL 8.4 기본 server charset/collation = utf8mb4 / utf8mb4_0900_ai_ci (출처: MySQL 8.4 Server Character Set and Collation)
# [호스트 리눅스 · root]
# 호스트 설정 파일을 컨테이너 /etc/my.cnf로 복사
docker cp /root/rds/my.cnf mysql8:/etc/my.cnf
# 설정을 읽도록 컨테이너 재시작 (단일 서비스 컨테이너는 docker로 제어)
docker restart mysql8
항목내용
재시작 방식실습 컨테이너는 systemd 서비스 관리 환경이 아님 → 호스트에서 docker restart mysql8로 프로세스 재기동. docker cp는 컨테이너가 정지된 상태에서도 파일 전달 가능
정상 확인docker ps Running → 컨테이너 안 mysql -u root -p → \s에서 Client character set utf8mb4
문자셋·collation — utf8mb4는 문자셋, utf8mb4_0900_ai_ci는 MySQL 8.4 기본 collation. [client]·[mysql]은 CLI용이라 DBeaver에는 자동 적용 안 됨

오류값이 서버를 멈추게 하는 과정

# [호스트 리눅스 · /root/rds/my.cnf 파일 안]
[mysqld]
character-set-server = utf8mb4
# 오류 재현: collation 자리에 문자셋 이름을 넣음 (collation 이름이 필요)
collation-server = utf8mb4

# [호스트 리눅스 · root]
# 잘못된 설정을 컨테이너로 복사한 뒤 서버 프로세스 재기동
docker cp /root/rds/my.cnf mysql8:/etc/my.cnf
docker restart mysql8
# 실행 중만 확인 → 죽어 있으면 -a로 종료 상태 확인
docker ps
docker ps -a
# 기동 실패 원인과 실제 오류값 확인
docker logs mysql8
항목내용
관찰된 로그[ERROR] [MY-010933] [Server] Unknown collation: 'utf8mb4'. → [ERROR] [MY-010119] [Server] Aborting
장애 이유서버가 시작 시 설정을 읽고 지원 collation인지 검사 → utf8mb4는 문자셋 이름이지 collation이 아님 → 초기화 중단 → 컨테이너가 시작했다가 종료될 수 있음
오류 처리
  • 로그의 파일·옵션·오류값을 찾아 해당 줄을 유효한 값으로 수정
  • 잘못된 설정의 주석 처리는 서비스 복구용 임시 조치, 문자셋 정책이 필요하면 올바른 collation 설정

항목내용
최적화
  • 서버 환경에 맞춰 mysqld 설정을 조정하는 작업. MySQL·MariaDB는 같은 계열이라 설정·문법이 같다는 강의 기준
  • 경량화 옵션은 [mysqld], 문자셋 설정은 [client]·[mysql]에 둠
실습 환경
  • mariadb11 컨테이너, 이미지 mariadb:11.4-ubi9, 호스트 3309 → 컨테이너 3306
  • 호스트 작업 경로 ~/rds, 설정 파일은 컨테이너 /etc/my.cnf
  • docker run에서 CPU·메모리 한도를 안 걸었다면 max_connections로 연결 수를 제한하는 방식도 검토
# [호스트 리눅스 · ~/rds/my.cnf 파일 안]
# MariaDB 클라이언트 도구 문자셋
[client]
default-character-set = utf8mb4

# mysql(mariadb) CLI 문자셋
[mysql]
default-character-set = utf8mb4

[mysqld]
# 클라이언트가 요청한 문자셋 대신 서버 설정 문자셋 사용
character-set-client-handshake = FALSE
character-set-server = utf8mb4
# collation = 문자열 정렬·비교 규칙 (백업 전용 설정 아님). 화면 파일에서 빠져 메모장 정리본에 추가된 값
collation-server = utf8mb4_unicode_ci
port = 3306
# UTC 대비 절대 오프셋 → OS가 KST여도 9시간을 다시 더하지 않음
default-time-zone = "+09:00"
# 최대 client 연결 수 (화면의 max_connection은 오타, 표준은 max_connections). 80은 하드웨어·메모리 배정에 따라 정한 값
max_connections = 80
# 비대화형 유휴 연결 timeout(초): API 서버(FastAPI 등)·APM·웹앱
wait_timeout = 600
# 대화형 유휴 연결 timeout(초): DBeaver 같은 수동 접속 도구
interactive_timeout = 600
항목내용
문자셋 설정MariaDB 11.4는 server 기본값이 배포판마다 다를 수 있음 → utf8mb4와 유효한 MariaDB collation을 명시하고 실제 상태 조회
연결 상한max_connections = 최대 client 연결 수, 값은 하드웨어·메모리 배정에 따라 결정
연결 수를 정하는 이유
  • 서비스는 메모리 보호를 위해 상한 설정, 혼자 로컬 공부할 때는 필수 아님
  • 상한 1이면 DBeaver 접속 뒤 다음 연결이 막히는 예
  • IntelliJ·Eclipse 등 개발 도구가 약 6개 연결 유지 + DBeaver SQL 편집기가 추가 연결 → 개발자 1명이 7~8개 차지하는 예 (강의 예, 모든 도구의 고정값 아님)
  • 연결을 안 닫으면 유휴 timeout 후 종료, 다시 작업하면 재연결
클라이언트별 연결IDE·DB 도구는 편집기·탭마다 여러 연결 → pool 크기·idle timeout은 개발팀과 협의, 배포 전 동시 접속 시험
계산 예와 실측
  • 연습값 sort_buffer_size=1000, join_buffer_size=3000, read_buffer_size=3000 → 합 7000, 연결 80개면 560000
  • InnoDB buffer pool 같은 cache 공간은 별도 고려
  • DB 메모리 3GB 가정 → 백업·복구까지 고려해 약 2.5GB에 맞추는 예
  • 실제 select @@sort_buffer_size; 관찰값 2097152
  • 최초 조회 때 Server has gone away 뒤 자동 재연결된 실습 결과
자원·값 협의
  • 10GB 서버 예: OS·서비스용 3GB 이상 확보 → 약 7GB를 컨테이너·데몬이 나눠 사용
  • 3GB 아래에서 Docker·crontab·SSH 문제와 out of memory 반복 가능 (강의 기준)
  • 개발 단계는 연결 약 50개로 제한 → 개발자에게 buffer 값 등을 받아 계산·확정
  • F12의 Network·Memory·Application·Performance 탭에서 페이지 할당량 확인
  • 동시 80명이 필요한데 메모리가 부족하면 연결 수를 줄이기보다 메모리 증설, timeout은 개발팀과 협의
timeout 적용
  • 게시판에서 SELECT 후 브라우저를 두는 경우 = 웹앱 연결 → wait_timeout
  • 너무 길면 연결 수 부족, 너무 짧으면 데이터가 오가는 중 끊겨 데이터 유실·timed out → 두 값을 함께 조정. 끊긴 뒤 다시 작업하면 재연결될 수 있음
시간대자료 기준 AWS·GCP·Azure 기본은 UTC, NCP는 한국 시간 → 실제 환경은 select now();로 확인
🔍 확인 필요 · 자료 안에서 충돌하는 두 항목

상한을 넘은 연결강의 메모: "상한을 넘으면 신규 연결은 대기하고 유휴 연결이 timeout으로 끊긴 뒤 연결될 수 있다" ↔ 같은 자료의 다른 정리: "대기한다고 보장되지 않고 Too many connections로 즉시 거절될 수 있음 → 모니터링·pool 제한·재시도 정책으로 대응"

-- 연습값: localhost와 % 계정은 별도 계정, 운영 암호로 쓰지 않음
CREATE USER 'hong'@'localhost' IDENTIFIED BY 'hong1234';
CREATE USER 'hong'@'%' IDENTIFIED BY 'hong1234';
-- 연습 권한: 운영은 필요한 작업만 최소 권한으로

FLUSH PRIVILEGES;
SHOW GRANTS FOR 'hong'@'localhost';
SHOW GRANTS FOR 'hong'@'%';

SELECT * FROM mysql.db WHERE user='hong';

검증 기준명령 종료 코드 성공, 로그에 치명 오류 없음, SQL 파일이 비정상적으로 짧지 않음 → 가장 확실한 건 독립된 테스트 DB에 복원해 테이블 수·행 수 검증
실습 관찰값실습 파일 약 11,992바이트 → 데이터·옵션에 따라 달라지는 관찰값, 고정 기준 아님
자동화 메모강의 메모: 셸 스크립트 + crontab 하루 1회, 다른 서버로 라이브 싱크해 복수 보관 → 운영은 보존기간·암호화·접근권한·복원 리허설 결정
PROCESS 오류가 있는 dump — 파일이 생성돼도 정상 백업 아님. MySQL 8.4는 --no-tablespaces로 PROCESS 오류 회피 → exit code·복원까지 확인. 덤프는 docker cp로 컨테이너 밖에 보관(컨테이너와 함께 잃지 않게)

SQL 분류 (DDL · DML · DCL)

분류의미·대표 명령이 수업
DDL데이터 정의어 — CREATE·ALTER·DROP (구조를 만듦)조금 사용
DML데이터 조작어 — INSERT·SELECT·UPDATE·DELETE (행을 다룸)조금 사용
DCL데이터 제어어 — 권한 제어 : GRANT(권한 부여)·REVOKE(권한 회수)거의 안 씀
TCL트랜잭션 제어 — COMMIT·ROLLBACK·SAVEPOINT용어만
항목내용주의·이유
인프라 담당 범위기본 쿼리 약 12개까지만 다룸더 깊은 쿼리는 개발자·AI·검색으로 해결

용어DDL·DML·DCL은 외워 두고, 계정·권한 실습에서 GRANT를 직접 사용 (이 파일 5장)풀스택(개발+인프라)을 다 하면 범위가 끝이 없어 DB 범위를 한정
DCL = 권한 제어 — GRANT(부여)·REVOKE(회수)가 DCL이고, COMMIT·ROLLBACK은 TCL(트랜잭션 제어). DDL은 구조, DML은 행, DCL은 권한

요청 대응"8을 5로 내려 달라"는 갑작스러운 요청에는 "왜 그렇게 해야 하나요"라고 당당히 물어봄버전을 되돌리는 작업은 데이터 유실 위험이 있어 이유와 범위를 먼저 확인
버전은 개발자가 지정 — 올리기는 5.7 → 8.0 한 단계만 공식 경로, 버전 건너뛰기와 다운그레이드(8 → 5.5)는 안 됨. 마이너 버전끼리만 통용
