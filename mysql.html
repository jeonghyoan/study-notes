항목내용
RDSAmazon Relational Database Service = MySQL·PostgreSQL 등 DB 엔진을 관리형 서비스로 제공 → AWS가 인프라 프로비저닝·유지보수·백업 같은 관리 기능 제공, 사용자는 endpoint·port·계정·DB 사용. 이 노트는 MySQL 실습만
실습 모형
  • 로컬 VirtualBox Linux 호스트 위 Docker 컨테이너에서 MySQL 실행 → DBeaver가 호스트 IP의 3306/tcp로 접속
  • 클라우드 관리형 RDS와 Docker 컨테이너는 운영 방식·관리 책임이 다름 → 동일 구조로 단정하지 않음
RDS 내부 구현"RDS 전용 서버에서 Docker로 여러 RDS를 구동" = 교육용 비유. AWS 공개 문서는 관리형 아키텍처를 설명하지만 내부 구현이 Docker라고 밝히지 않음 (참고: AWS RDS 핵심 개념·아키텍처)
실습 위치호스트 Linux 작업 경로 /root/rds, 로그인 계정 apink → root 전환. DB 클라이언트는 DBeaver
포트 선점 확인실행 전 docker ps와 호스트 LISTEN 확인 → 다른 컨테이너가 이미 3306을 게시하면 bind 실패("port is already allocated" 등) → 다른 컨테이너를 임의로 끄지 말고 사용 대상 확인

이미지 인증과 MySQL 컨테이너 실행

한눈에 보기 — 이미지 받기부터 접속까지

① 레지스트리 인증

docker login dhi.io

② 이미지 받기

docker pull dhi.io/mysql:8

③ 컨테이너 실행

-e MYSQL_ROOT_PASSWORD · -p 3306:3306

④ 접속

docker exec -it · mysql -u root -p

항목내용
레지스트리 구분dhi.io/mysql:8 = Docker Hardened Images(DHI) 레지스트리 참조 → Docker Hub 공식 MySQL 이미지와 같은 이미지라고 부르지 않음. DHI Community 이미지 pull에는 레지스트리 인증 필요
tag 관찰값
  • 실습은 :8 사용 → 서버 버전 8.4.13, 이미지 약 461MB, 이미지 목록 화면은 Debian 13 기반 표시
  • tag·용량은 갱신될 수 있음 → 실행 후 SELECT VERSION()으로 확인
dev·정식 tag실습 화면 안내: dev = 개발·테스트용, 정식 8.4 = 안정화 버전 → tag 이름만으로 지원정책을 단정하지 말고 현재 이미지 카탈로그·조직 배포 정책 확인
# [호스트 리눅스 · root]
# DHI 레지스트리 인증 → 성공 시 Login Succeeded
docker login dhi.io
# DHI MySQL tag를 내려받음 → 이미지 이름·tag 일치 확인
docker pull dhi.io/mysql:8
docker images
항목내용
인증 정보로그인 암호·access token은 명령행·노트에 기록하지 않음 (인증·이미지 형식 출처: Docker Hardened Image 사용 안내)

단일 MySQL 서비스 컨테이너

# [호스트 리눅스 · root]
# --name mysql8: 컨테이너 이름 고정 → docker logs mysql8처럼 이름으로 참조
# -e MYSQL_ROOT_PASSWORD: 이미지 초기화 때 MySQL root 암호 전달. a1234는 연습값 → 명령 기록·프로세스 정보에 노출될 수 있어 운영은 안전한 secret 경로로 주입
# -p 3306:3306: 호스트:컨테이너 순서, 호스트 3306 → 컨테이너 3306. 호스트에서 이미 사용 중이면 컨테이너 시작 실패 가능
# -d: 백그라운드 실행
docker run --name mysql8 -e MYSQL_ROOT_PASSWORD=a1234 -p 3306:3306 -d dhi.io/mysql:8
# 실행 상태와 게시 포트 확인
docker ps
# 외부:내부 포트 게시 확인
docker port mysql8
항목내용
--privileged·/sbin/initsystemd가 필요한 OS 연습용 컨테이너 방식(docker.html 3·4장). MySQL 단일 서비스 이미지는 엔트리포인트가 서버를 실행 → 별도 init 권한 불필요
MySQL 단일 서비스 실행 — MYSQL_ROOT_PASSWORD는 초기 설정용, -p 3306:3306은 호스트:컨테이너 순서. 일반 MySQL 컨테이너에는 --privileged·/sbin/init 불필요. dhi.io는 로그인 후 pull, 버전은 tag가 아니라 SELECT VERSION()으로 확인

컨테이너 사용자와 MySQL 프롬프트

# [호스트 리눅스 · root]
# 이미지 기본 사용자(mysql)로 컨테이너 셸 진입
docker exec -it mysql8 /bin/bash
# UID 0(root) 권한으로 컨테이너 셸 진입
docker exec -it -u 0 mysql8 /bin/bash
# [mysql8 컨테이너 · mysql 또는 root(-u 0)]
# MySQL root 계정으로 접속 (-p 뒤 암호는 프롬프트에서 입력)
mysql -u root -p
# [mysql8 컨테이너 · MySQL 프롬프트 · root]
\s
SELECT VERSION();
항목내용
-u 0컨테이너 프로세스를 UID 0으로 실행. 프롬프트가 I have no name!이어도 이름 해석이 안 된 것일 수 있음 → id로 uid=0 확인
최소 이미지DHI는 공격면을 줄이려 최소 구성 → vi·nano·dnf·clear가 없을 수 있음. bash: clear: command not found = clear 프로그램이 없다는 뜻, MySQL 서버 장애와 무관
기동 확인docker ps는 실행 중만 표시 → 안 보이면 docker ps -a에서 종료 상태·exit code 확인
컨테이너 사용자 구분 — docker exec -it는 이미지 기본 사용자, -u 0은 UID 0. 프롬프트 모양이 아니라 id로 권한 확인

항목내용
관찰 결과실습 화면: Server·DB character set utf8mb4, Client character set latin1. \s = 현재 세션·서버 상태를 보는 MySQL 클라이언트 명령
왜 맞추나클라이언트가 어떤 인코딩으로 보내고 서버가 어떻게 변환하는지 = 연결 문자셋이 결정 → 한글 입력 시 변환 오류·깨짐·Incorrect string value 가능 → 클라이언트·서버·DB 문자셋 확인
DBeaver 별도 설정my.cnf의 [client]·[mysql]은 MySQL CLI 클라이언트에 적용. DBeaver는 JDBC 드라이버 설정·연결 properties를 따로 사용 → CLI 설정이 자동 적용된다고 가정하지 않음

설정 파일을 찾고 호스트에서 전달

# [mysql8 컨테이너 · mysql]
# 전체 파일시스템에서 설정 파일 탐색 → Permission denied는 권한 없는 경로라는 뜻
find / -name my.cnf
# [호스트 리눅스 · root]
# 컨테이너 안에서 UID 0으로 전체 경로 탐색
docker exec -it -u 0 mysql8 find -name "my.cnf"
# [mysql8 컨테이너 · root]
# /etc 범위의 설정 파일 존재 여부 확인
find /etc -name "my.cnf"
ls /etc
ls -al /etc
# [호스트 리눅스 · root]
# 컨테이너 파일을 호스트로 복사 → 원본이 없으면 no such file 오류
docker cp mysql8:/etc/my.cnf my.cnf
# 파일이 없으면 호스트에서 작성해 컨테이너로 전달
docker cp my.cnf mysql8:/etc/
항목내용
실습 관찰
  • 사용한 dhi.io/mysql:8 컨테이너에는 /etc/my.cnf가 없었음 → 이미지·버전마다 설정 경로·include 구성이 다를 수 있어 모든 MySQL 8.4 이미지의 규칙으로 확대하지 않음
  • 실습 메모: MySQL 8.0 이미지에는 /etc/my.cnf가 있었고 사용한 8.4 tag에는 없었음 (이미지별 차이로 확인)
파일 없음 판단find /의 Permission denied = 접근 못 한 경로가 있다는 뜻 → 확인 가능한 표준 위치와 서버 시작 옵션을 함께 점검 → 파일이 없으면 호스트에서 만든 설정을 컨테이너에 복사. 없는 파일을 docker cp 컨테이너:/경로/파일 로컬파일로 꺼내면 "no such file" 오류
# [호스트 리눅스 · root]
# 컨테이너에 전달할 설정을 호스트 작업 경로에 작성
cd /root
# 새 작업 디렉터리 (이미 있으면 mkdir 오류 가능)
mkdir rds
cd rds
vi my.cnf

# [호스트 리눅스 · /root/rds/my.cnf 파일 안]
# 공통 클라이언트에 utf8mb4 적용 → MySQL 도구의 송수신 문자셋 지정
[client]
default-character-set = utf8mb4

# mysql CLI 명령에 적용
[mysql]
default-character-set = utf8mb4

# MySQL 서버 기본 문자셋
[mysqld]
character-set-server = utf8mb4
# 유효한 기본 collation (MySQL 8.4 기본값). 문자셋 이름을 collation 값으로 쓰지 않음
collation-server = utf8mb4_0900_ai_ci
항목내용
기본값MySQL 8.4 기본 server charset/collation = utf8mb4 / utf8mb4_0900_ai_ci (출처: MySQL 8.4 Server Character Set and Collation)
# [호스트 리눅스 · root]
# 호스트 설정 파일을 컨테이너 /etc/my.cnf로 복사
docker cp /root/rds/my.cnf mysql8:/etc/my.cnf
# 설정을 읽도록 컨테이너 재시작 (단일 서비스 컨테이너는 docker로 제어)
docker restart mysql8
항목내용
재시작 방식실습 컨테이너는 systemd 서비스 관리 환경이 아님 → 호스트에서 docker restart mysql8로 프로세스 재기동. docker cp는 컨테이너가 정지된 상태에서도 파일 전달 가능

항목내용
최적화

  • 경량화 옵션은 [mysqld], 문자셋 설정은 [client]·[mysql]에 둠
실습 환경
  • mariadb11 컨테이너, 이미지 mariadb:11.4-ubi9, 호스트 3309 → 컨테이너 3306
  • 호스트 작업 경로 ~/rds, 설정 파일은 컨테이너 /etc/my.cnf
  • docker run에서 CPU·메모리 한도를 안 걸었다면 max_connections로 연결 수를 제한하는 방식도 검토
# [호스트 리눅스 · ~/rds/my.cnf 파일 안]
# MariaDB 클라이언트 도구 문자셋
[client]
default-character-set = utf8mb4

# mysql(mariadb) CLI 문자셋
[mysql]
default-character-set = utf8mb4

[mysqld]
# 클라이언트가 요청한 문자셋 대신 서버 설정 문자셋 사용
character-set-client-handshake = FALSE
character-set-server = utf8mb4
# collation = 문자열 정렬·비교 규칙 (백업 전용 설정 아님). 화면 파일에서 빠져 메모장 정리본에 추가된 값
collation-server = utf8mb4_unicode_ci
port = 3306
# UTC 대비 절대 오프셋 → OS가 KST여도 9시간을 다시 더하지 않음
default-time-zone = "+09:00"
# 최대 client 연결 수 (화면의 max_connection은 오타, 표준은 max_connections). 80은 하드웨어·메모리 배정에 따라 정한 값
max_connections = 80
# 비대화형 유휴 연결 timeout(초): API 서버(FastAPI 등)·APM·웹앱
wait_timeout = 600
# 대화형 유휴 연결 timeout(초): DBeaver 같은 수동 접속 도구
interactive_timeout = 600
항목내용
문자셋 설정MariaDB 11.4는 server 기본값이 배포판마다 다를 수 있음 → utf8mb4와 유효한 MariaDB collation을 명시하고 실제 상태 조회
연결 상한max_connections = 최대 client 연결 수, 값은 하드웨어·메모리 배정에 따라 결정
연결 수를 정하는 이유
  • 서비스는 메모리 보호를 위해 상한 설정, 혼자 로컬 공부할 때는 필수 아님
  • 상한 1이면 DBeaver 접속 뒤 다음 연결이 막히는 예
  • IntelliJ·Eclipse 등 개발 도구가 약 6개 연결 유지 + DBeaver SQL 편집기가 추가 연결 → 개발자 1명이 7~8개 차지하는 예 (강의 예, 모든 도구의 고정값 아님)
  • 연결을 안 닫으면 유휴 timeout 후 종료, 다시 작업하면 재연결
클라이언트별 연결IDE·DB 도구는 편집기·탭마다 여러 연결 → pool 크기·idle timeout은 개발팀과 협의, 배포 전 동시 접속 테스트
계산 예와 실측
  • 연습값 sort_buffer_size=1000, join_buffer_size=3000, read_buffer_size=3000 → 합 7000, 연결 80개면 560000
  • InnoDB buffer pool 같은 cache 공간은 별도 고려
  • DB 메모리 3GB 가정 → 백업·복구까지 고려해 약 2.5GB에 맞추는 예
  • 실제 select @@sort_buffer_size; 관찰값 2097152
  • 최초 조회 때 Server has gone away 뒤 자동 재연결된 실습 결과
자원·값 협의
  • 10GB 서버 예: OS·서비스용 3GB 이상 확보 → 약 7GB를 컨테이너·데몬이 나눠 사용
  • 3GB 아래에서 Docker·crontab·SSH 문제와 out of memory 반복 가능 (강의 기준)
  • 개발 단계는 연결 약 50개로 제한 → 개발자에게 buffer 값 등을 받아 계산·확정
  • F12의 Network·Memory·Application·Performance 탭에서 페이지 할당량 확인
  • 동시 80명이 필요한데 메모리가 부족하면 연결 수를 줄이기보다 메모리 증설, timeout은 개발팀과 협의
timeout 적용

  • 너무 길면 연결 수 부족, 너무 짧으면 데이터가 오가는 중 끊겨 데이터 유실·timed out → 두 값을 함께 조정. 끊긴 뒤 다시 작업하면 재연결될 수 있음

복구 절차

  1. 백업 확인: 호스트 head -n 30 /root/rds/testdb.sql로 DB 이름·덤프 내용 확인. 덤프 생성 옵션에 따라 DB 생성문이 없을 수 있음
  2. 복구 범위 확인: 고객에게 DB 이름·테이블·컬럼 등 식별에 필요한 정보만 확인, 실제 고객 데이터·비밀번호는 요구하지 않음
  3. DB·권한 확인: MySQL root로 SHOW DATABASES, SHOW GRANTS → 대상 DB·계정 확인. % 원격 계정은 필요한 출발지로 제한
  4. 접근 보호: 불필요한 원격 접근 먼저 차단 → 실제 앱 서버 IP만 허용. 임시 비밀번호를 안전하게 전달하고 이후 변경 요청
  5. 빈 DB 준비: 필요하면 root로 CREATE DATABASE testdb CHARACTER SET utf8mb4. 기존 DB가 있으면 덮어쓰기 여부·복구 시점 확인
  6. 덤프 전달: 호스트에서 docker cp /root/rds/testdb.sql mysql8:/home/mysql/testdb.sql → 컨테이너에서 파일·권한 확인. 일반 mysql 계정은 홈 밖 경로에 못 써서 /home/mysql 사용, 복구는 root로
  7. 복원: 컨테이너 셸에서 root 계정으로 mysql -u root -p testdb < /home/mysql/testdb.sql (입력 리다이렉션은 MySQL 클라이언트를 실행하는 셸이 처리)
  8. 데이터 검증: SHOW TABLES, SELECT COUNT(*) FROM members로 테이블·행 수 확인 → 실습 데이터 100행이면 100인지 확인 → 담당자에게 복구 결과 검증받음

SQL 분류 (DDL · DML · DCL)

분류의미·대표 명령이 수업
DDL데이터 정의어 — CREATE·ALTER·DROP (구조를 만듦)조금 사용
DML데이터 조작어 — INSERT·SELECT·UPDATE·DELETE (행을 다룸)조금 사용
DCL데이터 제어어 — 권한 제어 : GRANT(권한 부여)·REVOKE(권한 회수)거의 안 씀
TCL트랜잭션 제어 — COMMIT·ROLLBACK·SAVEPOINT용어만
항목내용주의·이유
인프라 담당 범위기본 쿼리 약 12개까지만 다룸더 깊은 쿼리는 개발자·AI·검색으로 해결
자주 쓰는 쿼리INSERT(입력), DELETE(삭제), UPDATE(수정), SELECT(조회)이 네 개가 반복됨
용어DDL·DML·DCL은 외워 두고, 계정·권한 실습에서 GRANT를 직접 사용 (이 파일 5장)풀스택(개발+인프라)을 다 하면 범위가 끝이 없어 DB 범위를 한정
DCL = 권한 제어 — GRANT(부여)·REVOKE(회수)가 DCL이고, COMMIT·ROLLBACK은 TCL(트랜잭션 제어). DDL은 구조, DML은 행, DCL은 권한

utf8과 utf8mb4

구분내용
MySQL 5.1mb4 없음 — 무조건 utf8만 있음
MySQL 5.5부터utf8mb4 생김 (그 전에는 mb3가 있었고, mb3에서 발전한 것이 mb4)
차이게시판·카톡의 동그란 아이콘(이모지)을 쓰려면 utf8mb4여야 이미지로 뜸 — utf8만 쓰면 글자로 뜸
적용 예게시판 제작 시 브라우저 아이콘(이모지) 사용 → utf8mb4
  • utf8mb3의 한계
    utf8mb3(mb3)는 3바이트 BMP 문자만 지원 → 이모지(보충 문자)를 저장할 수 없음
  • 이모지 필수 조건
    이모지는 반드시 utf8mb4 — 4바이트 영역까지 담는 문자셋
  • 난이도
    mb3는 쉬운 편이고 mb4는 종류(콜레이션)가 많아 어려움
이모지 저장 — BMP 3바이트까지는 utf8mb3, 이모지는 보충 문자라 utf8mb4 필수. 5.1에는 mb4가 없어 이모지를 넣을 수 없고, 게시판에 아이콘을 쓸 계획이면 처음부터 utf8mb4

항목내용주의·이유

프롬프트 예"MySQL member 테이블을 만들 거야. id, password, 이메일, 연락처, 성별 … 형태로 생성해 주세요"컬럼 이름·타입을 미리 정해 두면 그대로 씀

-- [호스트 리눅스 · MySQL 프롬프트 · root]
use mall;      -- mall DB로 들어감 (테이블을 만들 DB 선택)
show tables;   -- 테이블 확인 → Empty set (아직 없음)
-- [호스트 리눅스 · MySQL 프롬프트 · root]
-- AI에게 받은 member 테이블 생성문: CREATE TABLE부터 마지막 ) 까지만 복사
CREATE TABLE member (
    -- 로그인 아이디: 기본키로 행을 구분
    id VARCHAR(50),
    -- 비밀번호: 해시 문자열이 들어가므로 길게 (255)
    password VARCHAR(255),
    -- 이메일: UNIQUE KEY로 중복 금지
    email VARCHAR(100),
    -- 연락처
    phone VARCHAR(20),
    -- 성별: M·F·OTHER 중 하나만
    gender ENUM('M','F','OTHER'),
    -- 가입 시각: 값을 넣지 않으면 현재 시간 자동 입력
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    -- 기본키: 개발자용 — 인프라는 만들어졌는지만 확인
    PRIMARY KEY (id),
    -- 이메일 중복 방지
    UNIQUE KEY uk_email (email)
);

MySQL ↔ MariaDB 호환

구분내용
연결서버에 MySQL을 깔아도 MariaDB용 연결로 접속 가능 (같은 포트, 같은 명령어, 거의 95% 동일) — "MySQL 서버면 MySQL로만 연결해야 한다"는 것은 잘못된 상식, 실무에서는 그렇게 안 함
반대 방향MariaDB 서버에 MySQL로 연결도 가능 — "인프라가 MariaDB니까 무조건 MariaDB로"라는 규칙 없음 (오라클은 오라클로 해야 함)
백업·복구MariaDB 백업을 MySQL로, MySQL 백업을 MariaDB로 복구 가능. 단 MySQL·MariaDB 백업을 MSSQL로는 복구 불가(구조가 완전히 다름)
제한호환은 버전에 따라 제한이 있음(뷰 알고리즘 차이, MySQL 5.7 JSON 등) — 서로의 백업을 항상 복구할 수 있는 것은 아님
엔진 호환 — MySQL·MariaDB는 포트·명령이 같아 클라이언트를 바꿔 연결 가능하지만, 백업 복구는 버전·기능 차이로 실패할 수 있음. MSSQL은 구조가 달라 불가

권한 부여 (GRANT)

  • 필요성
    blue로 접속은 되지만 DB가 없어 아무것도 못 함 → DB 권한을 줘야 함
-- [호스트 리눅스 · MySQL 프롬프트 · root]
use mysql;                        -- 권한 테이블이 있는 시스템 DB로 이동
show tables;                      -- db 테이블 확인
select host, db, user from db;    -- 현재 DB 권한 확인 (select * from db; 도 가능)
desc db;                          -- db 테이블의 컬럼 구조
확인 항목내용
부여 전 조회sys/mysql.sys 계정 행 외에 없음 (= 권한을 하나도 안 줌)
테이블 형식host · db · user 순서로 값이 들어감 — host는 localhost·%·IP 모두, db는 데이터베이스 이름, user는 방금 만든 사용자(blue)
순서사용자를 먼저 만들어야 여기서 권한을 줄 수 있음
desc dbAlter_routine_priv, Execute_priv, Event_priv, Trigger_priv 등 enum('N','Y') 권한 컬럼이 쭉 나옴 — select·insert·update·delete·create·drop·grant·references·alter …
N과 YN이면 그 명령 못 씀(테이블·데이터 생성 불가), Y로 줘야 사용 가능
-- [호스트 리눅스 · MySQL 프롬프트 · root]
-- erp DB의 모든 테이블에 모든 명령 허용 (erp는 루트가 미리 생성)
grant all privileges on erp.* to 'blue'@'localhost';
-- 사용자 만든 호스트마다 각각 실행 (% 계정용)
grant all privileges on erp.* to 'blue'@'%';
-- 권한 부여 현황 확인 → 4 rows in set
select host, db, user from db;
구성 요소의미
all privileges모든 명령 사용 허용
on DB명.*그 DB의 모든 테이블 (다른 지정 방식도 있으며 나중에 설명)
to '사용자'@'호스트'권한을 받을 계정
localhost·%각각 한 번씩 실행 (사용자 만든 것과 같은 방식)
선행 조건erp는 루트가 먼저 만들어 놓아야 함
회수revoke = grant의 반대 명령 — 같은 방식으로 revoke all privileges on erp.* from 'blue'@'%';
철자grant, privileges(P-R-I-V-I-L-E-G-E-S), on, erp.*, to
  • 실수 사례
    사용자를 localhost만 만들었는데 grant에서 %를 쓰면 에러 — 사용자 생성도 grant도 localhost 한 번 + %(또는 IP) 한 번 따로 해야 함 (red를 localhost와 IP로 만들었다면 grant도 각각)
  • 실행 결과
    select host, db, user from db; → 4 rows in set (이전 2행 + erp/%/blue, erp/localhost/blue). DBeaver 연결을 새로고침하면 erp 데이터베이스가 보임
  • flush 불필요
    grant 직후 서버가 즉시 반영 → flush privileges·mysqladmin … reload가 필요 없음. 필요한 경우는 grant 테이블을 직접 수정했을 때뿐
GRANT — 사용자를 만든 호스트(localhost·%·IP)마다 한 번씩 따로 실행. 없는 호스트로 grant하면 에러, GRANT는 서버가 즉시 반영하므로 flush는 grant 테이블 직접 수정 때만

일반 사용자 DB 연결 순서

순서작업
1root가 DB를 먼저 생성(mall, erp 등 신규 DB)
2use mysql;로 이동
3create user '아이디'@'localhost' identified by '패스워드'; (+ %/IP용을 한 번 더)
4grant all privileges on <DB명>.* to '아이디'@'localhost'; (+ %/IP용을 한 번 더)
5flush privileges; (또는 mysqladmin … reload) → 반영 확인용

WHERE 없는 삭제delete from user;를 엔터로 실행하면 user 테이블의 모든 사용자가 root까지 삭제delete·drop 두 단어는 정말 조심 — 서버를 통째로 잃는 사고
실행 결과delete … where user='ollama' → Query OK, 1 row affected, 확인 조회 → Empty set지운 사용자는 아이디·패스워드를 알아도 접속 불가 (반영 후)
flush 누락삭제 후 반영하지 않으면 사용자가 계속 접속됨flush privileges; → Query OK, 0 rows affected → 그때부터 접속 불가
긴급 차단DB 인젝션으로 패스워드가 유출된 상황 → 사용자 정지 기능이 없으므로 해당 사용자를 delete 후 flush privileges로 굉장히 빠르게 접속 차단차단이 목적이면 삭제 + flush가 가장 빠름
공식 방식사용자 삭제는 DROP USER가 공식 방식delete from user 직접 DML은 reload 전까지 반영되지 않고 db 등 관련 테이블이 남아 ERROR 1396을 부름
습관권한 테이블을 직접 고쳤으면 flush privileges까지 실행안 하면 지운 사용자가 계속 접속하는 상태로 남음
WHERE 없는 delete — delete from user;는 root까지 전부 삭제. 삭제 후 flush privileges가 없으면 기존 접속이 계속 살아 있고, 공식 삭제 명령은 DROP USER

사용자 재생성 ERROR 1396 — 매칭부터 끊기

항목내용
상황패스워드 유출 → 다른 팀과 협의해 패스워드 변경하기로 하고, 지운 사용자를 새 패스워드로 다시 만들려는 시점
에러 문구ERROR 1396 (HY000): Operation CREATE USER failed for 'ollama'@'localhost'
원인db 테이블에 매칭(권한 연결)이 남아 있어 생성이 불가능
규칙매칭을 먼저 끊고 사용자를 삭제·재생성 — 순서를 뒤섞으면 어디서부터 잘못됐는지 파악이 안 됨
-- [호스트 리눅스 · MySQL 프롬프트 · root]
-- 지운 사용자를 새 패스워드로 재생성 시도 → ERROR 1396
create user 'ollama'@'localhost' identified by 'b1234';
-- db 테이블의 매칭만 삭제 (DB 자체를 지우는 것이 아님)
delete from db where user='ollama';
-- 확인 (ollama 행이 없어야 함)
select * from db;
-- 반영
flush privileges;
-- 재생성
create user 'ollama'@'localhost' identified by 'b1234';
  • 실행 결과
    delete → Query OK, 1 row affected, flush·create user → Query OK, 0 rows affected (재생성 성공)
  • flush 누락
    반영하지 않으면 삭제만으로는 재생성이 안 됨
  • 매칭과 DB
    db 테이블 행 삭제는 DB 자체 삭제가 아님 — 올라마가 만든 테이블·데이터는 그대로 있고 매칭만 끊고 연결하는 것이 인프라 담당자 역할
  • 개발자 데이터
    모르고 DB를 drop하면 난리 — 개발자가 만든 DB 데이터는 절대 건드리지 않음
  • 다른 DB도 동일
    매칭을 먼저 끊고 사용자를 삭제. 사용자부터 지우면 재생성이 안 되고 개발자 문의가 계속 오며 리눅스 문제로 오해하게 됨
ERROR 1396 — 지운 사용자의 CREATE USER가 실패하면 db 테이블 매칭이 남은 것. delete from db where user=… → flush privileges → create user 순서. drop database와는 전혀 다른 작업

레플리카 환경에서의 위험

항목내용주의·이유
현재로컬 단독 서버라 워커와 연결을 안 했으므로 빨리 지우고 다시 만들어도 됨실습에서 순서를 익히는 이유
다음 구성마스터 서버 1대 + 워커(레플리카) 서버 여러 대마스터에서 만든 사용자·테이블이 워커에 자동 동기화되어 똑같이 생성됨
어긋날 때마스터에서 사용자·테이블을 어설프게 지우고 만들면 워커와 어긋나 서버가 에러를 내고, 마스터에 다시 넣어도 에러당황해서 워커를 건드리면 안 됨 (동기화 방식이 따로 있음)
동기화 기술마스터→워커 동기화는 MySQL 복제(replication) 기능오토 스케일링과 별개 — 레플리카는 읽기 부하 분산(scale-out)에 쓰이고 서버 자동 증감과 무관
사고 대응마스터가 해킹당해 박살 나면 셧다운하고 워커(레플리카)를 마스터로 승격해 운영개인정보가 있으면 뉴스·검찰 조사로 이어지므로 인프라 담당자의 판단이 필요
증상워커가 연결된 상태에서 사용자 생성이 안 되거나 워커가 계속 비어 있으면 원인 파악이 어려움지금 배우는 절차를 순서대로 정확히 해야 나중에 워커 핸들링이 편해짐
레플리카 — 마스터의 계정·권한 변경이 워커로 복제되어 어긋나면 서버 에러. 워커를 임의로 건드리지 말고 마스터에서 순서대로 다시. 동기화는 복제 기능이고 오토 스케일링과 무관

패스워드 변경 — 삭제 대신 수정

버전방법구문
구버전user 테이블 update슬라이드 표기 update user passwd = password('') where user='아이디'; — 구문이 불완전하고, 5.6 이하의 정확한 형태는 UPDATE mysql.user SET Password=PASSWORD('새PW') WHERE User='아이디'; 후 FLUSH PRIVILEGES; (5.7.6부터 Password 컬럼이 authentication_string으로 대체)
신버전(8.x)alter useralter user '아이디'@'localhost' identified by '변경패스워드';
-- [호스트 리눅스 · MySQL 프롬프트 · root]
-- 사용자 정보 유출 상황: 삭제하지 않고 패스워드만 변경 (b1234는 연습값)
alter user 'ollama'@'localhost' identified by 'b1234';
-- 슬라이드 절차의 마지막 단계: 권한 테이블을 직접 수정한 경우 반영
flush privileges;
  • 버전 차이
    구버전은 UPDATE 쿼리로 패스워드 변경, 8번대는 ALTER로 수정 — AI에게 물어도 같은 답이 나오는 지점
  • 반영
    계정 관리 문장은 서버가 즉시 반영하고(11장), 테이블을 직접 수정했을 때만 flush privileges 필요
  • 접속 정리
    변경 후 기존 접속은 해제하고 처리
  • 정리
    패스워드만 바꿀 거면 UPDATE/ALTER USER, 사용자 삭제는 마지막 수단 (앞의 재생성 실패)
패스워드 변경 — 사용자 정보 유출 시 삭제가 아니라 ALTER USER(8.x)·UPDATE(구버전)로 변경. 삭제는 db 매칭 때문에 재생성 실패(ERROR 1396)를 부르므로 마지막 수단

신버전 매칭 — GRANT ALL PRIVILEGES

-- [호스트 리눅스 · MySQL 프롬프트 · root]
-- 구버전의 y 19개 입력 대신 GRANT로 매칭 (to 뒤 사용자@호스트는 필수)

-- 반영

범위ollama.* = ollama DB의 모든 테이블

리눅스 계정과 DB 계정은 별개

항목내용
DB 계정DB에서 사용자를 만들고 GRANT로 권한을 줘도 푸티로 리눅스에 접속할 수는 없음
푸티 접속DB 사용자(예: ollama)를 푸티로 접속시키려면 DB에서 빠져나와 리눅스에 useradd로 사용자를 따로 만듦
구분GRANT가 아니라 리눅스 계정 세팅 문제 — DB 사용자를 만들었다고 포트 접속이 되는 것이 아님
같은 맥락루트 DB 계정 ≠ 루트 리눅스 계정 (9장)
DB 계정 ≠ 리눅스 계정 — GRANT로 DB 권한을 줘도 푸티 로그인은 불가. 리눅스 사용자는 useradd로 따로 만들고 두 계정 체계를 섞지 않음
  • 계정·GRANT 기본
    루트 패스워드·사용자 생성·호스트별 계정·DBeaver 원격 접속: 이 파일 11장
  • host 계정 문법
    컨테이너에서 'hong'@'localhost'·'hong'@'%'로 권한을 나누는 예: 이 파일 5장
  • 백업·복구
    사용자·권한을 정리한 뒤 데이터를 백업하고 되살리는 절차: 이 파일 13장
  • SQL 분류
    DDL·DML·DCL·TCL 전체표: 이 파일 9장

# DB 전체를 SQL 파일로 백업. -u root = 최고관리자가 직접 백업, -p = 엔터 후 패스워드 입력

-p패스워드 입력엔터 후 루트 패스워드를 물어봄

테이블만·추가·날짜 파일명

# [호스트 리눅스 · root · /home/backup]
# 특정 테이블(pay)만 백업 — DB 전체 백업이 아님

# 파일 끝에 이어 쓰기 (덮어쓰지 않음)
mysqldump -u root -p ollama >> ollama.sql
# 날짜(YYMMDD)를 붙인 파일명 — 2026-10-14 실습
mysqldump -u root -p ollama > ollama_261014.sql
항목내용주의·이유
테이블 지정DB명 뒤에 테이블 이름을 주면 그 테이블만 백업DB 전체가 너무 커서(예: 6GB 이상) 통째로 받기 애매할 때 사용
경로현재 경로가 백업 디렉토리면 경로 생략 가능, 다른 디렉토리면 전체 경로 지정어디에 파일이 생겼는지 모르면 백업 확인이 안 됨
>>파일 끝에 추가덧붙인 덤프를 복구해도 데이터가 꼭 중복되지는 않음 — mysqldump는 기본(--opt)으로 테이블마다 DROP TABLE 후 CREATE를 넣어 복구 결과가 마지막 덤프 내용이 됨 (--skip-add-drop-table이면 중복)
덮어쓰기같은 파일에 계속 쓰면 이전 백업이 사라지므로 한 번만 쓰는 >를 권장날짜를 붙인 파일명으로 그 날짜에 맞게 백업
덤프 파일명 — >는 덮어쓰기, >>는 파일 끝 추가. 기본 덤프는 복구 시 테이블을 DROP·CREATE하므로 마지막 덤프가 남고, 이전 백업을 살리려면 날짜를 붙인 새 파일명을 씀

-- [호스트 리눅스 · MySQL 프롬프트 · root]

사고 판정복구했는데 데이터가 안 보이면 사고가 터진 것
# [호스트 리눅스 · root]
# 백업 파일 내용을 입력으로 넘겨 복구. 복구는 mysqldump가 아니라 mysql
mysql -u root -p ollama < /home/backup/ollama.data
항목내용
기호 구분<는 셸의 입력 리다이렉션, >는 출력(파일을 비우고 쓰기), >>는 추가
역할백업은 mysqldump, 복구는 mysql → 나중에 셸(shell) 스크립트로 자동화할 때 이 구분을 씀
에러처음 실행하면 Unknown database 'ollama' — DB를 drop해서 날렸으므로 복구 전에 DB를 먼저 생성해야 함 (DB 테두리가 없으면 안의 테이블·데이터만 복구할 수 없음)
-- [호스트 리눅스 · MySQL 프롬프트 · root]
-- 복구 전에 DB를 먼저 생성
create database ollama;
-- 리눅스 쉘로 복귀한 뒤 방향키 ↑로 실패한 복구 명령 재실행
exit
순서작업
1mysql -u root -p로 접속
2create database ollama;로 DB 생성 (테이블·데이터는 아직 없음)
3exit로 리눅스 쉘 복귀
4방향키 ↑로 아까 실패한 mysql -u root -p ollama < /home/backup/ollama.data 재실행 → 성공(OK)
-- [호스트 리눅스 · MySQL 프롬프트 · root]
-- 복구 후 확인: DB 선택 → 테이블 → 데이터
