사용자·그룹 만들기

# [마스터·워커 공통 · root · 두 서버 모두]
useradd sparkuser             # Spark 전용 일반 사용자 생성 (홈 /home/sparkuser 함께 생성)
passwd sparkuser              # 비밀번호 설정 — 없으면 키 전송·로그인 불가
usermod -aG wheel sparkuser   # wheel(관리자 그룹) 추가, -aG=기존 보조 그룹 유지한 채 추가
su sparkuser                  # root → sparkuser 전환 (두 서버 모두)
# [마스터·워커 공통 · sparkuser]
cd /home/sparkuser            # 홈으로 이동
pwd                           # 두 서버의 경로가 같은지 확인
항목내용주의·이유
두 서버 동일마스터·워커에 같은 이름·같은 그룹 설정으로 계정 생성한쪽만 만들면 이후 키·설정 전송·클러스터 연결 단계에서 실패
그룹까지 동일wheel 추가 여부까지 맞춤계정 이름만 같고 권한이 다르면 서버마다 실행 결과가 달라짐
홈 경로/home/sparkuser두 서버의 경로가 같아야 scp 목적지·.bashrc 작업을 같은 명령으로 처리

SSH 키 생성

# [마스터·워커 공통 · sparkuser · 각 서버에서 자기 키]
ssh-keygen -t rsa -b 3072   # RSA 방식(-t), 3072비트(-b) 키 생성
항목내용주의·이유
생성 위치각 서버가 자기 서버에서 sparkuser로 생성마스터에서 만든 키를 워커에 복사해 주는 방식이 아님 — 서버마다 자기 개인 키·공개 키 쌍 필요
비트 수-b 3072 (화면 입력값은 4090)RSA는 최소 1024비트이고 기본값 3072비트(3072면 충분), 관례값 3072 또는 4096. 4090은 비표준 값이라 3072·4096으로 생성 (출처: man ssh-keygen)
패스프레이즈첫 생성 때 지정 (값은 기록하지 않음)키 파일 자체를 보호하는 암호. 생성 후 질문에 답하면 ~/.ssh/id_rsa·id_rsa.pub 생성
재생성질문이 나오면 Enter만 계속 입력, overwrite?가 나올 때만 y패스프레이즈를 비우고 다시 만들 때의 절차 — 아무 값도 넣지 않음
실수 사례먼저 만들어 둔 키로 접속이 안 되다가 다시 만들자 바로 작동키는 지우고 다시 만들어도 됨 — 원인을 찾느라 시간을 쓰기 전에 재생성이 빠름

키 전송 (ssh-copy-id)

Spark가 마스터·워커를 IP가 아닌 이름으로 찾아야 하므로 /etc/hosts 등록(아래)과 키 배포가 한 쌍. hosts가 등록된 상태에서 키가 서로 오갈 수 있음. 순서는 자기 서버 먼저 → 상대 서버.

# [마스터 · sparkuser · 워커에서도 sparkuser로 똑같이 실행]
ssh-copy-id sparkuser@spark-master   # 자기 서버에 내 공개 키 등록 (자기 자신도 키 인증 대상)
ssh-copy-id sparkuser@spark-worker   # 상대 서버 sparkuser의 authorized_keys에 공개 키 추가
화면의미다음 조치
Continue connecting (yes/no)?그 서버에 처음 접속해 호스트 키를 모르는 상태yes 입력 → 이어서 비밀번호 입력. 한 번 넣으면 이후엔 키로 접속
Number of key(s) added: 1공개 키 1개가 등록됨정상 전송 — 이 문구가 확인 기준
[spark-master]:9022 표시예전에 다른 포트로 접속한 기록(known_hosts)이 함께 보임이번 접속은 22번 — 예전 기록 때문에 실패한 것은 아님
비밀번호를 계속 물음키 등록 실패(패스워드 로그인 상태)키 생성 위치·계정·authorized_keys 확인 후 재전송

이름으로 접속 확인

# [마스터 · sparkuser]
ssh sparkuser@spark-worker   # IP 대신 /etc/hosts에 등록한 이름으로 워커 접속
exit                         # 접속 종료, 원래 서버로 복귀

/etc/hosts에 등록해 두면 IP 대신 이름만 넣어도 해당 IP 서버로 접속 — 이름이 주소의 별칭 역할. 비밀번호를 묻지 않고 프롬프트가 뜨면 키 인증까지 정상.

hosts 설정 (/etc/hosts)

# [마스터·워커 공통 · /etc/hosts 파일 안 · root · 두 서버 모두]
# 기존 두 줄(127.0.0.1 localhost …, ::1 localhost …)은 손대지 않고 그 아래에 추가
# 형식: IP 한 칸 띄우고 이름
192.168.222.2 spark-master
192.168.222.3 spark-worker
# [마스터·워커 공통 · root]

항목내용주의·이유
이름앞서 바꿔 둔 호스트네임과 맞춤(spark-master·spark-worker)이름이 어긋나면 workers 파일·SPARK_MASTER_HOST와 연결되지 않음
IP각자 자기 서버 IP강사 환경 IP를 그대로 쓰면 다른 서버를 가리킴
양쪽 등록마스터·워커 두 서버 모두 같은 두 줄 입력한쪽에만 있으면 그 방향 통신만 실패
적용저장하면 끝, 재시작(restart) 불필요파일을 읽을 때마다 조회 — 서비스 재시작과 무관
위험처음 만지는 파일이라 신중히 편집잘못 수정하면 이름 접속뿐 아니라 서버 접속 자체가 안 될 수 있음
/etc/hosts — 두 서버 모두에 같은 두 줄, 127.0.0.1·::1 기존 줄은 유지. 저장만으로 적용되고 재시작 불필요. 이름은 호스트네임과 일치, IP는 각자 자기 서버

클라우드(VPC)에서의 전제

구분내용주의·이유
같은 VPCAWS·GCP에서도 같은 VPC 안의 서버끼리는 사설 IP로 Spark 통신 가능마스터·워커가 같은 네트워크 그룹에 있어야 하는 조건이 VPC
다른 VPCVPC 피어링(VPC Peering)을 만들면 서로 다른 VPC도 사설 IP로 통신피어링 없이 다른 VPC에 있는 서버는 사설 IP 직접 통신 불가 (출처: AWS VPC Peering 문서)

/opt 디렉토리

리눅스의 OPT = 선택(optional) 패키지를 설치하는 디렉토리. 서드파티·애플리케이션 설치 공간이고, / 최상위 바로 아래라 root 소유 — 일반 사용자(sparkuser)는 쓰기 접근 불가. 그래서 설치는 root로.

# [마스터·워커 공통 · sparkuser]
ls -al /opt   # 소유자 확인 — root 소유라 sparkuser는 쓸 수 없음
exit          # sparkuser에서 나와 root로 복귀
# [마스터·워커 공통 · root]
cd /opt       # 설치 위치로 이동 (두 서버 모두)
항목내용주의·이유
/opt와 /tmp/opt는 패키지·앱을 설치하는 곳, /tmp는 임시 파일 공간설치 대상은 /opt — 재부팅·정리 정책에 지워지지 않는 위치

트러블슈팅: 워커에서 Java 경로 에러

한눈에 보기 — spark-class 에러에서 JDK 설치까지

① 증상

spark-class 줄 71 java 없음

② 경로 재확인

find 결과 없음

③ 원인

JRE만 설치

④ 해결

dnf install java-17*

⑤ 확인

3.5.9 출력

증상

# [워커 · sparkuser]
spark-submit --version   # 워커에서 Spark 버전 확인 시도
# 실행 결과 (에러)
/opt/spark/bin/spark-class: 줄 71: /usr/lib/jvm/java-17-openjdk/bin/java: 그런 파일이나 디렉터리가 없습니다
/opt/spark/bin/spark-class: 줄 97: CMD: 잘못된 배열 첨자

의미는 하나 — JAVA_HOME이 가리키는 경로에 java 실행 파일이 없음. 경로 오타를 조심해야 하는 이유가 이 에러로 바로 드러남.

원인

확인결과판단
오타 점검.bashrc·spark-env.sh의 경로를 다시 확인경로 표기는 정상 — 오타 문제가 아님
find /usr/lib -name "java-17-openjdk"워커에서 결과 없음디렉토리 자체가 없음
java -version정상 출력실행 환경(JRE)은 있음
/usr/lib/jvm 목록jre-17 계열 링크만 있음JDK(java-17-openjdk-devel)가 아닌 JRE만 설치된 상태 — 설치 오류가 아니라 설치 범위 차이

java-17-openjdk 디렉토리는 JDK 패키지가 만들고, JRE만 있으면 그 이름의 디렉토리가 생기지 않음 → JAVA_HOME 경로가 비어 있는 것과 같은 상태.

해결

# [워커 · root]
dnf install java-17*   # java-17로 시작하는 패키지 전부 설치 (별표 = 와일드카드)
항목내용주의·이유
설치 결과java-17-openjdk-devel 추가 설치(4.7M)이 패키지가 /usr/lib/jvm/java-17-openjdk 경로를 만듦
별표의 뜻이름이 java-17로 시작하는 패키지를 모두 설치관련 패키지가 한 번에 깔리는 것이 정상 — 일부만 깔려 있던 상태였다는 뜻
Spark 영향JRE만으로는 Spark 기동 불가spark-class가 JAVA_HOME/bin/java를 직접 실행하기 때문

확인

# [워커 · sparkuser]
find /usr/lib -name "java-17-openjdk"   # 경로가 생겼는지 재확인
spark-submit --version                  # 에러 없이 버전 출력되는지 확인

워커에서도 version 3.5.9가 나오면 마스터·워커 모두 작동하는 상태 — 이후 클러스터 기동(5장)으로 진행.

Java 경로 에러 — java -version이 되는데 java-17-openjdk 디렉토리가 없으면 JRE만 설치된 상태. dnf install java-17*로 -devel(JDK)까지 설치해야 JAVA_HOME 경로가 생김
  • 자세한 실습
    dnf 설치·와일드카드: linux.html 13장 / find -name: linux.html 16장

Spark 3.5.3 이미지: Dockerfile 작성·빌드·검증

한눈에 보기 — Spark를 이미지에 미리 설치

① 기존 파일 백업

mv Dockerfile Dockerfile_backup

② 베이스 점검

java -version → 없음이 정상

③ Dockerfile

Java 17 · Spark 3.5.3

④ 빌드

docker build -t spark-rocky9:3.5.3 .

⑤ 검증

java -version · python3 --version

항목내용
선행 작업마스터·워커·Jupyter가 이름으로 통신할 사용자 정의 네트워크 spark-net을 먼저 생성 → 자세한 실습: docker.html 9장
실습 환경
  • Rocky 9 VM 호스트 전용 IP 192.168.222.5, PuTTY 접속, 작업 경로 /root/docker
  • 강사 빌드 베이스 mzleejh/apink_rocky:9, 수강생은 각자 만든 Rocky 9 이미지 사용
기존 파일이전 용도의 Dockerfile → Dockerfile_backup으로 이름 변경 후 새 Dockerfile 작성. 기본 파일명 오타는 빌드를 막음
베이스 점검 결과
  • java -version → Java 없음이 정상 (Java 11이 있어도 17 설치)
  • /etc/ssh/sshd_config 있음 → SSH 추가 설치 불필요
  • /etc/vsftpd 유지, httpd 설치됨, nginx·MySQL 등 DB 없음
이미지화 이유Dockerfile = 이미지 정의, Spark 설치는 빌드 과정에서 진행 → OS 컨테이너에 매번 직접 설치하지 않고 Spark 이미지로 재사용, 실무는 Docker Hub에 올려 버전 관리
# [호스트 리눅스 · root]
cd /root/docker
mv Dockerfile Dockerfile_backup                      # 기존 파일 보존 + 새 기본 파일명 확보
ls -al                                               # 이름 변경 확인
docker run --rm -it mzleejh/apink_rocky:9 /bin/bash  # 임시 컨테이너에서 베이스 점검 (--rm: 나오면 삭제)
exit                                                 # 점검 후 임시 컨테이너 종료·삭제

# [호스트 리눅스 · /root/docker/Dockerfile 파일 안]
# 기반 OS 이미지 (각자 만든 Rocky 9 이미지)
FROM mzleejh/apink_rocky:9
# -y 자동 승인 / --allowerasing: 의존성 충돌 시 기존 패키지 제거·교체 허용 (Rocky 9의 curl-minimal ↔ curl 충돌 사례)
# java-17-openjdk-devel: Java 17 + 개발 도구 javac / curl·tar: 다운로드·압축 해제 / python3·python3-pip: PySpark·Jupyter용
# 여러 줄은 역슬래시로 연결, && 앞뒤 공백 / dnf clean all: 캐시 정리로 이미지 크기 감소
RUN dnf install -y --allowerasing java-17-openjdk-devel \
 curl tar python3 python3-pip && dnf clean all
# Java 설치 경로
ENV JAVA_HOME=/usr/lib/jvm/java-17-openjdk
# 받을 배포본 선택값 (버전을 바꿀 때는 이 값만 바꿔 URL 관리)
ENV SPARK_VERSION=3.5.3
ENV HADOOP_VERSION=3
# Spark 설치 경로
ENV SPARK_HOME=/opt/spark
# Spark·Java의 bin을 PATH에 추가 → 어느 경로에서나 실행. ENV 이름=값은 등호 주변을 붙여 씀
ENV PATH=$SPARK_HOME/bin:$JAVA_HOME/bin:$PATH
# 아카이브를 받아(curl -sL) 파이프로 압축 해제 (x 풀기, z gzip, -C 대상 경로) → spark-3.5.3-bin-hadoop3를 /opt/spark로 이동
# ${변수}: 뒤에 다른 글자가 이어질 때 변수 경계 표시 (독립 변수는 $변수)
RUN curl -sL https://archive.apache.org/dist/spark/spark-${SPARK_VERSION}/spark-${SPARK_VERSION}-bin-hadoop${HADOOP_VERSION}.tgz | tar -xz -C /opt/ && mv /opt/spark-${SPARK_VERSION}-bin-hadoop${HADOOP_VERSION} $SPARK_HOME
# 컨테이너 기본 작업 경로
WORKDIR $SPARK_HOME
항목내용
Java 버전Spark 3.5.3은 Java 8·11·17 지원 → Java 11이 반드시 오류를 내는 것은 아님, 이 구성은 17 선택 (출처: Spark 3.5.3 문서)
아카이브 URL 찾기Spark 다운로드 페이지 → Archived releases → 3.5.3 선택 (최신 목록의 더 높은 버전과 구분) → 버전 폴더의 spark-3.5.3-bin-hadoop3.tgz 링크로 URL 작성 → 버전 숫자는 ${SPARK_VERSION}·${HADOOP_VERSION}으로 치환. 버전·철자를 정확히 맞춤
작성 요령vi에서 set number로 행 번호 표시, 터미널 붙여넣기는 Shift+Insert
Spark Dockerfile — --allowerasing=충돌 패키지 교체 허용(curl-minimal↔curl), -devel=javac 포함, ${변수}=문자열 뒤 경계 표시, tar -xz -C=gzip 풀어 대상 경로로. 설치를 이미지에 넣어 재사용
# [호스트 리눅스 · root · /root/docker]
docker build -t spark-rocky9:3.5.3 .                # 현재 경로 Dockerfile로 이름:버전 이미지 빌드
docker images                                        # 이미지 목록·크기 확인
docker run --rm spark-rocky9:3.5.3 java -version     # Java 런타임 확인
docker run --rm spark-rocky9:3.5.3 javac -version    # 컴파일러 확인
docker run --rm spark-rocky9:3.5.3 python3 --version # Python 3 확인 (python -V는 실행 파일이 없어 오류)
항목내용
태그·크기
  • -t 태그 = 이미지명 spark-rocky9 + Spark 버전 3.5.3
  • 실습 결과 약 2.73GB (CONTENT SIZE 932MB), 베이스는 1.55GB
  • 이미지가 안 보이면 빌드 실패 확인
정상 출력
  • Java openjdk 17.0.21, javac 17.0.21, Python 3.9.25 (실습 출력값)
  • python -V는 실행 파일이 없어 오류 → python3으로 확인
검증 실패 시컨테이너에서 반복 설치하지 않음 → Dockerfile 수정 → 실패 이미지 제거 후 재빌드

    서버 2대에 tarball로 직접 설치(sparkuser·SSH 키·hosts·/opt·.bashrc·spark-env.sh): 이 파일 2~6장

마스터 컨테이너 기동·재시작

한눈에 보기 — 마스터를 사용자 정의 네트워크에서 기동

① 점유 확인

docker ps

② docker run

--network spark-net · -p 7077:7077

③ spark-class Master

--host spark-master

④ 확인

UI Status ALIVE · 버전 3.5.3

# [호스트 리눅스 · root]
docker ps                                            # 기존 이름·포트 점유 확인
# 순서: Docker 옵션 → 이미지명 → 실행 명령
# -d 백그라운드 / --name 컨테이너 이름 / --hostname 컨테이너 내부 호스트명 / --network 사용자 정의 네트워크 연결 / -p 호스트:컨테이너
# spark-class가 JVM으로 Master 클래스를 실행 (전체 경로·대문자 Master 정확히)
# --host: 이름 DNS로 찾을 주소 (--ip는 deprecated) / --port 7077: 기본값이라 생략 가능하지만 명시 / --webui-port 8080: UI 포트
docker run -d --name spark-master --hostname spark-master --network spark-net \
 -p 8080:8080 -p 7077:7077 -p 8888:8888 \
 spark-rocky9:3.5.3 \
 /opt/spark/bin/spark-class org.apache.spark.deploy.master.Master \
 --host spark-master --port 7077 --webui-port 8080
docker ps                                            # Up과 포트 게시 확인
docker stop spark-master                             # 자동 재기동 확인을 위한 중지
docker start spark-master                            # 시작 명령으로 지정된 마스터가 자동 기동
항목내용
임시 실행이번 실행은 CPU·메모리 옵션을 넣기 전 연습 → 완료본 아님. 같은 이름 컨테이너가 있으면 docker run이 이름 충돌로 실패 → 기존 것 먼저 삭제
시작 명령spark-class ... Master를 컨테이너 시작 명령으로 지정 → docker start 때 마스터 자동 기동
마스터 주소사용자 정의 네트워크 DNS에서 spark-master로 찾음 → 화면 주소 spark://spark-master:7077 (출처: Spark Standalone 문서)
정상 확인
  • docker ps에서 spark-master Up + 7077·8080·8888 게시
  • http://192.168.222.5:8080 → Spark Master, 버전 3.5.3, Status ALIVE, Workers 0·Alive Workers 0이면 성공
  • stop 뒤 UI 접속 불가, start 뒤 자동 복구 확인. 컨테이너 생성은 수 초 내 완료
AWS 비교
  • 수강생 계정은 VPC·서브넷이 없는 상태 → AWS 실습은 하지 않고, 운영 계정의 VPC·서브넷·flow 구성은 필요한 구축 범위를 확인하는 화면 시연
  • MFA 로그인 설정의 MFA 기기·설정은 삭제 금지 (관리자가 설정, 삭제하면 계정 접속 불가)
