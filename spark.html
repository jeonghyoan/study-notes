아키텍처 용어 — Master·Driver·Executor·Task

아키텍트가 쓰는 용어와 다른 부분이 있어 소통을 위해 정리 — 같은 대상을 다른 이름으로 부르는 경우가 많음.

용어뜻메모
Master 서버마스터아키텍트도 같은 용어로 부름
Slave 서버= Worker아키텍트가 slave라고 하면 워커로 이해
DriverSpark 프로그램을 받아 전체 애플리케이션을 실행하는 총괄 프로세스"Spark 드라이버 구축"이라는 말의 대상. 자동차·C 드라이버와 무관한 IT 용어
Task드라이버가 각 워커 노드의 executor에 할당하는 작업 단위task 할당이 드라이버의 주요 역할
Executor일꾼 — CPU core에 맞춰 작동하고, 몇 개 띄울지·어떤 작업을 수행할지 결정 (스타크래프트의 SCV 비유)코어 개수에 맞춰 동작

애플리케이션 실행 순서

① 제출

spark-submit

② 드라이버

main() 실행 · SparkContext

③ 마스터

executor 자원 할당

④ task 분배

드라이버가 스케줄

⑤ 연산

executor가 코어·메모리로 실행

드라이버가 main()을 실행하고 SparkContext로 task를 스케줄 — 마스터는 executor 자원을 할당하는 역할만 담당하고, executor(일꾼) 수를 확인해 각자 얼마나 가져갈지 계산하는 것이 task 할당

용어 구분 — Slave=Worker, Driver=전체 애플리케이션을 실행하는 총괄 프로세스, Executor=코어 단위 일꾼, Task=executor에 내려가는 작업 단위. 마스터는 start·stop과 자원 할당, 연산은 워커의 executor

노드·클러스터 용어 — 개발자와 인프라

같은 "노드"라도 분야마다 다른 대상을 가리켜 개발자와 이야기할 때 부딪힘 — 대화 전에 어느 쪽 의미인지 구분.

구분뜻메모
개발자의 노드Node.js, 자료구조(링크드 리스트)의 노드Node.js는 브라우저 밖에서 JavaScript를 실행하는 오픈소스 런타임 환경(언어는 JavaScript) — 스크립트 언어라는 표현은 정확하지 않음
인프라의 노드분산 컴퓨팅 시스템(클러스터)을 이루는 컴퓨터(서버) 1대 — master node·worker node시스템을 이루는 한 부분(파트)
같은 말worker node = slave node연식 있는 인프라 담당자는 slave node로 부름
실습 서버Node.js도 이미 설치돼 있음개발자 관점과 무관 — 인프라 용어와 다른 층
두 의미전혀 무관개발자와 마스터·워커 이야기가 통하지 않고 부딪히는 이유
용어내용주의·이유
클러스터독립된 여러 대의 컴퓨터(노드)를 고속 네트워크로 연결해 하나처럼 쓰는 방식노드=컴퓨터=서버. 마스터 노드=마스터 서버, 워커 노드 2개=워커 서버 2대 (2장)
노드의 역할클러스터를 이루는 개별 머신클러스터 전체를 제어·관리하는 두뇌 역할은 컨트롤 플레인(마스터 쪽 구성요소)이 맡음 — 출처: Kubernetes 문서
컨트롤 플레인 구성설명

코어·메모리 배분 계산

하드웨어 정보를 모르고 Spark를 설치하면 안 됨 — 서버 사양이 자원 지정의 기준. 코어·메모리는 환경 설정으로 항상 넣고, 고정값이 아니라 작업마다 유동적으로 바뀜. 환경 설정에서 코어·메모리를 지정하면 그 자원으로 데이터를 처리하겠다는 뜻.

요청 값 (총 8코어: 마스터 4 / 워커 2 / 워커 2)실제 동작이유
코어 2 + 메모리 2배마스터에서 1코어, 워커에서 1코어 사용 — 나머지 워커는 놂메모리도 마스터 1 + 워커 1 = 2로 합산
코어 6(메모리 6)마스터 2코어 + 워커 2코어 + 다른 서버 2코어를 끌어와 합 6코어마스터 쪽 E-Core 사용(남는 코어는 다른 서비스용으로 쓰지 않음), 메모리도 각 서버 2씩 = 6

원인

확인결과판단
오타 점검.bashrc·spark-env.sh의 경로를 다시 확인경로 표기는 정상 — 오타 문제가 아님
find /usr/lib -name "java-17-openjdk"워커에서 결과 없음디렉토리 자체가 없음
java -version정상 출력실행 환경(JRE)은 있음
/usr/lib/jvm 목록jre-17 계열 링크만 있음JDK(java-17-openjdk-devel)가 아닌 JRE만 설치된 상태 — 설치 오류가 아니라 설치 범위 차이

java-17-openjdk 디렉토리는 JDK 패키지가 만들고, JRE만 있으면 그 이름의 디렉토리가 생기지 않음 → JAVA_HOME 경로가 비어 있는 것과 같은 상태.

별표의 뜻이름이 java-17로 시작하는 패키지를 모두 설치관련 패키지가 한 번에 깔리는 것이 정상 — 일부만 깔려 있던 상태였다는 뜻
Spark 영향JRE만으로는 Spark 기동 불가spark-class가 JAVA_HOME/bin/java를 직접 실행하기 때문

항목내용주의·이유

선행 지식MySQL의 join·group by를 알아야 이해됨이후 더 다루는 내용 — 여기서는 셔플의 조각 수로만 이해
# [마스터 · /home/sparkuser/movie.py 파일 안 · sparkuser]

셔플 파티션 — spark.sql.shuffle.partitions는 조인·group by·window 함수·distinct처럼 데이터를 재배치할 때 쓸 조각 수. 이 환경은 코어·메모리가 적어 8, 자원이 많으면 크게

에러: numPartitions와 분할 컬럼

항목내용주의·이유
증상RDD에서 "레코드 수 / 파티션 수가 안 맞는다"는 에러 — 81~82번 줄 df read 부분읽기 단계에서 터지므로 코드 아래쪽 집계는 실행되지 않음
원인AI가 만든 JDBC 읽기에 numPartitions·partitionColumn·lowerBound·upperBound가 있는데 분할 기준 컬럼(id)이 테이블에 없음박스오피스 테이블에는 id 컬럼이 없음 — AI가 일반적인 예제를 그대로 넣은 경우
해결위 4개 옵션을 삭제하면 정상 동작우선 작동 여부가 중요 — 병렬 읽기 튜닝은 그 뒤
옵션 규칙numPartitions를 쓰려면 partitionColumn(숫자·날짜 컬럼)·lowerBound·upperBound가 같이 지정돼야 함Spark JDBC 데이터소스 문서 — 하나라도 빠지면 병렬 읽기 구성이 성립하지 않음
JDBC 병렬 읽기 — numPartitions는 partitionColumn·lowerBound·upperBound와 함께 써야 하고, 기준 컬럼이 테이블에 실제로 있어야 함. 없으면 4개 옵션을 지우고 단일 파티션으로 읽기

FROM mzleejh/apink_rocky:9
# -y 자동 승인 / --allowerasing: 의존성 충돌 시 기존 패키지 제거·교체 허용 (Rocky 9의 curl-minimal ↔ curl 충돌 사례)
# java-17-openjdk-devel: Java 17 + 개발 도구 javac / curl·tar: 다운로드·압축 해제 / python3·python3-pip: PySpark·Jupyter용
# 여러 줄은 역슬래시로 연결, && 앞뒤 공백 / dnf clean all: 캐시 정리로 이미지 크기 감소
RUN dnf install -y --allowerasing java-17-openjdk-devel \
 curl tar python3 python3-pip && dnf clean all
# Java 설치 경로 (설치 후 /usr/lib/jvm 아래에서 찾아 확인하는 값)
ENV JAVA_HOME=/usr/lib/jvm/java-17-openjdk
# 받을 배포본 선택값 (버전을 바꿀 때는 이 값만 바꿔 URL 관리)
ENV SPARK_VERSION=3.5.3
ENV HADOOP_VERSION=3
# Spark 설치 경로
ENV SPARK_HOME=/opt/spark
# Spark·Java의 bin을 PATH에 추가 → 어느 경로에서나 실행. ENV 이름=값은 등호 주변을 붙여 씀
ENV PATH=$SPARK_HOME/bin:$JAVA_HOME/bin:$PATH
# 아카이브를 받아(curl -sL) 파이프로 압축 해제 (x 풀기, z gzip, -C 대상 경로) → spark-3.5.3-bin-hadoop3를 /opt/spark로 이동
# ${변수}: 뒤에 다른 글자가 이어질 때 변수 경계 표시 (독립 변수는 $변수)
RUN curl -sL https://archive.apache.org/dist/spark/spark-${SPARK_VERSION}/spark-${SPARK_VERSION}-bin-hadoop${HADOOP_VERSION}.tgz | tar -xz -C /opt/ && mv /opt/spark-${SPARK_VERSION}-bin-hadoop${HADOOP_VERSION} $SPARK_HOME
# 컨테이너 기본 작업 경로
WORKDIR $SPARK_HOME

docker exec -it spark-master /bin/bash                 # 마스터 컨테이너 접속 (컨테이너 안에서는 root)
# [spark-master 컨테이너 · root]
cd /opt/spark/data                                     # 볼륨으로 연결된 디렉터리 — 처음에는 비어 있음
vi test.txt                                            # 파일 하나 생성 후 저장
exit                                                   # 호스트로 복귀
# [호스트 리눅스 · root]
ls -a /home/spark-data                                 # 컨테이너에서 만든 test.txt 확인 (컨테이너 → 호스트)
rm /home/spark-data/test.txt                           # 호스트에서 삭제
docker exec -it spark-master ls -al /opt/spark/data    # 컨테이너 안에서도 사라짐 (호스트 → 컨테이너)

PortBindings 에 11111 블록 추가

# [호스트 리눅스 · /var/lib/docker/containers/<마스터 ID>/hostconfig.json 파일 안 · root]
# 파일 전체가 이름:값 쌍을 중괄호로 감싼 JSON 객체 — PortBindings 안에 포트마다 "포트/tcp" 블록이 들어 있음
# 7077 블록을 쉼표까지 복사해 앞에 하나 더 넣고 포트 값만 11111 로 변경
# 쉼표·따옴표·중괄호 하나만 틀려도 컨테이너가 아예 뜨지 않음
"PortBindings":{"11111/tcp":[{"HostIp":"","HostPort":"11111"}],"7077/tcp":[{"HostIp":"","HostPort":"7077"}],"8080/tcp":[{"HostIp":"","HostPort":"8080"}],"8888/tcp":[{"HostIp":"","HostPort":"8888"}]}
  • 편집 절차
    [호스트 리눅스 · vi] 내용 전체 복사 후 :q!로 저장 없이 나옴 → [윈도우 · 메모장] PortBindings 맨 앞에 11111 블록 추가(원본은 다른 이름으로 백업) → [호스트 리눅스 · vi] 기존 내용 전부 삭제 → i → Shift+Insert → Esc → :wq. 남은 글자가 있으면 JSON 문법 오류로 컨테이너 미기동, vi에서 마우스 오른쪽 클릭 붙여넣기는 원치 않는 위치에 붙어 파일이 깨질 수 있음
  • 원리·백업
    hostconfig.json 구조(Binds·PortBindings)·한 글자 오타 위험: docker.html 8장

셸과 마스터 UI의 관계

상황마스터 UI(8080) Running Applications의미
셸을 띄운 직후앱이 하나 표시됨 (새로고침 필요)대기 상태 — 작업이 떨어지면 그때 워커에서 실행

exit로 셸 종료앱이 사라짐셸이 곧 드라이버 프로세스 — 셸을 나가면 앱도 끝남

현상 — 세 가지 실험

실험결과의미
템플릿 그대로 (globals 체크 + stop)정상 종료, Spark 웹 Completed Applications에 앱 이름이 생김정상 처리 — 자원 반환까지 완료
if 'spark' in globals() 부분을 #으로 주석 처리시작·종료·배열은 출력되나 Spark 웹에 Running Application이 계속 남음종료되지 않은 세션이 코어를 계속 점유, CPU·메모리 할당 유지
그 상태에서 spark.stop()만 달고 실행시작·종료까지만 나오고 이후 아예 안 뜸작동이 안 된 것 — 에러 난 앱이 고스트처럼 떠다니기 때문
정리 방법동작메모
kill (강제 정지)Spark 웹에서 앱을 강제 종료 — 고스트는 이 방법으로만 종료 가능강제로 죽이면 빨간색으로 표시됨 (강제로 죽였다는 뜻)이고, 다시 실행해도 계속 돌고 있음 — 완전히 컷된 뒤에야 정상
해결 순서떠다니는 앱을 모두 컷한 뒤 globals 체크 문구를 살려 실행순식간에 사라지고 정상 처리, 새로고침하면 앱 하나가 정상 생성됨
재실행실행 중이던 앱은 재실행하면 날아감(죽고 정리됨)단 끝에 stop을 안 걸면 무조건 계속 돌아감 (고스트)
차이globals 체크 + stop 문구가 있고 없고의 차이가 매우 큼그래서 템플릿에 주석 처리해 둔 것이며 뜻을 알아야 함

stop은 위·아래 둘 다

위치하는 일빠뜨리면
위 (시작 전)globals 체크로 살아 있는 세션을 모두 종료이전 세션이 남은 채 새 앱이 떠서 코어 부족
아래 (작업 끝)spark.stop()으로 워커 노드 회수대기 상태로 남고, 다시 실행하면 죽었다 재생성되지만 또 살아 있음 → 반복
하나만 걸면동작은 하지만 하나를 깜빡하면 위 문제가 계속됨둘 다 걸어야 안정적 — 그래서 stop은 항상 끝에도 넣고 시작에도 넣음
같은 원리개발자가 DB 커넥션 close를 쓰는 이유와 같음종료하지 않으면 계속 살아서 작동
용어이 종료·정리 습관을 가리키는 말로 "스코프"를 쓰지 않음scope = 이름이 직접 접근 가능한 프로그램 영역을 뜻하는 용어

안전 종료 — try/except

# [spark-master 컨테이너 · JupyterLab 노트북 첫 셀 · root]
# running APP 상태에서 state 또는 delay 상태 강제 정지
# spark 에서 작업시 running이 있는 부분을 모두 안전하게 객체를 확인 후 종료
if 'spark' in globals():      # 커널이 spark를 계속 잡고 있어 런이 계속 걸리는 현상을 막는 문구 (탭 자동완성)
    try:                      # 종료 중 문제가 생길 수 있음 — 작업 중 종료되면 큰일
        spark.stop()
    except:                   # exception 처리
        pass                  # 객체가 없으면 그냥 넘어감
항목내용메모
목적종료하다가 문제가 생길 수 있어 안전장치로 예외처리 사용작업 중인데 종료되면 큰일
흐름try 실행 → except(exception)에서 pass로 넘김에러 메시지를 숨기는 것이 아니라 종료 실패만 넘김
결과globals 체크에 걸리지 않으면(객체 없음) pass, 고스트처럼 살아 있는 세션이 있으면 모두 종료한 번의 실행으로 이전 앱까지 정리
필요성원래는 없어도 되는 문구이나 실습 편의상 필요하고 실무에서도 씀있고 없고가 중요 — 위 실험은 이 부분을 주석 처리한 상태
