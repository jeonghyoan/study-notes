NAT + 호스트 전용 → SSH 22

NAT(enp0s3, 10.0.2.15)는 외부 접속 불가 → 호스트 전용 어댑터(enp0s8) 추가 → PuTTY(포트 22, SSH)로 일반 사용자 로그인 후 su. root 직접 로그인은 PermitRootLogin이 결정하며 수정 후 systemctl restart sshd.service 필수.

권한 r4·w2·x1 · chmod · 디렉터리 권한 · SGID·umask

3묶음(오너/그룹/게스트)을 chmod 숫자로 변경, 상위 디렉터리가 막히면 하위 권한은 무의미. 생성·삭제는 파일이 든 디렉터리 권한이 결정(root 소유 파일도 apink 홈 안이면 apink가 삭제). cp = 복사한 사용자 소유 / mv = 원 소유자 유지 + 대상 w 필요. ls -al 맨 앞 d/-/l, 이름 앞 두 열 = 소유자·그룹. chgrp·chown :그룹으로 그룹 변경, -R로 하위 전체. SGID는 그룹 자리 s(x 없으면 S), umask는 기본 모드(파일 666·디렉터리 777)에서 비트를 끄는 값 — 022면 644·755, 006이면 660·771. 백업·복구는 cp -a — cp -r은 소유자·권한·수정 시간이 복사한 사람 기준으로 바뀜.

useradd → passwd · skill · userdel -r · tar·gpg · ssh-copy-id · rsync·lsyncd

useradd만으로는 비번이 없어 로그인 불가 → passwd 아이디. 침입 대응은 who → passwd 먼저 → skill -KILL -t pts/번호. userdel = ID·비번만, -r = 디렉터리까지(복구 불가). tar는 c/x/v/f, -f 뒤 파일명, gz는 z·bz2는 j, 해제는 xf 하나. 암호는 gpg -c / gpg -d. 서버 점검은 free -h(Mem used/free·Swap, 0에 가까우면 로드 100%), 리다이렉션 >(덮어씀)·>>(이어씀), OS·커널은 uname -r·cat /etc/os-release. 그룹은 groupadd로 만들고 usermod -aG로 넣은 뒤, 공용 디렉터리에 chgrp+chmod 770를 적용. 서버 간 자동화는 ssh-keygen -b 2048(1024는 invalid key length) → ssh-copy-id → rsync -avz -e "ssh -p 10022 -i 키" 순서. rsync는 삭제 미전파로 백업, lsyncd는 삭제까지 반영해 미러. 점검은 /var/log(secure·audit·boot.log·lastlog), 파일 찾기는 find 경로 -name·-mtime(부호 구분)·-size +100M -exec ls -lh {} \;, 패키지는 dnf install -y로 한 파일에 모아 설치.

255.255.255.0앞 3자리마지막 자리

  • 기본 게이트웨이는 모두 같아야 함

항목내용주의·이유
키 생성PuTTYgen(PuTTY Key Generator)으로 키(ppk) 생성 (영상에는 없음), 키 유형 RSA 2048 bitsDSA 등도 있는 암호화 방식
클라우드AWS EC2는 키 페어로 ~/.ssh/authorized_keys에 공개키를 등록해 SSH 접속, Session Manager 같은 대안으로도 접속 가능"무조건 키로만 접속"은 아님, GCP 방식은 확인하지 못함
ppk 보관ppk 파일은 유실 금지 — 사수가 준 키를 잃어버리면 크게 혼남, 개발자는 USB에 담아 다니며 사용패스워드를 모르므로 키가 유일한 수단
누가 설정하나일반 사용자(apink) 기준으로 설정, root는 키를 만들지 않고 직접 접속되지 않게 함OpenSSH 기본값 PermitRootLogin prohibit-password는 root의 비밀번호 로그인만 막고 공개키 로그인은 허용하므로, root 키 미사용은 서버 설정 방침
다른 사용자keygen으로 키를 만들고 디렉토리·파일 설정을 순서대로 똑같이 반복사용자마다 키를 따로

줄 수:set number로 봤을 때 1번 줄 하나만 있어야 함맨 위 공백 줄이 있으면 키를 못 찾음

형식 cp 원본 사본

# [호스트 리눅스 · apink · 프롬프트 $]
# 파일 복사 — 원본 유지 + 사본 생성. 가동 중인 환경 설정을 잘못 건드렸을 때 복구용으로 실무에서 많이 씀
vi 123.data   # 원본 파일 생성
cp 123.data 222.data   # 같은 디렉터리에 사본 생성
ls -l   # 복제 확인
cp 123.data test/backup.data   # test 디렉터리 안에 backup.data 이름으로 복사
cd test   # 복사 확인용 이동
ls   # backup.data 존재 확인
cat backup.data   # 내용 빠르게 확인
# 디렉터리 복사 — -r(recursive) 필수
cp web backup   # -r 없이 디렉터리 복사 → 에러: cp: -r not specified; omitting directory 'web' (옵션이 빠진 것)
cp -r web backup/   # 디렉터리를 안의 파일까지 통째로 복사 (원래 web 도 그대로)
cd backup   # 복사 확인: backup 안에 web 존재
ls -al   # backup 안 확인
cd web   # web 안에서 복제 확인
ls -al   # 복사된 파일 확인
# 특정 파일만 복사 — 준비: web 에 test.data, web.xml, kkk.xml 생성(vi, 내용은 아무거나) → ls -l 하면 xml 2개, data 1개
cp *.xml backup/   # 홈(/home/apink)에서 실행 → 에러: cannot stat '*.xml' (현재 경로에 xml 파일이 없음 → 현재 경로를 봐야 함)
cp web/*.xml backup/   # web 안의 확장자가 xml 인 파일만 복사 (* 와일드카드)
cd backup   # 복사 확인
ls -l   # xml 파일만 복사된 것 확인

cp -r — 디렉터리 복사는 -r 필수(없으면 에러), 확장자 일괄 복사는 cp 디렉터리/*.xml 대상/. 원본을 유지해 두어야 설정을 잘못 건드렸을 때 복구 가능

cp -r과 cp -a — 소유자·권한·수정 시간 (-a가 백업·복구용)

백업·복구에서는 원본의 소유자·그룹·권한·수정 시간까지 그대로 돌려놓아야 함. cp -r은 하위까지 복사하지만 이 네 가지가 명령을 실행한 사용자 기준으로 바뀌고, cp -a는 모두 원본 그대로 유지.

옵션소유자·그룹·권한·수정 시간결과
cp -r 원본 대상모두 변경 (실행한 사용자 기준)root로 복사하면 소유자가 root, 퍼미션도 root 기준, 날짜는 오늘
cp -a 원본 대상모두 그대로 유지원본을 750으로 바꿔 둔 상태면 복사본도 750, 원본 날짜가 10월 20일이면 복사본도 20일
# [호스트 리눅스 · blue2 · 프롬프트 $ · /home/blue2]
# 백업 디렉토리는 받는 사용자로 만든다 — root로 만들면 root 소유가 되어 일반 사용자가 못 씀
mkdir back
exit
# [호스트 리눅스 · root · 프롬프트 # · /home/blue2]
# -r 없이 디렉토리를 복사하면 아래 에러 — 디렉토리는 재귀 옵션 필수
cp /home/aidata/html /home/blue2/back
cp -r /home/aidata/html /home/blue2/back   # 소유자·권한·시간은 복사한 사람 기준으로 바뀜
ls -l back                                 # back 안에 html 디렉토리가 한 겹 생기고 소유자가 root
rm -drf back/html                          # 실습 되돌리기
cp -a /home/aidata/html /home/blue2/back   # 속성 유지 — 소유자 aidata, 권한 750, 원본 날짜 그대로
ls -l back                                 # 소유자·그룹·권한·날짜를 원본과 비교
항목cp -r 결과이유·주의
소유자root로 바뀜 (원래 aidata)복구하면 원래 사용자 aidata가 자기 파일을 수정·다루지 못함 — 이 때문에 에러가 난 사례가 많음
퍼미션복사한 사람(root) 기준으로 바뀜원본에 사용자가 세팅해 둔 권한이 무너져 관리자가 다시 맞춰야 함 — 올바른 복구 방식이 아님
수정 시간복사한 날(오늘) 날짜로 찍힘개발자가 오늘 파일을 고쳤는지 날짜로 따지는 일이 실제로 있음 — 날짜가 바뀌면 이력이 흐트러짐
디렉토리 구조대상 안에 html 디렉토리가 한 겹 생김대상 디렉토리 안에 다시 디렉토리가 들어간 형태
끝 슬래시cp -a html/ back도 html 자체를 복사GNU cp는 끝 슬래시만으로 내용만 복사하지 않음 — 내용만은 html/* 또는 html/. 사용. "끝 슬래시 = 내용만"은 rsync 규칙 (14장)
정식 방식cp -a셸로 백업·복구 스크립트를 만들 때 -a가 가장 확실 — 백업 스크립트: shell.html 6장
백업·복구는 cp -a — cp -r은 소유자·그룹·권한·수정 시간이 복사한 사람 기준으로 바뀌어 되돌린 뒤 원래 사용자가 파일을 고치지 못함

rm · rmdir — 삭제

  • rm = remove. 파일 삭제용 / 휴지통이 없음: 지우는 순간 복구 불가 → 한두 번 더 검토한 뒤 쳐야 하는 유일한 명령
  • 삭제 후 전문 도구·시간이 있으면 일부 복구될 수 있으나 보장되지 않음. root 권한이 복구 수단은 아니며 백업이 최선
# [호스트 리눅스 · apink · 프롬프트 $]
rm 222.data   # 파일 삭제 (remove)
ls -a   # 사라진 것 확인
rm test   # 디렉터리에는 사용 불가 → 에러: cannot remove 'test'
rmdir test   # 빈 디렉터리만 삭제. 파일이 들어 있으면 에러: failed to remove 'test'
rm -drf test   # 하위 디렉터리·파일까지 전부 삭제 (파일명·디렉터리명 가리지 않음)
옵션의미주의
-rrecursive(재귀) — 안에 있는 하위 디렉터리·파일까지 삭제-r만으로도 중첩 삭제 가능
-d빈 디렉터리 삭제-r과 함께 쓰면 따로 필요 없음
-fforce — 없는 파일 무시, 확인 질문 안 함
  • 결론: rm -drf 이름으로 외우기 (옵션 의미는 자격증 대비용으로 공부)
rm — 휴지통 없음, 디렉터리는 rm만으로 못 지움, rmdir은 빈 디렉터리만, rm -drf 옵션(-r 재귀 · -d 빈 디렉터리 · -f 확인 생략) 정리

심볼릭 링크 (ln -s)

링크는 원본 경로를 가리키는 바로가기 — 링크 안에서 고치면 원본이 바뀜

링크 이름

/root/httpd · ln -s로 생성

원본 경로

/etc/httpd/conf/ (디렉토리·파일 모두)

httpd.conf

링크 안에서 수정 = 원본 수정 100%

rm은 링크만 지우고 원본은 그대로 — 원본이 남았는지는 경로를 Tab으로 자동완성해 확인

항목내용주의·이유
개념윈도우 바탕화면의 바로가기와 같음, S-Link라고도 부름링크를 지워도 원본 파일은 지워지지 않음
형식ln -s 원본경로 만들링크이름 — 원본은 디렉토리·파일 모두 가능s = 심볼릭 링크를 걸겠다는 뜻 (ln = link)
ls -l 표시맨 앞이 l이고 이름 뒤 화살표(->)로 원본 표시
lrwxrwxrwx 1 root root … httpd -> /etc/httpd/conf/		맨 앞 l이 링크 판별 기준 (디렉토리 d, 파일 -)
장점/etc/httpd/conf까지 매번 이동하지 않아도 됨. /var/lib/... 같은 긴 경로도 링크 하나로 해결실무에서 정말 많이 씀 — 사수가 "심볼릭 링크 걸어 놨으니 그 디렉토리 가서 환경설정"이라고 안내
# [호스트 리눅스 · root · 프롬프트 #]
cd /root                        # 링크를 만들 위치 (pwd 로 /root 확인)
ln -s /etc/httpd/conf/ httpd    # /etc/httpd/conf/ 를 가리키는 httpd 링크 생성 (Apache 설정 디렉토리)
ls -l                           # lrwxrwxrwx … httpd -> /etc/httpd/conf/ 확인
cd httpd                        # 링크 안으로 이동 (원본 디렉토리로 들어간 것과 같은 상태)
pwd                             # /root/httpd — 링크 경로로 표시
ls -a                           # 원본 디렉토리 내용 (httpd.conf, conf.d 등)
vi httpd.conf                   # 수정 = /etc/httpd/conf/httpd.conf 수정과 100% 동일
ln -s /etc/nginx/ nginx         # nginx 설정 디렉토리 링크
ls -al                          # nginx -> /etc/nginx/ 확인
rm nginx                        # 링크만 삭제 → remove symbolic link 'nginx'? 질문에 y. 원본 /etc/nginx 는 그대로
심볼릭 링크 — ln -s 원본 링크이름, ls -l 맨 앞 l과 ->로 판별. 링크 안에서 고치면 원본이 바뀌고 rm은 링크만 지움

chmod — 권한 변경

형식 chmod 숫자 파일/디렉터리 (change mode)

# [호스트 리눅스 · apink · 프롬프트 $]
chmod 777 123.data   # owner·group·guest 전부 읽기·쓰기·실행 → ls -al 에서 파일명이 녹색으로 바뀜 (실행 권한이 붙으면 실행 파일로 인식, 쉘 스크립트 같은 실행 파일은 녹색)
chmod 700 123.data   # 나만 읽고 쓰고 실행 (그룹·게스트는 손을 못 댐) → 민감 파일 보호용
  • 700은 파일을 숨기는 것이 아니라 접근을 막는 것 — 목록(ls -al)에는 그대로 보임. 숨김 파일은 이름이 .으로 시작
  • 그룹을 만들어 그룹 단위로 접근을 막는 것도 가능 (그룹 생성·가입: 이 파일 8장)

소유자·그룹 변경 (chgrp·chown·-R)

명령기능주의·이유
chgrp 그룹 대상대상의 그룹 변경 (change group)그룹만 바꿀 때 가장 짧음
chown :그룹 대상그룹만 변경 (소유자는 그대로)앞을 비우고 : 뒤에 그룹명
chown 소유자:그룹 대상소유자·그룹 함께 변경한 번에 둘 다
chown 그룹명 대상(오류) 그룹명을 소유자 자리에 넣은 경우chown은 소유자(사용자) 변경용 → mega_server를 사용자로 해석해 실패. 그룹은 chgrp 또는 :그룹
# [호스트 리눅스 · root · 프롬프트 #]
chgrp mega_server infra         # 디렉토리 그룹을 mega_server 로 변경 — 그룹을 만든 뒤 첫 단계
chown :mega_server httpd        # 그룹만 변경 (소유자 blue1 은 그대로)
chown blue1:mega_server httpd   # 소유자·그룹 함께 변경
chown mega_server infra         # (오류) 그룹명을 소유자 자리에 넣음 — 그룹은 바뀌지 않음

-R — 하위 전체 한 번에 변경

디렉토리 안에 파일이 여러 개면 하나씩 바꿀 수 없음 → -R(대문자)로 하위 디렉토리·파일 전부

# [호스트 리눅스 · blue1 · 프롬프트 $ · /home/infra/httpd 안]
echo test1 > test1.txt   # 파일 4개 생성 — 모두 소유자 blue1, 그룹 blue1
echo test2 > test2.txt
echo test3 > test3.txt
echo test4 > test4.txt
ls -l                     # 4개 모두 blue1 blue1 확인
# [호스트 리눅스 · root · 프롬프트 #]
cd /home/infra             # 하위 디렉토리 기준으로 작업
chgrp -r mega_server httpd/   # (오류) 옵션은 대문자 R — 소문자 r 은 잘못된 옵션
chgrp -R mega_server httpd/   # 하위 디렉토리·파일 전부 그룹 변경
chmod -R 770 httpd/           # 하위 전부 퍼미션 변경 (그룹에 rwx)
chown -R blue2 디렉토리/       # 하위 전부 소유자 변경
-R 대소문자 — 옵션은 대문자 R(소문자 r은 오류). 재귀 대상은 디렉토리라 끝에 /를 붙여 구분

SGID를 디렉토리에 걸면 그 아래 새 파일이 디렉토리 그룹을 물려받음

공용 디렉토리

그룹 = mega_server

파일마다 chgrp 불필요

파일을 만들면 기본 권한은 644 — 만들 때마다 chgrp·chmod 하는 번거로움을 SGID(그룹 상속)와 umask(생성 권한)로 줄임

명령결과 표시주의·이유
chmod g+s 222.txt그룹 실행 자리(x)가 s로 바뀜기호 방식 — g는 그룹, +s는 SGID 추가
chmod 2670 222.txt-rw-rws---3자리 앞에 2를 붙인 4자리(2000 + 권한) — 숫자 방식 권장
chmod 644 222.txtrw-r--r--로 s가 풀림일반 권한으로 덮으면 SGID가 사라짐
표시의미실제 동작
소문자 sSGID 켜짐 + 그룹 실행(x) 켜짐그룹 권한으로 실행·상속이 모두 살아 있는 상태
대문자 SSGID 켜짐 + 그룹 실행(x) 꺼짐표시일 뿐 읽기 전용 기능이 아님 — 같은 그룹이 수정 못 하는 이유는 그룹에 w가 없어서 (GNU coreutils 매뉴얼 "What information is listed")
# [호스트 리눅스 · blue1 · 프롬프트 $ · /home/infra 안]
vi 222.txt                 # 실습 파일 생성 — 기본 권한 644 (rw-r--r--)
chmod g+s 222.txt          # 그룹 실행 자리에 s 설정 (SGID)
ls -l                      # -rw-r-Sr--  ← 그룹 x 가 없어 대문자 S 로 표시
chgrp mega_server 222.txt  # 그룹을 mega_server 로 변경 (S 표시는 그대로)
# [호스트 리눅스 · blue2 · 프롬프트 $]
vi 222.txt                 # 여전히 수정 불가 → 그룹에 w 가 없어서 (S 때문에 읽기 전용이 된 것이 아님)
# [호스트 리눅스 · blue1 · 프롬프트 $]
chmod 644 222.txt          # 일반 권한으로 덮음 → s 가 풀려 rw-r--r--
chmod 2670 222.txt         # 앞 2 = SGID + 그룹에 w 포함 → -rw-rws---
# [호스트 리눅스 · blue2 · 프롬프트 $]
vi 222.txt                 # 이제 수정 가능 — 그룹에 w 가 들어갔기 때문
적용 대상동작메모
디렉토리그 안에 새로 만든 파일이 디렉토리의 그룹을 물려받음 (파일마다 chgrp 불필요)주로 이쪽에 사용. 공용 디렉토리에 걸어 두고 하위 파일이 상속되게 하는 방식 (GNU coreutils 매뉴얼 "Directory Setuid and Setgid")
실행 파일실행할 때 파일 그룹 권한으로 동작파일에는 잘 안 걸지만 그룹 권한 자리에 s/S가 보이면 SGID로 읽을 줄 알아야 함
SGID — 그룹 권한 자리의 s(대문자 S)가 SGID 표시. S는 x가 꺼져 있다는 뜻일 뿐이고, 같은 그룹이 수정 못 하는 원인은 그룹 w가 없어서. 기호 방식이 헷갈리면 숫자 앞에 2000을 붙이는 방식으로

umask — 생성 시 기본 권한

항목내용주의·이유
정의파일·디렉토리를 만들 때 자동으로 적용되는 퍼미션을 정하는 값매번 chmod 하지 않아도 되게 하는 설정
확인umask → 기본 0022 (root가 만든 모든 사용자의 기본값)4자리로 보이지만 실제로 쓰는 것은 뒤 3자리, 맨 앞자리는 건드리지 말 것
적용 범위사용자마다 따로 — umask 006을 실행하면 그 사용자만 바뀜다른 사용자의 umask는 그대로
계산빼기가 아니라 해당 비트를 끄는 것(기본모드 & ~umask)기본 모드 = 디렉토리 777, 파일 666
umask디렉토리 (777 기준)파일 (666 기준)
022777 − 022 → 755666 − 022 → 644
006777 − 006 → 771666 − 006 → 660
# [호스트 리눅스 · blue1 · 프롬프트 $]
umask              # 기본값 0022 확인
umask 006          # 이 사용자만 006 으로 변경 (그룹에 읽기·쓰기, 게스트는 실행만)
cd /home/infra     # 공용 디렉토리로 이동
mkdir httpd        # umask 006 이 적용된 디렉토리 생성
ls -al             # drwxrwx--x blue1 blue1 httpd  ← 만들자마자 771, chmod 불필요
# [호스트 리눅스 · blue2 · 프롬프트 $]
umask              # 0022 기본값 그대로 — 사용자별 설정이라 blue1 의 변경이 영향 없음
umask 006          # blue2 도 같은 방식으로 변경
cd httpd/          # 게스트 권한이 --x 라 디렉토리 통과는 됨
ls -al             # ls: cannot open directory (허가 거부) — 게스트에 r 이 없어 목록을 못 읽음
# [호스트 리눅스 · root · 프롬프트 #]
chgrp mega_server httpd   # httpd 그룹을 공용 그룹으로 바꿔야 blue2 가 그룹 권한을 받음
🔍 직접 확인 · 19강 · 시각 미상(필기 기록)

필기에는 blue2가 umask 006을 실행한 뒤 umask 결과가 0066으로 적혀 있음 — 006을 넣었으면 0006으로 보여야 하므로 umask 066 입력이었는지 표기 오류인지 영상에서 확인 필요

umask — 매번 chmod 하는 번거로움을 없애는 생성 기본 권한. 기본 모드는 파일 666·디렉토리 777이고 umask는 비트를 끄는 값이라 022면 644·755, 006이면 660·771. 사용자별 설정이고 뒤 3자리만 사용

아무에게나 주면 안 됨잘못 주면 네트워크·데몬 정지 등 root와 거의 같은 일을 다 할 수 있음서버를 내리거나 설정을 바꾸는 권한까지 포함
실행 결과sudo -s에 루트 비밀번호가 아니라 megazone 자기 비밀번호를 입력하면 루트 프롬프트(whoami → root)대상 사용자 비밀번호를 요구하지 않음
자격 증명 캐시기본 sudoers 정책은 터미널별로 5분만 기억하고 sudo -k로 무효화항상 무암호로 들어가는 것은 NOPASSWD 설정일 때뿐 — 5분이 지나면 다시 비밀번호 필요
할 수 있는 일지금까지 배운 root 명령(ntsysv 등)과 root 비밀번호 변경까지 가능비밀번호를 바꾸면 원래 root도 되돌리기 어려움
세컨드 루트root에 준하는 권한을 가진 보조 관리자 계정(가짜 루트)비밀번호를 뺏기면 root를 뺏긴 것과 비슷 — 서버 셧다운 등 사고로 이어짐
실무급한 일이 있을 때 진짜 root 비밀번호 대신 별도 아이디에 root 권한을 주기도 함그 아이디는 절대 뺏기면 안 되므로 암호·접속 이력을 따로 관리
sudoers 파일/etc/sudoers — root 권한 항목이 있는 권한 환경설정 파일손대지 말 것 — 잘못 고치면 root 로그인 자체가 막힘
su는 substitute user — root에서 su - 사용자는 비밀번호 없이 전환되므로 root 탈취가 전 계정 탈취. wheel에 넣은 계정은 세컨드 루트이며 sudo -s는 자기 비밀번호로 들어감

# [호스트 리눅스 · root · 프롬프트 #]
groupadd mega_server   # 협업용 그룹 생성 (사용자는 생기지 않음)
cat /etc/group         # 그룹 목록 확인
# 출력 형식: 그룹명:x:GID:소속사용자
# aidata:x:1004: / blue1:x:1005: / blue2:x:1006: / mega_server:x:1007:
groupdel test_group    # 연습용 그룹 삭제
칸내용주의·이유
1번째그룹명
2번째x — 그룹 비밀번호 자리 (지금은 쓰지 않음)
3번째GID(그룹 ID) — 사용자를 추가할 때마다 리눅스가 다음 번호를 자동 부여고유키. 강제로 바꾸면 접속 불가 등 문제가 생기고 해커들이 건드리는 부분이라 보안 파트에서 다시 다룸
4번째그룹에 속한 사용자 목록 (쉼표 구분)여기가 비어 있으면 아직 아무도 안 넣은 상태

사용자를 그룹에 넣기 — usermod -aG

# [호스트 리눅스 · root · 프롬프트 #]
usermod -aG mega_server blue1   # blue1 을 mega_server 그룹에 추가 (a = append, G = 그룹). root 가 실행
# [호스트 리눅스 · blue1 · 프롬프트 $]
groups                          # 현재 사용자가 속한 그룹 확인
# 출력: blue1 mega_server   ← 보조 그룹으로 mega_server 가 붙음
usermod -aG — a가 없으면 기존 보조 그룹이 전부 지워지고 이번 그룹만 남음(append가 아니라 덮어쓰기). 그룹 추가는 반드시 -aG

공용 디렉토리 만들기 — chgrp + chmod 770

단계명령주의·이유
누가 만드나root가 만드는 것이 맞음일반 사용자도 만들 수는 있지만 그룹은 root가 만들기 때문
생성 직후mkdir infra → 소유자 root, 그룹 rootdrwxr-xr-x root root
소유자 변경 시도chown mega_server infra → (오류)chown은 소유자 변경용인데 mega_server는 사용자가 아니라 그룹
그룹 지정chgrp mega_server infrachgrp = change group, chown = change owner
퍼미션chmod 770 infra → 소유자·그룹 rwx, 게스트 0아무 사용자나 접근하지 못하게
# [호스트 리눅스 · root · 프롬프트 #]
cd /home                  # 공용 디렉토리를 만들 위치
mkdir infra               # 만든 직후 소유자 root, 그룹 root
ls -l                     # drwxr-xr-x root root infra — 그룹은 읽기·실행만, 쓰기 없음
chown mega_server infra   # (오류) 그룹명을 소유자 자리에 넣음 — 소유자는 바뀌지 않음
chgrp mega_server infra   # 디렉토리 그룹을 mega_server 로 변경
chmod 770 infra           # 소유자 rwx · 그룹 rwx · 게스트 0
ls -ld infra              # drwxrwx--- root mega_server 확인

접근 테스트 — 그룹에 넣은 사용자만 들어감

# [호스트 리눅스 · root · 프롬프트 #]
su aidata                 # 그룹에 없는 사용자로 전환
# [호스트 리눅스 · aidata · 프롬프트 $]
cd /home/infra            # 허가 거부 (Permission denied) — mega_server 그룹이 아님
exit                      # root 로 복귀
# [호스트 리눅스 · root · 프롬프트 #]
su blue1                  # 그룹에 넣은 사용자로 전환
# [호스트 리눅스 · blue1 · 프롬프트 $]
cd /home/infra            # 들어가짐 — 이것이 그룹으로 여는 방식
pwd                       # /home/infra 확인

파일 공유가 막히는 이유 — 그룹 + 그룹 퍼미션

# [호스트 리눅스 · blue1 · 프롬프트 $ · /home/infra 안]
echo "test file" > 123.txt   # 파일 생성
ls -l                        # 소유자 blue1, 그룹도 blue1 — 디렉토리 그룹을 물려받지 않음
# [호스트 리눅스 · blue2 · 프롬프트 $]
vi 123.txt                   # readonly 표시 — 수정 불가 (644라 그룹 권한이 r 뿐)
# [호스트 리눅스 · blue1 · 프롬프트 $]
chgrp mega_server 123.txt    # 그룹을 공용 그룹으로 변경
# [호스트 리눅스 · blue2 · 프롬프트 $]
vi 123.txt                   # 여전히 readonly — rw-r--r-- 라 그룹 권한이 r 뿐
chmod 770 123.txt            # (실패) 소유자가 blue1 이라 blue2 는 권한 변경 불가
# [호스트 리눅스 · blue1 · 프롬프트 $]
chmod 770 123.txt            # 소유자 7 · 그룹 7 · 게스트 0 → rwxrwx---
# [호스트 리눅스 · blue2 · 프롬프트 $]
vi 123.txt                   # 이제 수정 가능 — 그룹에 w 가 생겼기 때문
그룹 협업의 핵심 — 같은 그룹이라고 무조건 공유되지 않음. 그룹 + 그룹 퍼미션을 둘 다 맞춰야 수정 가능. 파일을 만들면 소유자·그룹이 만든 사람으로 잡히므로 디렉토리에 SGID를 걸어 그룹 상속(7장)

사용자의 기본 그룹 바꾸기 (/etc/group · usermod -g)

항목내용주의·이유
목표blue1이 파일을 만들면 그룹이 자동으로 mega_server로 잡히게 함파일마다 chgrp 하는 번거로움 제거
권한root만 가능 (일반 사용자는 손도 못 댐)오타가 나면 오류가 많이 나는 파일이라 매우 주의
표준 방법usermod -g mega_server blue1 — 기본(로그인) 그룹 변경홈 디렉토리 안 파일의 그룹도 함께 바뀜 (man 8 usermod)
파일 직접 수정vi /etc/group → Shift + G로 맨 아래 → blue1:x:1005: 줄에서 i → 그룹명을 mega_server로 → Esc → :wq → 같은 이름이 GID 1005·1007 두 줄로 중복이름만 바꾼 것이라 그룹이 둘로 갈라져 이후 groupadd·usermod·권한 판정이 꼬임 → usermod -g 사용
부작용/home/blue1 홈 디렉토리 그룹도 mega_server로 표시됨홈 디렉토리는 그룹 권한이 0(drwx------)이라 그룹에 포함돼도 의미 없음 → 크게 관계없음
# [호스트 리눅스 · root · 프롬프트 #]
usermod -g mega_server blue1   # 기본 그룹 변경 — 새로 만드는 파일의 그룹이 mega_server 로 잡힘
# [호스트 리눅스 · blue1 · 프롬프트 $]
cd /home/infra                 # 공용 디렉토리로 이동

강제 접속 해제 : skill

항목내용
상황관제에서 "hong이 접속했다"고 전화 → hong 본인은 "접속 안 했다" → 계정을 뺏긴 것(해킹) → root가 그 사용자를 강제 접속 해제("튕겨낸다")
핵심 옵션-t = terminal : 해당 터미널을 강제로 죽이라는 뜻
-t 없이 쓰면에러는 안 나지만 튕겨나지 않음 → 선택 옵션(t 터미널, u 사용자 등) 없이 쓰면 대상 해석이 모호해 의도대로 안 될 수 있음 (배포판 차이가 아님)
참고man 페이지는 skill 자체를 obsolete로 보고 pkill·killall 사용을 권장 (man7.org skill(1))
# [호스트 리눅스 · root]
skill -KILL hong       # 사용자만 지정 → 에러 없음, 하지만 안 튕겨남 (hong 창에서 ls -al 계속 됨)
skill -KILL pts/3      # 터미널만 지정 → 역시 안 튕겨남
skill -KILL -t pts/3   # -t(terminal)로 대상 명시 → pts/3 강제 종료 (hong 창 닫힘)
who                    # hong이 목록에서 사라졌는지 확인
skill 강제 해제 — skill -KILL -t pts/번호 (t = terminal). 사용자·터미널만 쓴 형식은 에러 없이 안 튕겨남
passwd 먼저, 튕겨내기는 나중 — 비번을 안 바꾸고 튕겨내면 같은 비번으로 즉시 재접속됨

항목내용

# 삭제 전: drwx------. 3 hong hong 78 ... hong
# 삭제 후: drwx------. 3 1001 1001 78 ... hong   ← 소유자·그룹이 숫자(UID·GID 1001)로 바뀜

Redirection — echo 출력을 파일로

# [호스트 리눅스 · root]
echo testing > 123.txt         # 화면에 안 찍히고 파일에 저장 (파일 없으면 생성)
ls -l                          # 파일이 생겼는지 확인
cat 123.txt                    # 내용 확인 → testing
echo "홍 테스트" >> 222.txt    # 없던 파일이면 생성, 있으면 이전 내용 유지한 채 뒤에 추가
cat 222.txt                    # 내용 확인 → 홍 테스트
기호영문 호칭동작
>overwrite redirection파일이 없으면 생성하며 내용을 쓰고, 있으면 기존 내용을 덮어씀 (앞 내용 사라짐)
>>append redirection기존 내용 뒤에 이어 씀 (추가)
<반대 방향파일 내용을 명령의 입력으로 넣는 방향 — 지금 범위 아님
항목내용주의·이유
echo의 역할echo = 출력(찍기) 명령. 뒤의 >가 그 출력의 방향을 화면에서 파일로 바꿈어려운 개념이 아니라 방향을 바꾸는 기호의 이름이 redirection
덮어쓰기 결과같은 파일에 >로 다른 문구(예 : "리눅스 서버")를 다시 쓰면 기존 내용이 지워지고 새 내용만 남음기록을 남기려면 >>
실무 호칭"overwrite redirection으로 적용", "append redirection으로 해줘"처럼 영문 호칭으로 구분해 지시한국어로만 말하면 어느 쪽인지 되묻게 됨

디스크 파티션 구조와 용량 배분

df -h의 출력은 파일시스템 목록이고, 그 이면에 파티션을 어떻게 나눴는지가 있음. 같은 총용량이라도 나누는 방식에 따라 컨테이너·DB를 몇 개나 올릴 수 있는지가 달라짐.

# [호스트 리눅스 · root]
df -h                                     # 파일시스템별 용량·사용률 (GB 단위가 핵심)
# 출력 예: /dev/mapper/rl-root on / , /dev/mapper/rl-usr on /usr , /boot , /dev/shm …
# /dev/mapper/이름 = LVM 논리 볼륨 — 디스크 여러 개를 묶어 필요할 때 늘릴 수 있는 구조
vgextend rl /dev/sdb                       # LVM: 새 디스크(물리 볼륨)를 볼륨 그룹 rl 에 추가 — 디스크를 붙여 용량 증설
lvextend -l +100%FREE /dev/mapper/rl-root  # 표준 예시: 남은 공간 전부를 논리 볼륨에 할당
xfs_growfs /                               # 표준 예시: XFS 파일시스템에 늘어난 크기 반영 (Rocky 기본 파일시스템)
구분내용주의·이유
물리 파티션/home 같은 디렉터리를 별도 디스크로 떼어 용량을 따로 잡는 방식한쪽이 차도 다른 쪽은 영향 없음 — 대신 한 곳이 남아도 다른 곳으로 자동으로 가지 않음
가상 파티션 (자동 파티션)용량을 한 덩어리로 잡고 홈 디렉터리 등을 공용으로 쓰는 방식설치할 때 알아서 나누므로 빠르지만, 필요한 곳에 필요한 만큼만 주지 못함
LVM디스크를 볼륨 그룹으로 묶어 논리 볼륨을 만들고, 필요할 때 vgextend로 디스크를 추가해 늘림df의 /dev/mapper/rl-root가 LVM — /usr이 부족하면 마운트·확장으로 증설 가능
LVM의 함정LVM으로만 잡으면 필요 없는 곳까지 용량을 미리 할당해 낭비가 생김할당은 총량을 나눠 갖는 것 — 남는 공간을 한 곳에 몰아 두는 편이 유연함
항목이 서버 현황실무 원칙
/home약 24~25GB 할당, 실사용 205MB (1% 미만)홈에서 대용량 작업을 하지 않으면 2GB 정도로 충분 — 나머지는 낭비

rpm -qa | grep git        # git이 들어간 패키지 전체 — 결과가 너무 많아 한눈에 안 보임

rpm·dnf·yum의 역할

도구역할주의·이유
rpm개별 패키지를 설치·조회·삭제하는 패키지 관리 도구의존성은 확인만 하고 자동으로 받아 설치하지는 않음
dnf·yum저장소에서 필요한 패키지를 자동으로 받아 설치 (의존성 해결)레드햇 계열의 표준 설치 명령 — 그래서 dnf로 설치한 것도 rpm으로 조회·삭제
패키지 형식dnf·yum으로 설치한 패키지는 모두 RPM 패키지 형식RPM은 Red Hat 계열의 패키지 형식·관리자 이름
소스 설치./configure로 직접 빌드하는 방식은 삭제 방법이 따로 있음이 파일의 실습은 모두 rpm 방식
데비안 계열데비안·우분투는 apt로 설치하고 확인 명령이 다름 (dpkg 계열)리눅스는 레드햇 계열 하나를 먼저 마스터하는 편이 빠름

이름 범위rpm -e는 패키지 이름만으로 삭제 가능하고 버전·릴리스·아키텍처는 선택같은 이름의 여러 버전이 있을 때만 구분이 필요

정리 습관실습이 끝나면 같은 방식으로 찾아서 삭제쓸데없는 패키지가 남으면 용량·보안 부담

서버 간 SSH 키 만들기 (ssh-keygen)

항목내용이유
목적마스터가 워커 sparkuser로 접속할 때 패스워드를 묻지 않게rsync·lsyncd가 사람 없이 반복 실행되려면 무인 인증이 전제
방식키 한 쌍 생성 — 개인 키 id_rsa는 마스터에만, 공개 키 id_rsa.pub는 워커 authorized_keys로공개 키는 나눠 줘도 되고, 개인 키는 절대 넘기지 않음
기존 키어제 만든 authorized_keys는 윈도우 PuTTY(ppk)가 접속할 때 쓰는 자리새로 만드는 id_rsa는 서버가 서버로 접속할 때 쓰는 키 — 용도가 다름
키 주인root가 아니라 aidata로 만듦rsync를 aidata로 실행하므로 /home/aidata/.ssh/id_rsa를 봐야 함
# [마스터 · aidata · /home/aidata]
# RSA 1024비트로 먼저 생성 — 아래에서 2048 미만 거부를 확인하고 다시 만듦
ssh-keygen -t rsa -b 1024 -N "" -f ~/.ssh/id_rsa
옵션의미주의·이유
-t rsa암호화 방식 = RSA기본값 rsa. 요즘은 ed25519도 쓰지만 서버 간 자동화는 RSA가 가장 호환됨
-b 1024키 길이 1024비트RHEL 9 계열 정책이 2048비트 미만을 거부 → 아래 실패 사례
-N ""새 키의 암호(passphrase)를 빈 값으로 지정쌍따옴표 두 개가 한 쌍. 이 값이 있어야 사용할 때 암호를 묻지 않음
-f 경로키를 저장할 파일 경로~/.ssh까지 Tab 자동완성. 경로를 정하면 생성을 묻지 않음

생성 직후 SHA256:… 형태의 지문(fingerprint)이 출력 — 방금 만든 키의 식별 표기이고, epel 설치 때 받은 GPG 키와는 무관

# [마스터 · aidata]
# 위치 확인 — /home/aidata 이어야 키가 홈의 .ssh에 생김
pwd
# 키가 모이는 .ssh 디렉토리로 이동
cd .ssh
# 기존 authorized_keys(ppk용)와 새 id_rsa·id_rsa.pub를 함께 확인
ls -al
파일정체용도
authorized_keys허용할 공개 키를 모아 두는 파일 (기존)윈도우 PuTTY가 ppk로 접속할 때 이 안의 키와 대조
id_rsa마스터가 가진 개인 키 (새로 생성)마스터가 워커에 자신을 증명할 때 사용. 외부 반출 금지
id_rsa.pub같은 쌍의 공개 키(public key)워커 authorized_keys로 복사될 내용 — 워커가 마스터를 식별하는 값

1024비트 키가 거부되는 경우

항목내용이유
증상load pubkey "/home/aidata/.ssh/id_rsa": invalid key length가 뜨고 패스워드를 물어 패스워드로 로그인됨키 길이가 정책에 못 미쳐 ssh가 키를 읽지 못한 상태 — 로그인이 된 것처럼 보이지만 키 인증은 실패
원인RHEL 9 계열 시스템 암호화 정책(crypto-policies) DEFAULT의 RSA 최소 길이 2048비트 — /etc/crypto-policies/back-ends/openssh.config의 RSAMinSize=2048Rocky Linux 9도 RHEL 9 기반이라 같은 정책. 배포판 이름이 아니라 정책이 기준
고칠 곳워커가 아니라 마스터의 키를 2048비트로 다시 생성워커는 받은 공개 키를 그대로 두고, 마스터가 새 키를 다시 보내면 됨
확인 위치워커 ~/.ssh: su sparkuser → cd ~/.ssh → ls -al에 authorized_keys만 있고 id_rsa 없음 / 마스터 ~/.ssh: known_hosts, known_hosts.old, id_rsa, id_rsa.pub양쪽 디렉토리를 비교하면 개인 키가 어느 쪽에 있어야 하는지 바로 보임
1024비트 키 — invalid key length는 CentOS Stream 9·Rocky 9의 crypto-policies(RSAMinSize=2048)가 1024비트 RSA를 거부해서 발생. 마스터에서 -b 2048로 다시 만들고 ssh-copy-id를 다시 실행

rsync — 수동 동기화

항목내용이유

실행명령을 입력할 때만 동작 (수동형)자동 반영이 필요하면 lsyncd — rsync가 먼저 되어야 lsyncd도 의미가 있음
계정마스터 aidata → 워커 sparkuser서로 다른 사용자·다른 서버 사이에서도 키 인증으로 전송

cd html
# 비교용 테스트 파일 2개 — 워커에 같은 이름이 생기는지 눈으로 확인

수정·새 파일전송·덮어쓰기 됨같은 이름의 새 파일을 올리면 내용이 교체됨
원본에서 삭제대상에 남아 있음rsync 기본 동작은 전송·갱신만 — 지우는 일은 하지 않음

rsync의 삭제 — 기본은 삭제를 전파하지 않아 지운 파일이 대상에 남음(백업에 유리). -delete를 붙이면 원본에 없는 대상 파일까지 지워 똑같이 맞추므로, 백업용 동기화에 습관적으로 붙이면 복구할 사본이 사라짐

lsyncd — 실시간 동기화

항목내용이유
이름lsyncd = Live Sync Daemon. 그 자체가 백그라운드 상주 데몬패키지 이름 끝 d가 daemon 표시
동작감시 대상의 변경을 감지해 rsync를 자동 호출 — 생성·수정·삭제를 계속 반영사람이 명령을 치지 않아도 대상이 원본과 같아짐
선행 조건rsync·키 인증이 먼저 동작해야 함lsyncd는 rsync를 부르는 역할 — rsync가 실패하면 라이브 동기화도 무의미
설치·설정 위치마스터에만. 워커는 설정도 가동도 없음받는 쪽은 rsync만 있으면 됨

수동(rsync)과 실시간(lsyncd) — 같은 rsync를 누가 부르느냐

rsync 수동

  • 명령을 칠 때만 동작
  • 삭제는 전파하지 않음 → 백업
  • 실행 시점을 사람이 정함 (cron 가능)

lsyncd 실시간

  • 변경 즉시 수 초 안에 반영
  • 삭제까지 전파 → 미러
  • 데몬이 계속 rsync를 호출
# [마스터 · aidata]
# 설정 파일은 root만 쓸 수 있어 root로 전환 (root 패스워드 입력)
su
# [마스터 · root]
# 실시간 동기화 설정 파일 열기
vi /etc/lsyncd.conf
# [마스터 · vi 명령 모드 · root]
# 줄 번호 표시 — 지울 줄과 남길 줄을 판단하기 위함
:set number
# [마스터 · /etc/lsyncd.conf 파일 안 · 설치 직후 기본값]
# 같은 서버의 /var/www/html을 /tmp/htmlcopy/로 복사하는 예시 설정
# default.rsyncssh = 원격에 lsyncd/ssh 설정을 두고 ssh로 직접 동기화하는 방식
sync{ default.rsyncssh, source="/var/www/html", host="localhost", targetdir="/tmp/htmlcopy/" }
편집할 일주의·이유
줄 정리필요한 줄만 남기고 dd로 삭제, 줄 사이는 엔터로 띄워 보기 좋게한 줄로 붙여 쓰면 오타를 찾기 어려움
host·targetdir삭제 — rsync 방식에서는 쓰지 않음남겨 두면 설정이 섞여 원하는 대상으로 가지 않음
default.rsyncsshdefault.rsync로 변경 — rsync를 실행하는 방식이 실습 대상(워커)에는 lsyncd가 없으므로 rsync만 호출하는 방식
target워커사용자@워커IP:워커경로로 작성쌍따옴표 안 오타 주의 — vi는 경로 자동완성이 없어 직접 입력
rsync = { }블록 안 키·값을 한 칸씩 띄워 작성들여쓰기는 보기용이라 탭을 안 써도 동작. 쉼표는 항목 구분이라 빠지면 설정 오류
문법설정 파일은 Lua 문법 — sync{ } 블록 안에 키=값을 쉼표로 나열따옴표·쉼표·중괄호 짝이 맞아야 기동. 문법 오류는 systemctl status lsyncd로 확인
설정 위치마스터에서만 설정 — 워커 창은 내려놓아도 됨워커는 설정·가동이 없고 수신만
환경 값워커 IP·포트·경로를 자기 환경에 맞게delay·exclude 같은 세부 옵션은 여기서는 다루지 않고 작동 확인까지만
# [마스터 · /etc/lsyncd.conf 파일 안]
# 동기화 작업 1개 정의 — sync 블록 하나가 원본 → 대상 한 쌍
sync{
    # rsyncssh 대신 rsync 방식 — 원격에 lsyncd를 두지 않고 rsync만 호출
    default.rsync,
    # 원본 = 마스터의 html 디렉토리 (끝 /까지: 디렉토리 안의 내용)
    source="/home/aidata/html/",
    # 대상 = 워커 사용자@워커 IP:워커 경로 (rsync 명령의 대상 표기와 동일)
    target="sparkuser@192.168.222.3:/home/sparkuser/html/",
    # rsync를 호출할 때 넘길 옵션 블록
    rsync = {
        # 데몬이 PATH 없이 실행돼도 찾도록 rsync 절대 경로 지정
        binary = "/usr/bin/rsync",
        # -a : 재귀 + 권한·소유자·수정 시각 보존
        archive = true,
        # -z : 전송 중 압축
        compress = true,
        # -v : 전송 파일을 로그로 남김
        verbose = true,
        # rsync가 쓸 ssh 명령 — 포트·키·호스트 키 확인 정책을 여기서 지정
        rsh = "/usr/bin/ssh -p 10022 -i /home/aidata/.ssh/id_rsa -o StrictHostKeyChecking=no"
    }
}
rsh 구성의미주의·이유
/usr/bin/sshssh 실행 파일의 실제 경로데몬 환경에는 PATH가 짧아 이름만으로는 못 찾을 수 있음
-p 10022워커 ssh 포트rsync 명령에서 -e로 주던 값과 같은 역할
-i /home/aidata/.ssh/id_rsa인증에 쓸 개인 키키 인증이 되어 있어야 무인 실행이 멈추지 않음
-o 이름=값ssh 설정(ssh_config) 항목을 명령줄에서 직접 지정하는 스위치설정 파일을 고치지 않고 이 명령에만 적용. "옵션을 연다"는 뜻이 아니라 항목을 덮어쓰는 자리
StrictHostKeyChecking=no처음 접속하는 호스트의 키를 묻지 않고 known_hosts에 자동 등록호스트 키 검증을 느슨하게 해 중간자 공격에 취약 — 무인 자동화에서 질문에 멈추지 않게 하려는 설정
옵션 이름 표기소문자(stricthostkeychecking=no)로 써도 동작ssh가 옵션 이름의 대소문자를 구분하지 않아 생기는 동작
StrictHostKeyChecking=no — 호스트 키를 묻지 않고 자동 등록. 무인 실행이 질문에 멈추지 않는 대신 중간자 공격 검증을 끄는 설정이므로 신뢰하는 내부망·실습에만 쓰고, 운영 서버에서는 accept-new나 키 사전 등록으로 대체

시간 기준 -mtime

# [호스트 리눅스 · root · 프롬프트 #]
find /var/log -mtime 2     # 48~72시간 전에 수정된 것
find /var/log -mtime -2    # 최근 48시간 이내 (오늘 포함)
find /var/log -mtime +2    # 72시간(3일) 이상 지난 것
표기뜻계산
2 (부호 없음)정확히 2일 전 구간경과 시간을 24시간 단위로 세고 소수 부분을 버림 → 48~72시간 전
-22일 이내 (최근)48시간 안에 수정된 파일 — 오늘 것도 포함
+22일 초과 (이전)최소 3일(72시간) 이상 지난 파일
하루 단위1일 = 24시간2일 = 48시간
부호의 의미-n은 n일 이내, +n은 n일 초과부호에 따라 결과가 완전히 달라짐 — 잘못 쓰면 엉뚱한 데이터를 출력하고 "오늘 기록이 없는데" 같은 오해가 생김
-mtime 부호 구분 — 2는 48~72시간 전, -2는 48시간 이내, +2는 3일 이상 지난 것. 분석용 로그에서 부호를 틀리면 없는 데이터를 있다고 판단하게 됨

용량 검색 — 서버 용량이 부족할 때

# [호스트 리눅스 · root · 프롬프트 #]
find / -type f -size +100M -exec ls -h {} \;    # -h만으로는 파일 이름만 출력 — 크기는 보이지 않음
find / -type f -size +100M -exec ls -lh {} \;   # -l을 붙여야 100MB 이상 파일을 사람이 읽는 단위로 출력
find /home/blue2 -type f -size +100M -exec ls -lh {} \;   # 사용자 홈만 검색 — 실무에서 주로 쓰는 형태
구성의미주의·이유
/최상위부터 전체 검색실무에서는 최상위를 한 번에 검색하지 않고 사용자 홈을 주로 검색 — 불필요한 파일을 많이 올려 두는 경우가 많음
-type f일반 파일(regular file)만 대상모든 타입이 아님 — d는 디렉토리, l은 심볼릭 링크
-size +100M100MB 초과 (대문자 M)+20M이면 20MB 초과
-lsls처럼 목록 출력길이가 너무 길어 보기 어려움
-exec ls -lh {} \;찾은 파일마다 ls -lh 실행ls -h는 -l·-s와 함께 써야 크기가 단위로 표시됨 — -l 없이 -h만 쓰면 이름만 출력
-execdir-exec 대신 쓰는 형태 — 찾은 파일의 디렉터리로 이동해 실행경로가 섞여 다른 명령이 실행되는 위험을 줄여 보안상 권장되는 형태
