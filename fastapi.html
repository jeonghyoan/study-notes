정의와 동작

항목내용주의·이유
정의API = Application Programming Interface — 프로그램끼리 값을 주고받는 창구정의를 외우는 문제는 나오지 않음 — 통신으로 이해
요청 규약HTTP 요청 통신 규약 GET·POST·PUT·DELETE (+ PATCH 등)이 4가지만 알면 됨
처리요청을 보내면 백엔드가 DB 쿼리 등으로 처리 → 결과(JSON/XML)를 돌려줌응답 형식은 2장
만드는 이유영화진흥위원회가 외부에 자기 DB(MySQL) 접근을 열어 줄 수는 없음 → DB 값을 가져와 JSON으로 뿌려 주는 창구를 만든 것API 사용자는 테이블 구조·계정을 몰라도 값만 받음
CSV 제공처XML/JSON 생성이 번거로워 DB를 엑셀(CSV)로 올려 둔 경우요즘 API는 JSON/XML이 기본 — 형식 비교 2장
포트API 서버도 포트를 열어야 외부에서 접근 가능개방은 인프라 담당자와 협의가 필요한 일 — 3장

메서드역할대응하는 SQL

응답 값의 출처 — 베이스 테이블과 뷰 테이블

구분내용주의·이유
베이스 테이블실제 데이터를 저장하는 일반 테이블데이터가 디스크에 있는 실체
뷰 테이블가상 테이블 — 데이터를 디스크에 따로 저장하지 않고, 복잡한 JOIN 쿼리를 간단히 호출하게 만든 것API가 조인 결과를 짧은 쿼리로 꺼내는 통로
장점긴 조인문을 한 번에 호출하고 원하는 컬럼만 출력호출하는 쪽 쿼리가 짧아져 실수·노출이 줄어듦
속도일반 뷰는 쿼리문을 저장해 둔 가상 테이블이라 호출할 때마다 원본 쿼리가 실행됨 → 속도 이점이 있는 구조가 아님목적은 편의·보안·재사용. 결과까지 저장해 빠르게 조회하는 것은 Materialized View — MySQL 8.0 Reference Manual(CREATE VIEW)

<color>blue</color>
<food>삼겹살</food>
<fruit>peach</fruit>

<!-- 태그를 한 줄에 이어 붙여도 같은 형식 -->
<이름>홍길동</이름><나이>35</나이>
  • 행 늘리기
    같은 태그 묶음을 반복하면 여러 행 — 컬럼명을 태그로 두면 표와 1:1 대응
  • 계보
    XML = SGML에서 파생된 마크업 언어. HTML도 SGML 계열이며 XML이 HTML에서 나온 것이 아님 — W3C XML 1.0 스펙
  • JSON 구조
    JSON은 객체(key-value)와 배열로 이루어진 데이터 형식 — 배열만 있는 형식이 아님. RFC 8259(ECMA-404)

CSV — 표를 그대로 올린 형식

  • 쓰는 곳
    XML/JSON 생성이 번거로운 제공처가 DB를 엑셀(CSV)로 올려 둔 경우
  • 한계
    행을 고치거나 지우는 갱신이 안 되는 일방향 형식 — API 응답으로 쓰기엔 JSON/XML이 기본
  • 공공데이터
    영화진흥위원회처럼 API로 JSON을 주는 곳은 키를 받아 호출 — 키 사용 예는 9장, 호출 실습은 spark.html 18장
데이터 형식 — JSON은 AI가 선호하고 객체 + 배열 구조(RFC 8259), XML은 태그로 표현하며 태그 이름은 보통 컬럼명, SGML 파생. CSV는 XML/JSON 생성이 번거로울 때 쓰는 표 형식으로 갱신 불가

REST와 RESTful

항목내용주의·이유
면접 단골REST / RESTful API를 구축할 때 포트를 어떻게 여는지원칙 설명만 하고 포트·인프라 협의를 빼면 답이 반쪽
REST API웹에 존재하는 자원을 주소(URI)로 지정해 가져오는 아키텍처 스타일특정 라이브러리·제품 이름이 아니라 설계 원칙
표현 방식 두 가지abc.co.kr/bbb.html?key=API키(쿼리 파라미터 — 영화진흥위원회 방식) / abc.co.kr/bbb/키값(경로에 값)둘 다 자원을 주소로 가리키는 방식 — 이 차이로 REST와 RESTful이 갈리지 않음
RESTfulREST 원칙(자원 URI · HTTP 메서드 · 무상태 등)을 지킨 API를 가리키는 말Roy Fielding 박사 논문(2000) — 쿼리 파라미터 사용 여부가 기준이 아님
포트REST든 RESTful이든 서버가 뜨려면 포트를 열어야 함인프라 담당자와 협의가 필요한 일 — 자기 마음대로 열 수 없음

FastAPI의 자리

항목내용주의·이유
정의파이썬으로 REST API 서버를 빠르게 구축하는 프레임워크"Fast"는 말 그대로 빠르다는 뜻
언어파이썬 전용자바·닷넷 쪽에서는 FastAPI를 거의 못 씀. Node.js 등 다른 언어로도 API 서버 구축은 가능
자바 계보자바 웹 프레임워크 → Spring → Spring Boot같은 역할을 자바에서 하는 조합
파이썬 계보Django(대표 기본 프레임워크) · Flask(예전에 많이 씀) · FastAPIDjango·Flask를 먼저 배운 사람이 FastAPI로 오는 흐름
다음 단계MLOps는 이후에 다룸 — 이 앞 단계인 API 상식을 알아야 연결됨핵심 조합은 FastAPI + Spark (Spark: spark.html 1~2장)
REST·RESTful 구분 — REST는 자원을 URI로 가져오는 아키텍처 스타일, RESTful은 그 원칙(URI·메서드·무상태)을 지킨 API. 쿼리 파라미터를 쓰는지로 갈리지 않음. 면접에서는 두 용어에 더해 포트 개방·인프라 협의까지 답해야 완성
FastAPI의 자리 — 파이썬 전용 프레임워크(자바·닷넷에서는 거의 못 씀). 같은 역할의 자바 계보는 Spring → Spring Boot, 파이썬은 Django·Flask 이후 FastAPI. 이 환경의 핵심 조합은 FastAPI + Spark

app = FastAPI()

@app.get("/")
def read_root():
    # dict를 돌려주면 FastAPI가 JSON으로 변환 — {"msg": "..."} 형태가 그대로 응답
    return {"msg": "서버 오픈되었습니다"}

# 경로에 파라미터 id — /data/홍 처럼 주소 끝의 값을 함수 인자로 받음
@app.get("/data/{id}")
def read_item(id: str):                  # int=숫자만, str=문자
    # 받은 값을 키 두 개로 돌려줌 — f-string으로 문장 안에 값 삽입
    return {"값": id, "데이터 출력": f"데이터 값은 {id}"}

# [마스터 · JupyterLab 노트북 셀 · spark]
import nest_asyncio, asyncio, uvicorn
nest_asyncio.apply()                     # 이미 도는 이벤트 루프에 중첩 허용 — 비동기 충돌 해결

# app 객체를 직접 전달 — "모듈명:app" 문자열 대신이라 주피터에서 모듈을 찾지 못하는 문제가 없음
config = uvicorn.Config(app, host="0.0.0.0", port=9999, log_level="info")
server = uvicorn.Server(config)
asyncio.create_task(server.serve())      # 비동기 서버를 task로 등록 — 셀이 끝나도 서버가 계속 돎
print("FastAPI 서버가 background로 구동되었습니다.")

    서버는 동기·비동기 두 종류이고, 여기서는 비동기 서버를 task로 등록
  • 정상 신호
    로그의 빨간 글씨가 전부 에러는 아님 — Uvicorn running on ...이 보이면 정상, 200 OK가 찍히면 통신이 정확히 된 것
  • 종료
    주피터 Kernel Shutdown을 누르면 서버가 죽고 포트가 끊김 — 새로고침하면 접속 불가

@app.get("/login/{id}")

from fastapi import FastAPI
import uvicorn

# 앱 객체 — 라우트는 이 객체에 데코레이터로 붙임 (6장)
app = FastAPI()

# POST로 받는 라우트 — 통신 방식은 데코레이터에서 정해짐 (6장)
@app.post("/notice")
def post_frm(id: str):
    # dict 반환 → 호출한 쪽에 JSON으로 전달. f"..."는 format 문자열(값이 들어간 문자열)
    return {"key": "test", "데이터 출력": f"데이터 값은 {id}"}

# GET으로 받는 라우트 — 경로를 /notice와 다르게 두어 요청을 구분
@app.get("/user")
def get_frm(id: str):
    return {"key": "test2", "데이터 출력": f"데이터 값은 {id}"}

# 이 파일을 직접 실행할 때만 서버 기동 (8장)
if __name__ == "__main__":
    print("FastAPI 서버 구동되었습니다")
    uvicorn.run("file_api:app", host="0.0.0.0", port=9999)

개념 — Origin과 차단 주체

항목내용주의·이유
CORSCross-Origin Resource Sharing — 출처가 다른 쪽에 자원을 쓸 수 있게 하는 규칙프로토콜·도메인·포트 중 하나라도 다르면 Cross-Origin
Origin 예abc.co.kr ≠ www.abc.co.kr, http ≠ https, 80 ≠ 9999포트만 달라도 다른 출처 — 이번 실습은 80과 9999
차단 주체브라우저가 동일 출처 정책(SOP)으로 응답을 막음서버가 요청을 거부한 것이 아님 — 로그에 200 OK가 남는 이유
허용 방식서버가 응답 헤더(Access-Control-Allow-Origin 등)로 허용 의사 표시HTML 쪽에서 해결할 방법은 사실상 없음

허용 코드 — CORSMiddleware

# [마스터 · /home/spark/file_api.py 파일 안 · spark]
# CORS를 처리하는 미들웨어 — uvicorn이 아니라 FastAPI(Starlette)에 들어 있는 클래스. pip 추가 설치 불필요
from fastapi.middleware.cors import CORSMiddleware

# 수업 기본형 — 전부 허용. 보안은 이후 과정이라 작동이 우선
app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],        # 허용할 출처 — "*"는 아무 출처나 받아 보안이 뚫림
    allow_credentials=True,     # 쿠키·인증 정보 허용 여부
    allow_methods=["*"],        # 허용할 메서드 — GET·POST·PUT·DELETE
    allow_headers=["*"],        # 허용할 헤더 — JSON 전송(Content-Type: application/json)과 폼 전송이 달라 영향
)

# 허용 목록으로 좁힌 형태 — 지정한 IP·포트에서 온 요청만 받고 나머지는 거부
se = [
    "http://192.168.22.2",        # 웹(80) 출처
    "http://192.168.22.2:8080",   # 다른 포트
    "http://localhost",
]
app.add_middleware(CORSMiddleware, allow_origins=se)   # 메서드·헤더도 배열 변수로 만들어 제한 가능

  • 적용
    수정 후 Ctrl+C로 정지 → 재실행. 미들웨어는 앱 생성 시 등록되므로 재시작해야 반영

  • 확인
    F12 → Network 탭에서 요청·응답 헤더 확인
CORS 원리 — Origin은 프로토콜 + 도메인 + 포트의 조합이고 하나라도 다르면 Cross-Origin. 막는 것은 브라우저(SOP)이고, 푸는 것은 서버의 허용 헤더(CORSMiddleware). 포트가 다른 이번 실습(80·9999)이 대표 사례
허용 조합의 함정 — allow_origins=["*"]와 allow_credentials=True를 함께 두면 브라우저가 와일드카드 + 자격증명 조합을 거부. 쿠키·인증을 쓰려면 허용 origin을 목록으로 명시

DELETE — 삭제 라우트

# [마스터 · /home/spark/mysql_db.py 파일 안 · spark]
@app.get("/del/{id}")      # 경로 {id}로 삭제할 번호 지정 — 실습에서 만든 형태
def del_movie(id: str):
    with get_mysql_connection() as con:
        with con.cursor() as cur:
            # %s 자리에 (id,)를 바인딩 — 값을 문자열로 이어 붙이지 않아 SQL 인젝션 차단
            result = cur.execute("DELETE FROM DailyBoxOffice WHERE id = %s", (id,))
            # INSERT·UPDATE·DELETE는 commit 필수 — 빠지면 DB에 반영 안 됨
            con.commit()
    # 1이면 삭제 완료, 0이면 대상이 없어 삭제 안 됨
    return {"result": result}
실행 결과의미확인 방법
{"result": 1}해당 번호 1건 삭제 완료같은 URL 다시 호출 → {"result": 0}
{"result": 0}대상이 없어 삭제된 행 없음SELECT * FROM DailyBoxOffice WHERE id=15 → 빈 결과
  • 복구 불가
    삭제는 백업이 없으면 되돌릴 수 없음 — 실습에서도 지운 행은 백업본으로만 복원
  • fetchall 위치
    fetchall()은 SELECT에서만 사용 — INSERT·UPDATE·DELETE 결과는 execute의 반환값(행 수)으로 받음. 한 건만 필요하면 fetchone()
  • 접속 정보 dict 를 넘기는 방법
    접속 정보를 dict 하나로 두고 pymysql.connect(**db_config) 로 키·값을 풀어 전달 — dict 를 통째로 넘기면 인자 자리에 dict 가 들어가 에러
  • 실수 — commit 누락
    con.commit()을 빼면 응답은 나오는데 DB가 그대로 — 처음에 안 지워진 원인
  • 실수 — finally close
    finally에서 close()를 하면 요청 한 번 끝날 때 연결이 닫혀 다음 요청이 계속 에러 → 실습에서는 finally 부분을 삭제
  • 연결 유지
    API는 연결이 계속 유지돼야 해서 close를 별도로 다뤄야 한다는 것이 강사 설명 — 요청마다 열고 닫는 구조와 충돌
  • 실수 — 들여쓰기
    return을 with 바깥으로 빼는 들여쓰기가 틀리면 에러
  • 이름 자유
    URL 뒤 숫자만 바꾸면 해당 번호가 삭제됨. 함수·파라미터 이름은 다른 것과 겹치지 않으면 자유
삭제의 메서드 — 실습은 @app.get("/del/{id}")로 만들었지만, 데이터를 바꾸는 작업은 DELETE(또는 POST) 메서드로 만들어야 함. GET은 조회용 안전한 메서드라 링크 클릭·크롤러 호출만으로 삭제될 위험 — RFC 9110(HTTP Semantics) 9.2.1
처리 짝 — SELECT는 execute → fetchall(), INSERT·UPDATE·DELETE는 execute → commit(). 결과 1은 성공, 0은 대상 없음. 값은 %s 파라미터 바인딩으로 넘겨 SQL 인젝션 차단
