vsftpd(FTP) 통합 학습노트

범위: vsftpd(FTP 서버) 설정 파일 /etc/vsftpd/vsftpd.conf 라인별 설정(익명·쓰기·umask·로그·포트 20/21) · 타임아웃 · ASCII/Binary 전송과 확장자 차단(deny_file) · chroot(홈 디렉토리 밖 접근 차단) · 포트 변경(9021)과 VirtualBox 포트 포워딩 · 설정 오류 대응·백업(systemctl status·journalctl). 내용이 추가될 때마다 범위가 늘어남.

변경 → restart → 같은 조건 접속 확인

설정을 하나라도 바꾸면 systemctl restart vsftpd.service 필수, FileZilla를 완전히 종료하고 같은 아이디·비번으로 재접속해 확인. 오타 한 글자로 서비스가 안 뜨므로 수정 전 cp 백업, 원인은 systemctl status·journalctl -xeu로 확인.

보안 4축 : 익명 · 쓰기 · chroot · 포트

anonymous_enable=NO 유지, write_enable=NO면 다운로드 전용, xferlog_enable NO 금지. chroot_local_user=YES는 쓰기 가능한 홈에서 500 에러 → allow_writeable_chroot=YES. 기본 포트 21은 listen_port=9021로 변경.

접속 21 · 포트 선택 · 타임아웃 기준

접속은 21번, 20번은 액티브 모드 데이터 연결 포트. 포트 변경 시 충돌 주의(3306 금지, 9000번 이상 권장, 1500 이하 금지). idle_session_timeout = 무동작 시간, data_connection_timeout = 전송이 멈춘 시간.

anonymous_enable (12번) — 익명 접속 실습

# [호스트 리눅스 · /etc/vsftpd/vsftpd.conf 파일 안 · root]
# 12번 : 익명(anonymous) 접속 허용. 실습 때만 YES, 끝나면 NO로 복구 (YES 상태는 실무에서 크게 문제됨)
anonymous_enable=YES
단계내용결과·이유
YES로 변경 + 재시작FileZilla를 완전히 종료 후 재실행 → 호스트 = 리눅스 IP, 사용자·비밀번호 비움, 포트 21 → 빠른 연결접속됨(뚫림) — 이 한 줄로 익명 접속 허용 여부, 곧 보안이 갈림
NO로 복구 + 재시작같은 조건(아이디·비번 없이)으로 접속안 됨(막힘)
anonymous_enable — YES면 아이디·비번 없이 접속되어 보안이 뚫림. NO 유지. 바꾼 뒤에는 반드시 restart 후 같은 조건으로 접속 확인

local_enable (15번)

항목내용주의·이유
값YES 그대로 둠웬만하면 건드리지 말 것
의미로컬(익명이 아닌) 사용자 로그인 허용 여부NO면 일반 사용자 전원 접속 불가 (로그 기록 옵션이 아님)
local_enable — 일반(로컬) 사용자 로그인 허용 여부. NO면 일반 사용자 전원 접속 불가이므로 YES 그대로 유지

write_enable (18번) — 다운로드 전용 실습

# [호스트 리눅스 · /etc/vsftpd/vsftpd.conf 파일 안 · root]
# 18번 : 쓰기(업로드) 차단 → 다운로드 전용 시스템 구축. 실습 후 YES로 복구
write_enable=NO
단계내용결과·이유
NO로 변경 + 재시작접속·디렉토리 목록 확인접속 정상, 디렉토리 목록 보임
파일 업로드FileZilla로 업로드 시도치명적인 전송 오류, 큐에서 계속 대기하며 업로드 안 됨 (접속은 허용하고 쓰기만 막은 것)
다운로드서버에만 있는 파일(예 123.data) 더블클릭다운로드됨
복구18번을 YES로 되돌림읽기·업로드·다운로드 모두 가능
write_enable — NO면 업로드 불가, 다운로드만 가능 (다운로드 전용 서버). 접속은 되므로 업로드 시 치명적인 전송 오류로 확인

local_umask (22번)

# [호스트 리눅스 · /etc/vsftpd/vsftpd.conf 파일 안 · root]
# 22번 : 로컬 사용자가 만드는 파일에 적용하는 umask (8진수, 맨 앞에 0 필요). 이 실습에서는 기본값 022 유지
local_umask=022
# 실무 사례 값 : 읽기·쓰기는 되고 실행은 안 되게 함. 실행되면 FTP로 올린 파일로 백도어를 돌려 서버 권한을 빼앗기고 포트가 열릴 수 있음
local_umask=066
항목내용주의·이유
기본값 022숫자는 보통 앞에 0을 붙여 표기, 쓰기 권한(w) 관련 부분이 2man 기본값은 077, 샘플 설정 파일 값이 022
실무 066읽기·쓰기는 되고 실행은 안 되게 함실행을 막는 이유 : 백도어 실행 방지
권한 확인 위치FileZilla 오른쪽 서버 쪽 목록의 권한 열 (rwx…)숫자로 읽을 때는 앞에 0을 붙여서 생각
🔍 직접 확인 · 8강 077 설명 · 13:49~14:09

"077로 바꾸면 읽고 쓰고 실행이 다 됨", "게스트가 작동되니 다른 사람이 덮어쓸 수 있다"는 설명이 어느 값 기준인지 문맥 불분명 — 영상 해당 구간을 다시 듣고 확인 필요

local_umask — 업로드 파일의 권한 마스크(8진수, 맨 앞 0). 실무 066 = 실행 권한 차단으로 FTP 업로드 파일 백도어 실행 방지

홈 디렉토리 밖 접근 막기 (chroot)

한눈에 보기 — chroot 설정 → 500 에러 → 해결

① 문제

홈·루트 버튼으로 최상위까지 보임

② 설정

101 chroot_local_user=YES · 102 chroot_list_enable=NO

③ 500 에러

재시작 후 접속 불가 (쓰기 가능한 홈 거부)

④ 해결

103번 자리에 allow_writeable_chroot=YES 추가

⑤ 정상

최상위를 눌러도 자기 디렉토리만 보임

실무에서 이렇게 한다는 소개 — 외울 필요 없음

문제와 설정 라인

항목내용주의·이유
문제FileZilla에서 홈·루트(최상위) 버튼을 누르면 최상위 디렉토리까지 다 보임 (101~104번 라인을 설정한 뒤에도 이 상태에서 시작)보안이 뚫린 것과 같음 (자기 디렉토리만 보여야 함)
FTP가 약하다는 말대부분 이 상태로 두기 때문 (해커가 좋아함)
101번 chroot_local_user=YES로컬 사용자를 홈 디렉토리에 가둠 — 접속하면 자신의 경로가 기준점(최상위)이 됨리눅스에 등록된 로컬 사용자만 해당
102번 chroot_list_enable켜면 chroot_list_file의 목록이 가두지 않을 사용자(예외)가 됨NO로 하면 예외 목록이 없어져 모두 가둬짐 → 에러가 나는 흐름
104번 chroot_list_file=/etc/vsftpd/chroot_list예외(가두지 않을) 사용자 목록 파일103번 추가 후 105번으로 밀림

2. 500 에러재시작 후 FileZilla 재접속500 에러로 접속 못 함 (보안상 막힘). 설정을 다시 풀면 최상위까지 다 보이므로 이러지도 저러지도 못하는 상황
3. 원인가둔 홈 디렉토리가 쓰기 가능하면 vsftpd가 실행을 거부하는 보안 검사500 OOPS: vsftpd: refusing to run with writable root inside chroot() (vsftpd 2.3.5 이후)
4. 해결103번(#(default follows) 윗줄) 자리에 allow_writeable_chroot=YES 한 줄 추가위 보안 검사를 우회. man 페이지에는 이 옵션이 없었음 (출처 : DigitalOcean Community, Dell KB 000214872)
실수 사례allow_writeable_chroot를 대문자 W로 입력해 오타 발생소문자로 수정
5. 정상 확인재시작 후 FileZilla를 완전히 종료하고 다시 접속자기 디렉토리만 보이고 최상위를 눌러도 자기 것만 보임 = 정상
chroot 500 에러 — chroot_local_user=YES인데 가둔 홈이 쓰기 가능하면 500 OOPS: refusing to run with writable root inside chroot() → allow_writeable_chroot=YES(모두 소문자)로 해결. 홈 디렉토리 밖이 보이면 안 됨
chroot 범위 — 이 장(chroot 상세)은 평가 범위에 나오지 않음. 외울 필요 없고 실무 소개로 이해

기본 포트를 바꾸는 이유

항목내용주의·이유
보안 효과21번(기본 포트)은 공격하기 쉬우므로 임의로 9021로 변경해커가 9021을 모르면 헤매다 다른 대상으로 넘어감 (접속하는 사람만 새 포트를 알면 됨)
실무기본 포트는 거의 안 씀선임이 포트를 다 바꾸라고 하는 것이 정석
SMTP 예시기본 포트를 쓰면 공격당하기 때문에 메일 서버도 다른 포트를 쓴다는 설명 (네이트 메일)SMTP 서버 간 릴레이는 25번, 메일 제출(submission) 표준 포트는 587 (RFC 6409)
🔍 직접 확인 · 8강 SMTP 포트 번호 · 78:08

전사에는 "567번"으로 적혀 있으나 587의 오기일 가능성이 큼 — 실제 발언 확인 필요. 네이트 메일이 실제로 쓰는 포트는 확인 못 함 — 네이트 메일 SMTP 설정 안내 페이지에서 포트 번호 확인 필요

기본 포트 변경 — 21(기본 포트)은 공격 대상이 되기 쉬움 → listen_port=9021 로 변경하고 netstat -lnp 로 확인, 접속자는 새 포트로 접속. 실무에서 기본 포트는 거의 안 씀

대역사용 권고이유
