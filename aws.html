헷갈리는 두 항목의 실제 의미

  • ARM64
    Lambda 함수가 실행될 CPU 아키텍처 선택 — 기본은 x86_64, 켜면 Graviton 기반 arm64. PC의 CPU와는 무관하고, arm64는 가격 대비 성능이 유리하지만 코드·패키지가 arm64와 호환돼야 함
  • KMS 암호화
    외부 업체에 넘기는 용도가 아니라, 배포 패키지를 직접 관리하는 KMS 키로 암호화해 키 접근 제어·감사를 붙이는 설정

화면 하단 안내 — 아이콘 표시 설정은 함수 생성 후 추가·삭제 불가, 나머지 설정은 나중에 변경 가능. Create Event Function을 누르면 함수가 만들어지고 코드 편집 화면으로 이동.

추가 설정 8항목 — ARM64·사용자 지정 실행 역할·함수 URL·테넌트 격리 모드·VPC·코드 서명·KMS 암호화·태그는 이번 실습에서 모두 기본값. 여기서 미리 세팅하면 Lambda 동작이 꼬이고 원인 찾기도 어려워짐 — VPC·KMS·코드 서명은 그 서비스를 실제로 다룰 때 설정

수신 이벤트 전체 출력

# [AWS 콘솔 · Lambda 함수 mz-apink 코드 편집기 · admin]
import json

def lambda_handler(event, context):
    print("수신된 이벤트:", json.dumps(event))     # 수신 데이터 전체 출력 — 값 파악용
    return {
        'statusCode': 200,
        'body': json.dumps('Hello from Lambda!')
    }
  • event
    프론트엔드(클라이언트)가 보낸 JSON 데이터
  • 실행 순서
    저장(Ctrl+S) → Deploy(Ctrl+Shift+U) → Test(Ctrl+Shift+I)
  • 실행 결과
    Status: Succeeded, 응답 Hello from Lambda, 로그에 수신 이벤트 JSON 출력 — 이것이 Lambda의 기본 사용 방식
  • 전체 출력의 용도
    동작 확인용이라 필수 아님 — 프론트엔드가 없을 때 어떤 값이 오는지 파악하는 수단. 확인이 끝나면 주석 처리
  • 실무 테스트
    프론트엔드 개발자에게 테스트를 요청해 실제 데이터를 받아 확인
  • 연결 에러
    AI(챗봇)가 준 코드대로 문자열과 이벤트를 +로 이어 붙이면 str이 아닌 값을 연결해 에러 → +를 지우고 쉼표로 연결

키로 값 꺼내기

# [AWS 콘솔 · Lambda 테스트 이벤트 편집기 · admin]
# 이벤트 이름 Event-apink1로 저장 — email 키를 로그인 값으로 쓰는 상황
{"user": "홍길동", "age": 35, "email": "hong@nate.com"}
# [AWS 콘솔 · Lambda 함수 mz-apink 코드 편집기 · admin]
import json

def lambda_handler(event, context):
    # print("수신된 이벤트:", json.dumps(event))   확인이 끝나면 주석 처리
    userdata = event.get("email", "로그인")         # 키가 없으면 기본값 "로그인"
    message = f"{userdata} 님 AWS 에 오신것을 환영합니다."   # f-string — 값을 문장 안에 삽입
    print(message)
    return {
        'statusCode': 200,
        'body': json.dumps({
            'msg': message,                         # 키 이름은 임의
            'status': 'success'                     # 정상 전달 표시
        })
    }

event.get(키, 기본값)은 키가 있을 때 값을, 없을 때 기본값을 돌려줌 — 없는 키로 event["email"]을 쓰면 KeyError로 실행이 실패하므로 테스트 이벤트에 그 키를 넣었는지와 함께 확인. 실행 결과는 응답에 status: success와 msg가 표시되는 상태.

응답 헤더와 한글 표기

# [AWS 콘솔 · Lambda 함수 mz-apink 코드 편집기 · admin]
# 응답에 헤더를 붙여 형식·문자셋을 지정 — body는 문자열이므로 헤더로 형식을 알려 줌
# 'Access-Control-Allow-Origin': '*' 는 보안상 넣지 않음 — 외부 허용은 별도 설정에서
    return {
        'statusCode': 200,
        'headers': {
            'Content-Type': 'application/json; charset=utf-8'
        },
        'body': json.dumps({'msg': message, 'status': 'success'})
    }
  • 증상
    응답 body의 한글이 \uXXXX 유니코드 이스케이프로 보임
  • 원인
    json.dumps의 기본값 ensure_ascii=True가 한글을 \uXXXX 표기로 바꾼 것 — URL 인코딩 문제가 아니고, charset=utf-8 헤더를 넣어도 이 표기는 그대로 남음
  • 한글 그대로 내보내기
    json.dumps(..., ensure_ascii=False) — 헤더가 아니라 json.dumps 옵션이 표기를 바꿈
  • 확인 결과
    200 응답, body 문자열에 \u 이스케이프 표기가 그대로 남은 상태
  • CORS 헤더
    브라우저에서 다른 출처로 호출할 때 필요한 Access-Control-Allow-Origin과 세 곳의 허용 설정: 27장
이벤트 = API 호출 — Lambda가 받는 event는 클라이언트가 보낸 JSON 그대로라, event.get(키, 기본값)으로 꺼내고 반환 dict의 statusCode·body가 응답이 됨. 문자열과 이벤트를 +로 이으면 str 타입 에러 — 쉼표로 연결
한글 응답 — \uXXXX 표기의 원인은 json.dumps 기본값 ensure_ascii=True. charset=utf-8 헤더로는 바뀌지 않고, ensure_ascii=False로만 한글이 그대로 나감. Access-Control-Allow-Origin: *는 보안상 빼고 필요할 때 별도 설정

리스트 정렬 — sort(key=lambda ...)

# [VS Code · Lambda 프로젝트 mz-apink · lambda_function.py · lambda_handler 안]
    user = [("홍길동", 55), ("강감찬", 21), ("이순신", 30)]
    user.sort(key = lambda b: b[1])   # 튜플의 1번 값(숫자) 기준 정렬
    print(user)
항목내용메모
실행 결과[("강감찬", 21), ("이순신", 30), ("홍길동", 55)]나이(튜플 1번 값) 기준 오름차순 — 셔플이 아님
용도리스트 안의 튜플·딕셔너리를 특정 값 기준으로 정렬할 때 sort 뒤에 lambda를 붙임DB 조회 결과를 특정 컬럼 기준으로 정렬하는 상황과 같은 모양
이름 규칙lambda b:의 b는 임의 이름, key는 바꾸면 안 되는 키워드key=는 각 요소에서 정렬 기준 값을 뽑아 주는 함수를 받는 키워드 인자 — 배열의 키가 아님
  • 실수 사례 1
    key를 다른 이름(예 key11)으로 바꾸면 TypeError: sort() got an unexpected keyword argument 'key11'
  • 실수 사례 2
    users.sort(...)로 써서 변수명 user와 달라 에러 → 변수명을 통일

변수에 lambda 넣기

    print(sum(30, 50))

실행 결과 80 — 인자를 받는 lambda는 lambda 매개변수: 식 형태로 쓰고, 호출할 때 값을 넘김.

sort(key=lambda ...) — key는 고정 키워드라 다른 이름으로 바꾸면 TypeError: sort() got an unexpected keyword argument. lambda b: b[1]은 튜플의 1번 값을 정렬 기준으로 뽑아 주는 것이라 결과는 오름차순(21 → 30 → 55)이고 셔플이 아님. 리스트 변수명과 sort를 부르는 변수명도 일치

# [AWS 콘솔 · Lambda 함수 mz-apink 코드 편집기 · 새 파일 test.py · admin]
import json

def lambda_handler(event, context):
    try:                                # 정상 실행이 된 경우
        return {
            'state' : 200,              # 정상 상태 코드 (연습용 키)
            'body' : json.dumps({       # 결과는 대부분 JSON으로 반환
                'msg' : '통신처리 완료'
            })
        }
    except Exception as e:              # 문제 발생 시 이쪽으로 옴
        print(e)                        # 에러 내용 출력
        return {
            'state' : 500,              # 500 = 서버 쪽 문제
            'body' : json.dumps({
                'msg' : '통신에러 발생'
            })
        }

상태 키는 화면에서 'state'로 입력하는 연습용 코드 — 에러가 나면 Lambda 테스트로 처리 결과를 확인.

응답 키 — Lambda 응답을 API Gateway·함수 URL로 돌려줄 때 상태 코드 키는 statusCode, 본문 키는 body이고 대소문자 구분. 'state'나 소문자 'statuscode'는 상태 코드로 인식되지 않음 — 실습 코드의 'state'는 연습용 표기

S3 = Simple Storage Service — 콘솔 S3 → 버킷, 버킷은 파일을 담는 거대 창고. 구글의 같은 서비스는 GCS(Google Cloud Storage)

항목내용주의·이유
정의S3 = Simple Storage Service, AWS 클라우드 스토리지 서비스. 버킷 = 거대 창고서버 컴퓨팅(EC2)과 분리된 저장 계층
저장 대상이미지, 문서(pdf·pptx), 동영상, 압축파일, 로그파일형식 제한 없이 객체로 저장
EC2만 쓸 때업로드 파일이 서버에 쌓여 50GB 같은 서버 용량이 계속 부족 — 동영상까지 올리면 서버가 버티지 못함파일을 S3로 넘겨 저장하면 서버 용량이 작아도 운영 가능, 버킷 안에 폴더별로 저장
기본 상태프라이빗 — 퍼블릭 액세스 차단이 켜진 기본값공개로 풀면 데이터가 모두 유출 — AI가 공개로 풀라고 답해도 그대로 따르지 않음
메서드업로드(PutObject) = HTTP PUT(push 방향), 다운로드(GetObject) = GET, 삭제는 DELETE버킷에 따로 정해진 기본 메서드는 없음 — PUT·GET·DELETE 등 어떤 작업을 허용할지는 IAM·버킷 정책으로 결정
궁합S3와 가장 잘 맞는 서비스는 Lambda업로드 이벤트·presigned URL 모두 Lambda와 연결해 실습 (20·24장)
내구성과 가용성 — S3 Standard 내구성은 99.999999999%(9가 11개, 11 nines), 가용성 설계 목표는 99.99%. 내구성은 저장한 데이터가 사라지지 않을 확률, 가용성은 서비스가 응답할 확률로 서로 별개의 지표
프라이빗 기본 — 버킷은 기본이 비공개이고 모든 퍼블릭 액세스 차단이 켜진 상태. 공개로 풀면 저장한 파일이 모두 노출되므로, 실습 버킷에서도 공개 해제는 하지 않음

객체 소유권 — ACL

ACL = Access Control List = 접근 제어 목록, 보안 계층에 해당 — 개념만 알면 됨.

선택지내용실습
ACL 비활성화(권장·기본)Bucket owner enforced — 소유자가 모든 객체를 소유하고 ACL로 권한을 나누지 않음비활성화
ACL 활성화객체별·버킷별 ACL로 접근 권한을 부여미사용

ACL 활성화·비활성화는 비용·복구와 무관 — 덮어쓰기·삭제 복구는 버전 관리(Versioning) 기능이고, “비활성화 12개 = 활성화 1개”라는 비용 차이는 근거가 없음.

버전 관리·태그·객체 잠금

옵션내용실습
버킷 버전 관리같은 키의 객체를 덮어쓰거나 삭제해도 이전 버전을 보존해 복구할 수 있게 하는 기능비활성화(테스트용) — 버킷 자체를 버전별로 나누는 기능은 아님
태그키-값 태그 추가 — 권한 분석·관리 자료를 만들 때 사용사용 안 함
객체 잠금(Object Lock)절대 수정·유실되면 안 되는 자료를 영구 보존 — 예: 은행이 연말 마감 후 1년치 입출금 데이터를 버킷에 옮기고 잠금, 수정 불가비활성화

기본 암호화 유형

기본값 SSE-S3 — 실습도 SSE-S3, SSE-KMS·DSSE-KMS는 선택하지 않음. KMS = Key Management Service(키 관리 서비스).

유형키 관리비용용도
SSE-S3 (Amazon S3 관리형 키)서버 쪽에서 마스터키 관리없음기본값
SSE-KMS (AWS KMS 키)고객이 키를 직접 생성·관리, 키 정책을 고객에게 설명·전달키 생성 비용 + 일별 유지 비용(3일 쓰면 3일치)고객 요청 시 — 키 단위 접근 통제, 키별 접근 로그 기록(보안감사)
DSSE-KMS (이중 계층 서버 측 암호화)이중 보안가장 큼강력한 규제 준수(금융·공공기관) — 고객이 요구하면 필수
  • 버킷 키
    Bucket Key — KMS 호출(요청) 비용을 줄이는 옵션. SSE-KMS일 때만 의미가 있어 SSE-S3면 활성·비활성 상관없음
  • 생성
    버킷 만들기 클릭 → 목록에서 mz-apink-s3… 버킷 확인

같은 계정에 수강생 버킷이 여러 개 보여도 퍼블릭이 아니라는 것과 접근 가능 여부는 별개 — 퍼블릭 액세스 차단은 익명(외부) 공개를 막는 설정이고, 같은 계정의 IAM 사용자가 다른 버킷을 보고 쓸 수 있는지는 그 사용자의 IAM 정책으로 정해짐.

암호화 3종 — SSE-S3는 기본·무료(서버 쪽 마스터키 관리), SSE-KMS는 고객이 키를 관리하고 비용이 들지만 키 단위 접근 통제·접근 로그(보안감사)를 얻음, DSSE-KMS는 이중 계층으로 가장 비싸고 규제 준수(금융·공공)에 필요한 선택. 버킷 키는 KMS 요청 비용 절감용이라 SSE-KMS일 때만 의미

트리거 목록에 표시

버킷만 만든 상태에서는 Lambda와 S3가 연결되지 않음 — 버킷에 객체가 만들어지는 순간 함수가 실행되도록 트리거를 붙이는 단계

  1. Lambda → 함수 mz-apink → 트리거 추가 → 소스 S3 → 버킷 선택
  2. 이벤트 유형 — 모든 객체 생성 이벤트(s3:ObjectCreated:*) 선택. 목록에 PUT·POST·COPY 등이 있고 기본(권장)은 PUT
  3. 삭제 이벤트는 사용 안 함 — rls 항목도 제외
  4. 접두사·접미사(선택) — 입력 안 함, 특수문자 URL 인코딩 등도 생략
  5. 재귀 호출 확인 체크 필수 — 입력·출력에 같은 버킷을 쓰면 재귀 호출로 Lambda 사용량·비용이 늘 수 있음을 인정하는 항목
  6. 추가 → 실행 결과 — 트리거 목록에 S3 트리거, 아래에 버킷 정보 표시

콘솔 홈에는 최근 방문 서비스(IAM 포함 작업 이력)가 표시되고, Lambda 대시보드에는 함수·이벤트 수와 사용량이 표시됨 — 트리거가 붙었는지 대시보드와 트리거 목록 두 곳에서 확인.

이벤트 유형 해석

이벤트 유형반응 범위메모
ObjectCreated:*버킷에 객체를 만드는 모든 작업별표(*)가 모든 작업을 뜻함 — 실습 선택
PUTObjectCreated:Put만PUT·POST = 파일 전송(업로드), 거의 같은 방식 — 선택한 방식과 같은 메서드로 보내야 반응
POSTObjectCreated:Post만POST로 업로드하는 폼과 짝을 이룸
COPYObjectCreated:Copy만S3 내부에서 파일 복사가 일어날 때 반응
  • 다른 유형을 고르면
    그 유형만 처리 — PUT만 선택하면 PUT만 반응하고 나머지 업로드는 무시
  • 실무
    버킷을 넘겨받으면 이벤트 유형부터 확인하고 처리 — 어떤 업로드에 반응하는 구성인지가 먼저이고, 이벤트 유형을 보고 처리하라는 것이 실무 지시의 뜻
  • GET
    객체 생성 이벤트 유형은 Put·Post·Copy·CompleteMultipartUpload 등이고 GET(다운로드)은 이벤트 알림 유형이 아님 — HTTP 메서드와 이벤트 유형은 별개
  • 가장 중요한 값
    버킷 이름(저장 위치) — 개발자에게 알려 주면 그 버킷에 파일이 저장됨
  • 삭제 위험
    버킷을 삭제하면 안의 데이터가 모두 사라짐
재귀 호출 — 함수의 입력과 출력에 같은 버킷을 쓰면 업로드가 다시 함수를 호출해 사용량·비용이 끝없이 늘어남. 재귀 호출로 사고를 낸 사례가 있어 권장하지 않고, 정책으로 호출 자체를 막는 경우도 있음 — 트리거 추가 시 재귀 호출 확인 체크 필수

S3 전체 접근

실습에서 다루는 보안은 Lambda(함수) 쪽 권한 — 버킷 권한 탭의 정책 편집은 잘못하면 버킷이 공개되므로 보안팀 영역으로 두고 기본 보안만 유지

  • 버킷 권한 탭
    보안 리소스·정책 — 개별 권한·정책 편집이 가능하지만 잘못 편집하면 공개될 수 있음
  • 실습 범위
    Lambda 실행 역할에 S3 정책을 붙이는 것까지 — 객체 소유권·관리·지표·메타데이터는 건드리지 않음
  • CORS
    권한 탭 맨 아래 CORS(Cross-Origin Resource Sharing)는 27장에서 설정, 그 전에는 손대지 않음

실행 역할에 정책 연결

  1. Lambda → 함수 → 구성 → 권한 → 실행 역할(예: mz-apink-role-…) 클릭 → IAM 화면
  2. 권한 추가 → 정책 연결 → 검색창에 Amazon S3 입력
  3. 정책 선택 — 연습 기본은 ReadOnly(업로드 차단), 익숙해지면 FullAccess. 이번 실습은 FullAccess 연결
  4. 실행 결과 — 역할 링크에서 연결된 정책 확인, 권한 새로고침 시 function·lambda 등 항목이 추가됨
정책범위메모
AmazonS3ReadOnlyAccessS3 읽기 전용 — 업로드·삭제 불가연습 기본으로 쓰는 최소 권한
AmazonS3FullAccessS3 스토리지에 모든 접근이번 실습에서 연결 — 폴더 생성·업로드가 모두 필요
Files client access 계열파일 시스템 형태로 붙는 액세스 포인트용이번 실습에서는 선택하지 않음
  • 문제 발생 시
    정책을 분리(해제)해 원인 범위를 좁힘 — 권한 때문에 실패하는지 확인하는 첫 단계
  • 모니터링 탭
    호출 수, 오류, 성공률, 비동기 실행 지표 표시 — 연결 후 함수가 실제로 불리는지 확인하는 창
FullAccess의 무게 — FullAccess를 붙이면 그 Lambda가 S3의 모든 버킷에 접근 가능. 실습은 편의를 위해 쓰지만 운영에서는 버킷·동작을 지정한 최소 권한 정책으로 좁히고, 이상이 보이면 즉시 정책 분리

  • 화면
    버킷 클릭 → 객체 탭 — 범용 버킷 사용, 액세스 포인트 등 다른 탭은 사용 안 함
  • 폴더 만들기
    이름 upload, 암호화 키는 지정 안 함
  • S3의 폴더
    S3는 폴더가 없는 평면 객체 스토어 — “폴더”는 키 접두사(upload/)를 폴더처럼 보여 주는 것. 콘솔의 폴더 만들기는 이름이 /로 끝나는 빈 객체를 만듦
  • 업로드
    upload 폴더 → 업로드 → 파일 끌어다 놓기(파일·폴더 추가, 제거 가능) → 업로드 — 대상 경로를 반드시 확인
  • 실행 결과
    바탕화면 user.jpg(image/jpeg, 1,112.6KB) → s3://mz-apink-s3-…/upload/
  • 삭제
    객체 선택 → 삭제 → 영구 삭제 확인문 입력 → 개체 삭제
  • 탭 분리
    S3 탭과 Lambda 탭을 따로 열어 두고 혼동하지 않기 — 비슷한 화면에서 엉뚱한 리소스를 지우는 실수가 잦음

# [VS Code · Lambda 프로젝트 mz-apink · fileup.py · lambda_handler 안]
# 위의 import·s3_client 설정·BUCKET_NAME은 그대로 두고 핸들러만 교체
def lambda_handler(event, context):
    try:
        if event is None:                       # 이벤트가 없으면 빈 dict
            event = {}
        params = event.get('queryStringParameters', {})   # 쿼리 스트링 파라미터
        if params is None:                      # 파라미터가 없으면 빈 dict
            params = {}

        file_name = params.get('file_name', 'default.txt')   # 이름 없이 호출되면 default.txt
        file_type = params.get('file_type', 'application/octet-stream')   # 기본 = 순수 바이너리

        s3url = s3_client.generate_presigned_url(   # 만료 시간이 있는 업로드 URL 생성
            'put_object',                       # PUT으로 전송 (POST object 아님)
            Params = {                          # 대문자 시작 (함수 인자)
                'Bucket' : BUCKET_NAME,
                'Key' : f"upload/{file_name}",  # upload 폴더 + 프론트가 보낸 파일 이름
                'ContentType' : file_type
            },
            ExpiresIn = 300                     # 단위 초, 300 = 5분
        )
        return {
            "statusCode": 200,
            "headers": {
                "Access-Control-Allow-Origin": "*",     # CORS 허용 (27장)
                "Content-Type": "application/json"
            },
            "body": json.dumps({"upload_url": s3url, "key": file_name})   # 업로드 URL 반환
        }
    except Exception as e:
        return {
            'statuscode' : 500,                 # 소문자 표기 — 정상 키는 statusCode
            'body' : json.dumps({'error' : str(e)})     # 에러 위치 파악용 (27장)
        }
  • 파라미터 이름
    file_name·file_type은 HTML을 만들 클로드에게 그대로 알려 줘야 함 — 이름이 어긋나면 업로드가 실패 (27장)
  • 기본값
    외부에서 파라미터 없이 호출하는 경우 대비 — default.txt가 생기면 이름 없이 호출된 것
  • 함수 위치
    generate_presigned_url은 s3_client. 입력 시 나오는 함수 목록 중 하나
  • 만료 시간
    ExpiresIn 단위는 초 — 100 정도면 충분하나(동영상은 더 필요) 너무 짧으면 왕복 시간 때문에 실패할 수 있어 실습은 300
  • 정리
    앞 코드의 print(“디렉토리가 생성 되었습니다”)는 삭제 — 테스트는 생략 가능하고 HTML이 호출하면 동작
presigned URL의 만료 — presigned URL은 항상 만료 시간이 있는 주소이고, 만료는 접근 가능 기간을 제한(보안)하는 장치. 요금은 요청·저장·전송량 기준이므로 시간 제한으로 요금이 결정되는 구조는 아니고, 짧은 만료는 대용량 업로드에서 실패 원인이 됨

form과 enctype

<form name="…" method="post" action="람다 URL" enctype="…"> — method = 전송 방식(POST), action = 보낼 주소(Lambda), enctype = 보낼 수 있는 데이터 종류.

enctype / Content-Type의미
application/x-www-form-urlencoded텍스트만 보낼 때 — form enctype 기본값
multipart/form-data파일 전송 — 단점은 압축·텍스트·영상 등 모든 종류가 다 날아옴이라 제한이 어려움
application/jsonJSON만 전송, 이미지는 전송 못 함 — form enctype이 아니라 fetch/XHR의 Content-Type 헤더 값
application/xml·미디어 타입 등여러 종류가 있음
application/octet-stream순수 바이너리 — 이미지·바이너리 파일만, ASCII 파일은 안 옴. 이번 실습에서 사용, FTP 전송 타입 binary/ASCII 중 binary에 해당

HTML form의 enctype으로 지정할 수 있는 값은 urlencoded·multipart/form-data·text/plain 3가지뿐 — application/octet-stream·application/json은 form enctype이 아니라 fetch/XHR 요청의 Content-Type 헤더로 지정. 알아 두면 좋은 수준이니 한 번 검색해 확인할 것.

enctype — form이 보낼 수 있는 형식은 urlencoded(텍스트)·multipart/form-data(파일)·text/plain 세 가지. octet-stream은 fetch의 Content-Type 헤더로 지정하는 순수 바이너리 타입이고, 이번 실습은 이미지 업로드라 이 타입을 씀

AllowedMethodsPUT, POST, GET, HEADPUT = presigned URL 업로드, POST = POST로 만든 HTML 대비, GET·HEAD = 조회·확인
AllowedOrigins*요청하는 웹 페이지의 출처(스킴+도메인+포트) 목록 — 실서비스에서는 * 금지
ExposeHeadersETag고유 식별자 — 파일이 맞는지·변경됐는지(무결성) 확인

실행 결과 — 권한 탭 맨 아래에 CORS 규칙 표시. AllowedOrigins는 서버 IP가 아니라 요청하는 웹 페이지의 출처(예 http://127.0.0.1:5500)이고, AllowedHeaders도 IP가 아니라 허용할 요청 헤더 이름 목록 — 실제 서비스에서 API·버킷을 *로 다 열어 두면 안 됨.

Lambda 응답 헤더에 CORS 추가

HTML이 요구한 Access-Control-Allow-Origin을 fileup.py 응답의 headers에 추가 (24장 코드) — 요구가 없으면 생략 가능.

에러 디버깅 — HTML과 Lambda 이름 맞추기

  • 증상
    CORS를 해결해도 PUT 쪽 에러 — HTML은 파라미터를 filename, Lambda는 file_name으로 사용해 이름 불일치
  • 해결
    F12에서 해당 요청을 복사해 클로드에 붙여넣고 해당 람다 소스에 맞는 fileupload.html로 수정하세요 요청
  • 결과
    클로드가 API 주소는 그대로 두고 경로·파라미터 이름을 Lambda에 맞게 수정
  • 메서드
    GET으로 보내던 요청은 fetch(url, { method: "PUT" })로 PUT 변경, 파일 이름 변수는 file_name으로 통일
  • 이름 통일
    코드 전체에서 변수·파라미터 이름 통일(url → s3 url, 파일 이름 → file_name)
  • Content-Type
    클로드가 Content-Type(application/octet-stream 등)을 빠뜨리는 경우가 있으니 확인
  • 500 응답
    Lambda except는 print만 두지 말고 500 + body에 str(e)를 반환 — 어디가 실패했는지 파악하려면 필수

API Gateway CORS 구성

원인 — S3 CORS·Lambda 헤더를 설정해도 API Gateway에서 승인되지 않아 뒷단(Lambda) 에러가 남. 세부 정보는 상태 활성화됨, 스테이지 default, 권한 부여 없음, API 유형 HTTP.

  1. API Gateway → mz-apink-API → 왼쪽 메뉴 CORS → CORS 구성
  2. Access-Control-Allow-Origin에 * 입력 → 추가 → 저장
  3. 나머지 칸(Allow-Headers, Allow-Methods, Expose-Headers, Max-Age, Allow-Credentials)은 건드리지 않음
  4. 실행 결과 — 파일 선택 → 업로드 성공 → S3 upload/ 폴더에 이미지(user.jpg 등) 저장

API에 CORS를 구성하면 API Gateway는 백엔드 통합(Lambda)이 반환한 CORS 헤더를 무시함(화면 안내) — Lambda 응답의 Access-Control-Allow-Origin이 필요한 것은 Gateway CORS를 구성하지 않았을 때의 이야기.

데이터 흐름 정리

  1. 브라우저(HTML, Live Server)가 API Gateway 엔드포인트로 file_name·file_type을 쿼리 스트링으로 보내 Lambda 호출
  2. Lambda(fileup.py)가 presigned URL(PUT, 만료 300초) 생성 → {"upload_url", "key"} 반환
  3. HTML이 받은 presigned URL로 PUT 요청을 보내 S3 upload/ 폴더에 파일 업로드
  4. 브라우저가 S3·API Gateway를 호출하므로 CORS(S3 CORS 규칙 + API Gateway CORS + Lambda 응답 헤더) 허용이 필요
CORS는 세 곳 — S3 버킷 CORS JSON(PUT·POST·GET·HEAD, ExposeHeaders ETag), API Gateway CORS(Allow-Origin), Lambda 응답 헤더(Access-Control-Allow-Origin). 하나만 빠져도 preflight에서 막히고, API Gateway까지 전부 풀면 보안이 무너짐. * 전체 허용은 연습용 — 실서비스는 출처를 좁혀 지정
이름·메서드 일치 — file_name(HTML·Lambda 동일), HTTP 메서드 PUT, Content-Type 세 가지가 어긋나면 업로드 실패. 에러가 나면 F12 네트워크 탭에서 요청을 복사해 Lambda 규칙에 맞게 HTML을 고치라고 지시하고, Lambda except는 500과 str(e)를 함께 반환
