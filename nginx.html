nginx 통합 학습노트

/etc/nginx/nginx.conf

nginx 환경설정은 /etc/nginx/nginx.conf, 아파치(/etc/httpd)와 혼동 주의. 주요 라인은 6번 worker_processes, 14번 worker_connections, 37~41번 server·listen·root. 수정 후 systemctl restart nginx 필수, root는 server 블록에 하나 (2장)

모듈 스트림 → nginx*

dnf module enable nginx:1.24로 스트림을 고른 뒤 dnf install nginx*로 설치 → 이미지·XML 라이브러리까지 총 44개. 기본 dnf install nginx는 최소 패키지만 들어 나중에 오작동 (1장)

proxy_pass 80 → 8080

nginx 프록시가 80번 요청을 WAS(localhost:8080)로 넘겨 :8080을 숨김. X-Real-IP·X-Forwarded-For·Host 헤더로 클라이언트 IP·도메인 전달, 설정 후 재시작 (6장)

설정위치의미값

worker_connections14번 줄워커 프로세스 1개가 동시에 처리하는 최대 접속(커넥션) 수기본 1024
# [호스트 리눅스 · /etc/nginx/nginx.conf 파일 안 · root]
# 사용할 워커 프로세스 수 — auto는 CPU 코어 수를 자동 감지해 그 수만큼 생성
worker_processes auto;
# 코어가 많아도 워커를 1개만 쓰려면 auto 대신 1 (이 서버는 2코어라 auto와 2가 비슷)
worker_processes 1;

events {
    # 워커 1개가 동시에 열 수 있는 최대 연결 수(프록시 연결 포함) — 접속자가 많으면 메모리를 보고 2048 등으로 올림
    worker_connections 1024;
}

worker_connections

항목내용주의·이유
늘릴 때접속자가 많으면 1024 → 2048 …로 늘림한도에 도달하면 새 연결을 받지 못함
늘리기 전 확인서버 메모리 할당량을 보고 올릴 것마구 늘리면 안 됨
값의 의미워커 프로세스 1개가 여는 최대 동시 연결 수(프록시 연결 포함)문서 기본값 512, 배포판 설정 파일은 1024
한도 도달새 연결을 받지 못하는 상태1024명이 동시에 접속한다고 서버가 죽는 것은 아님

worker_processes

항목내용주의·이유
autoCPU 코어 수를 자동 감지해 워커 프로세스 수를 정함접속할 때마다 코어를 모두 사용하는 값이 아님
숫자워커 프로세스의 개수 — 예: 24코어 서버에 4 → 워커 4개특정 코어를 지정하는 값이 아님
코어가 많은 서버24코어처럼 코어가 많아도 auto를 잡지 않는 운용(강사 경험)코어가 한꺼번에 몰렸다 들어오는 구조라 손실이라는 설명은 강사 경험. nginx 문서는 코어 수로 설정하거나 auto로 두는 것을 좋은 출발점으로 권함
이 서버2코어뿐이라 auto든 2든 비슷, 1개만 쓰려면 worker_processes 1;분산 서버·Spark에서 다시 나오는 개념

user nginx;

건드리지 말 것 — nginx 설치 시 nginx 사용자가 자동 생성됨 (PostgreSQL 설치 시 postgres 사용자가 생기는 것과 같은 원리)

워커 — auto는 코어 수를 세어 워커 프로세스를 만드는 값(접속마다 코어 사용 아님), 숫자는 워커 개수(코어 지정 아님). worker_connections는 워커당 최대 동시 연결 수, 한도 도달 시 새 연결 거부(서버 다운 아님) → 메모리 보고 조정

업로드 후 root 소유로 이동

항목내용주의·이유

왜 옮기는가업로드한 파일은 apink 소유라 수정 가능해 위험 → root가 관리하도록 이동 (exit 후 root)에러 페이지는 서버 담당자 영역
# [호스트 리눅스 · root]
# 웹 디렉토리 관리용 디렉토리(root) — html·cgi-bin 이미 있음
cd /var/www
# apink 홈의 원본을 /var/www로 이동 (복사는 cp)

# 이동 후 소유자 확인 (apink)
ls -l
# 소유자:그룹을 root로 변경 (chown = owner 변경) → root만 수정 가능

# root root 확인

항목내용주의·이유
위치html 안이 아니라 /var/www 바로 아래에 둬도 됨어디에 올리느냐(경로)에 따라 설정이 달라지므로 위치를 먼저 정할 것
mv 끝 /대상(/var/www)이 이미 있는 디렉토리면 끝 / 유무와 관계없이 그 안으로 이동대상이 없을 때만 그 이름으로 바뀜 (linux.html 6장)
결과root root가 되면 root 외에는 수정 불가, apink는 접근 안 됨웹 서버는 read 권한으로 읽음

nginx에 연결 (47·48번 줄)

# [호스트 리눅스 · /etc/nginx/nginx.conf 파일 안 · root]
# 404가 나면 이 HTML을 보여 줌 — 경로는 / + 파일명
error_page 404 /404.html;
# 파일명은 location에서 지정
location = /404.html {
    # 에러 페이지가 실제 있는 디렉토리
    root /var/www;
    # 외부에서 /404.html 직접 접근 차단
    internal;
}
항목내용결과·주의
실행 순서저장 → systemctl restart nginx → 없는 페이지 호출만든 404 화면이 모든 사용자에게 뜨면 정상
직접 접근/404.html을 직접 쳐서 들어오면 404로 뜸해커의 직접 접근 차단 (internal의 역할)
실수 — 전체 경로error_page 줄에 /var/www/404.html처럼 전체 경로를 넣는 방식올바르지 않음 — URI(/404.html)로 적고 실제 경로는 location의 root로
실수 — internal 없음location 안에 root만 넣은 초안에서는 404 화면이 안 뜸에러 페이지를 일반 사용자 root(/home/apink/www)에서 찾기 때문
일반 사용자 페이지와 차이일반 사용자 404 페이지는 root만 쓰지만, root가 관리하는 HTML은 location 안에 root + internal;파일 소유자·접근 범위가 다르기 때문

다른 코드 추가 (예: 302)

error_page … + location = … 블록(예: 49~54번 줄)을 그대로 복사해 위에 붙여넣고 코드 번호와 파일명만 바꿈 (코드별로 한 벌씩)

# [호스트 리눅스 · /etc/nginx/nginx.conf 파일 안 · root]
# 302가 나면 안내 페이지 출력
error_page 302 /302.html;
location = /302.html {
    # 에러 코드별 HTML을 두는 기본 디렉토리
    root /var/www;
    # 직접 접근 차단
    internal;
}
항목내용주의·이유
결과302 오류가 나면 이 페이지("프로그램 오류" 안내)가 뜸홈으로 돌아가는 버튼 등은 AI가 넣어 준 것

아파치와 비교아파치도 환경설정에 에러 페이지(404 출력) 설정이 있고, nginx는 이 설정이 conf 안에 같이 붙어 있음httpd.html 4장

가장 어려운 파트 — 오타 주의, 인프라 담당자 필수 지식

목표

항목내용주의·이유
목표:8080 없이 IP(도메인)만 쳐도 nginx 화면이 아니라 WAS(Tomcat) 화면이 뜨게 함 (80 → 8080)개발자가 "도메인 치고 8080 치면 이상하다, 연결해 달라"고 요청하는 경우에 대응
다른 방법WAS를 80으로 돌리는 방법도 있으나 일이 커짐 → 웹 서버(nginx)에 proxy 설정WAS 포트는 그대로 두고 웹 서버가 앞에서 중계
난이도이 작업 중 가장 어려운 파트, 오타 주의, 인프라 담당자는 꼭 알아야 함WAS 서버를 많이 쓰기 때문
PHPPHP 개발자는 80번으로 바로 서비스함WAS 프록시가 필요한 경우와 구분
아파치아파치도 같은 프록시 설정 기능이 있음웹 서버 공통 기능

설정 (root)

실행 순서: WAS 정지 → vi /etc/nginx/nginx.conf → 37번 server 블록 수정 → 저장 → systemctl restart nginx

# [호스트 리눅스 · /etc/nginx/nginx.conf 파일 안 · root]
server {
    # 38번 — 80번 포트로 요청 받음
    listen 80;
    # 39번 — IPv6용
    listen [::]:80;
    # 웹서비스용 root는 주석(41번), Tomcat 경로를 root로 — 탭·스페이스는 상관없음
    #root /home/apink/www;
    root /home/apink/tomcat/;

    location / {
        # WAS 주소·포트 — WAS 시작 포트와 같아야 함(8081로 띄웠으면 8081), localhost 또는 서버 IP
        proxy_pass http://localhost:8080;
        # 실제 클라이언트 IP를 백엔드로 전달
        proxy_set_header X-Real-IP $remote_addr;
        # 클라이언트 IP를 이어 붙여 전달
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        # 도메인·가상 호스트 정보 전달 — 주소 끝에 :8080이 붙지 않게 함
        proxy_set_header Host $http_host;
    }
}
항목내용주의·이유
포트 일치proxy_pass 포트는 WAS 시작 포트와 같아야 함WAS 포트를 8081로 띄웠으면 8081
주소localhost 또는 서버 IP127.0.0.0 같은 주소는 오류
문법각 줄 끝 ; 필수, 대소문자 구분, FORWARDED 철자 주의, 전부 직접 타이핑복사·붙여넣기에서 숨은 문자·오타가 섞이기 쉬움
X-Real-IP받은 클라이언트 IP는 백엔드 개발자에게 전달됨개발자가 접속자 IP를 로그에 남길 수 있음
Host주소가 apple.com에서 끝나고 :8080이 붙지 않음$host로 써도 크게 문제없음

프록시 개념

항목내용주의·이유
정의프록시 = 웹에서 WAS로 연결하는 중개(중계) 서버클라우드에도 proxy server가 따로 있음
방향웹서버 앞에서 요청을 받아 뒤의 WAS로 넘기는 이 구성은 리버스 프록시, 포워드 프록시는 클라이언트를 대신하는 쪽둘을 같은 것으로 설명하면 면접에서 틀림
흐름클라이언트 요청은 WAS가 아니라 웹이 먼저 받음(nginx·아파치 동일) → 프록시가 80을 8080으로 넘겨 WAS 쪽 웹을 출력 → 8080을 숨기는 역할WAS 포트를 외부에 노출하지 않는 것이 목적
담당 범위서버 담당자는 location까지만 걸면 끝, Tomcat 경로 뒤 디렉토리는 개발자 몫
X-Real-IP 확인브라우저 개발자 도구(Network·Response)나 크롬 확장으로 볼 수 있으나 인프라 담당자는 볼 필요 없음개발자가 값을 요청하면 전달만 되고 있는지 확인
X-Forwarded-For헤더 이름이며 포워드 프록시를 뜻하지 않음. 프록시 뒤 백엔드에 원래 클라이언트 IP를 알려 주는 용도접근한 서버를 숨기는 용도가 아님
다크웹Tor는 여러 릴레이를 거치는 계층 암호화 경로단일 프록시로 위치를 숨기는 구조가 아님
심화더 자세한 내용은 클라우드 때 (VirtualBox만으로는 한계)
프록시 — 80을 8080으로 넘겨 :8080을 숨김. 클라이언트 요청은 WAS가 아니라 웹이 먼저 받음. proxy_pass 포트는 WAS 포트와 일치, 설정 후 restart, server 블록의 root는 하나

  • 이미 있는 경우
    앞서 인스턴스를 만들 때 HTTP 트래픽 허용을 체크해 80 규칙이 있으면 새로 만들 필요 없음

  • 정리
    확인을 마치면 DBeaver는 닫음
LISTEN과 방화벽 — 서버 안에서 80이 LISTEN이어도 GCP 네트워크 방화벽에 규칙이 없으면 밖에서 못 들어옴. netstat과 방화벽 규칙 목록을 모두 확인

웹 루트를 사용자 홈으로 — 403과 홈 권한

한눈에 보기 — root 변경 → 403 → public 생성 → 홈 755 → 재시작

① root 변경

/home/megazone/public

② 403

접근 금지 — 홈 권한

③ public

su megazone → mkdir public

④ 755 → 재시작

열림

403은 파일이 아니라 경로 권한 문제 — nginx가 홈 디렉터리까지 들어갈 수 있어야 함

root 경로 변경

앞서 만든 사용자 megazone의 홈(/home/megazone) 아래 public(VS Code에서 만든 폴더)을 웹 루트로 사용.

# [GCP VM 호스트 리눅스 · root]
# :set number 후 41번 줄 root 수정
vi /etc/nginx/nginx.conf
# 설정 변경 후 재시작
systemctl restart nginx
# [GCP VM 호스트 리눅스 · /etc/nginx/nginx.conf 파일 안 · root]
# 41번 줄 — 기존 /usr/share/nginx/html(데모 화면 경로)을 교체
root /home/megazone/public;
  • 결과
    데모 화면이 사라지고 403(접근 금지) 표시

사용자 쪽 public 디렉터리

# [GCP VM 호스트 리눅스 · root]
# 일반 사용자로 전환 — 프롬프트가 [megazone@… ~]$ 로 바뀜
su megazone
# 홈에 public 생성 (별도 핸들링 필요 없음)
mkdir public
  • PuTTY
    여기까지 하고 PuTTY 세션은 그대로 둠

403 해결 — 홈 디렉터리 권한

403 원인은 홈 디렉터리 권한. /home에서 ls -al 했을 때 megazone 디렉터리가 drwx------(700대)이면 웹이 안 열림.

# [GCP VM 호스트 리눅스 · root]
# /home 에서 megazone 디렉터리 자체를 755로
chmod 755 megazone
# root로 복귀
exit
# nginx 재시작
systemctl restart nginx
  • 안쪽 권한
    megazone 안의 public은 755만 잡혀 있으면 되고, 그 안의 index.html 등은 그대로 둠
  • 자세한 실습
    웹 루트 변경 기본: 이 파일 4장 / 권한·ls -al 표기: linux.html 7장
403은 경로 권한 — index.html이 있어도 nginx가 /home/{사용자}까지 들어갈 수 없으면 403. 홈이 drwx------이면 chmod 755로 실행 권한을 열어 줌

도메인 연결 — DNS 조회와 접속 확인

한눈에 보기 — 도메인 생성 → 대상 IP → 전파 대기 → 조회 → 브라우저

① 도메인

apink.kbsn.or.kr 생성

② 대상 IP

VM 외부 IP 8.230.15.154

③ 전파 대기

IP가 바뀌어 반영되는 시간

④ 조회

nslookup · ping

⑤ 접속

브라우저·SSH 모두 도메인

IP만 알면 도메인을 만들어 붙일 수 있음 — 도메인이 IP를 대신 기억하는 이름표

개념

항목내용주의·이유
전제도메인을 따로 잡지 않고 IP만 알면 도메인을 생성해 바로 연결서버 IP가 정해져 있으면 도메인 쪽에서 대상 IP만 지정
DNS 서비스Cloud DNS(AWS는 Route 53)는 도메인의 권한 DNS를 호스팅하는 정식 서비스레지스트라 DNS에서 IP를 연결하는 방식도 가능 — 쓰는 쪽이 정답은 아니고 목적에 따라 선택 (Cloud Domains 개요)
이번 범위자세한 방법은 나중에 연결할 때 안내방법 영상 없이 결과만 시연

연결 시연

순서작업결과
1도메인 서비스에서 apink.kbsn.or.kr 생성, 대상 IP = VM 외부 IP(8.230.15.154)도메인 등록 접수
2도메인 등록이 끝나기를 대기IP가 바뀌어 반영되는 시간이 걸림
3nslookup으로 도메인 → IP 확인, ping으로 응답 확인잘 잡힘
4브라우저에 도메인을 입력같은 사이트가 뜸 (그 전엔 IP로 접속)
5SSH(PuTTY)도 도메인으로 접속이름만 바뀌고 대상은 같은 서버
# [윈도우 · cmd]
# 도메인 → IP 확인 — 등록한 외부 IP가 나오면 전파 완료
nslookup <도메인>
# IP 응답 확인 — 응답이 오면 대상 서버까지 연결
ping <IP>
  • 다른 수강생
    다른 수강생의 VM IP로도 같은 방식으로 도메인을 등록 → 그 도메인으로 접속하면 해당 사람의 사이트(오늘의 날씨 페이지)가 뜸 → 각자 도메인을 쓸 수 있고 모바일에서도 사용 가능
  • 자세한 실습
    이 파일 7장 (웹 서비스 공개) / nslookup·고정 IP·네트워크 점검: linux.html 2장
DNS 전파 — 도메인 등록 직후에는 응답이 없거나 이전 값이 나옴. nslookup에서 등록한 IP가 확인된 뒤에 브라우저·SSH 접속
