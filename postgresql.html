PostgreSQL 통합 학습노트

설치 → 스트림 → initdb

소스는 make·make install, RPM은 dnf module enable postgresql:16으로 스트림을 바꾼 뒤 postgresql-server 설치 (1장). postgresql-setup --initdb 뒤 5432 LISTEN 확인, 실패 로그는 /var/lib/pgsql/initdb_postgresql.log (2장). 접속은 pg_hba.conf 위에서부터 첫 일치 규칙 — trust는 비밀번호 검증 없음, md5/scram-sha-256으로 (3장)

pgdata 볼륨 · restart

데이터 경로 /var/lib/postgresql/data를 이름 있는 볼륨 pgdata에 연결 → 컨테이너를 바꿔도 데이터 유지 (11장). 접속은 pg_hba.conf의 0.0.0.0/0 md5 줄을 열어야 원격·컨테이너 접속이 통과 (12장). 편집기가 없는 컨테이너는 docker cp로 꺼내 수정 → docker restart, max_connections 10 (13장)

백업·복구 · search_path

pg_dump -f sample.sql → drop database → create database·owner → 관리자는 -d apink -f sample.sql, -d를 빼면 기본 DB로 복구 (9장). 스키마 우선순위는 alter user … set search_path — 새 세션부터 적용 (8장). DBeaver는 localhost가 아니라 서버 IP, Test Connection에서 Connected 확인 (10장)

왜 PostgreSQL 인가

항목내용주의·이유
선택 이유가장 가볍고 켜고 끄기가 빠름실습 PC로 Oracle을 올리면 시작에 밥 먹고 와야 할 정도라 진행 불가
Oracle 설치oracle-database-ee-21c 같은 RPM 패키지를 제공하고 preinstall RPM을 먼저 설치100% 소스 설치가 아님 — 환경이 MySQL·PostgreSQL과 크게 달라 별도 학습 필요
Oracle 특징설치가 끝나면 설치 경로를 알려 주고, 그 경로를 기준으로 보안을 잡음DB마다 설정 파일 위치가 다르다는 점이 이후 경로 학습으로 이어짐
특징내용주의·이유
용도대규모 데이터 분석, 복잡한 로직 형태의 데이터 관리에 강함단순 조회보다 분석·집계가 많은 시스템에 맞음
벡터 DBpgvector (PG + vector) — PostgreSQL에 CREATE EXTENSION vector로 설치하는 오픈소스 벡터 검색 확장, AI 용도별도 DB 제품이 아니라 확장 — 임베딩 저장·유사도 검색에 사용
경량가볍고 쉽게 사용·관리 — MySQL·MariaDB처럼 무거운 데몬이 아님실습 PC에도 부담이 없어 켜고 끄기가 빠름
SQL 표준SQL 표준을 엄격히 따르는 편 (표준 문서를 따로 찾아볼 것)DB를 바꿔도 SQL이 덜 깨지는 이유
고급 데이터 타입JSON, XML, JSONB, Array, GIS, Byte(bytea) 지원MySQL도 네이티브 JSON·공간 타입·BLOB을 지원하지만 JSONB·배열·GIS 함수·확장 생태계는 PostgreSQL이 넓음
칠판 요약PostgreSQL → pgvector(AI) / 데이터 타입: JSON·XML·JSONB → Array, GIS → 데이터데이터 형태별로 어느 DB를 고를지 판단하는 근거

고급 데이터 타입

타입내용주의·이유
JSONAI와 통신하는 프로토콜은 전부 JSON 형태(배열)API 요청·응답을 가공 없이 저장하는 형태
XMLJSON과 함께 지원오래된 연계·공공 데이터에서 아직 쓰이는 형식
JSONBJSON의 바이너리 저장 형태키 조회·인덱스에 유리, 입력할 때 키 순서·공백이 정규화됨
Array배열 타입 — 한 컬럼에 여러 값인프라 담당자는 배열 구조를 반드시 알아야 함: compose·yml도 배열 구조라 모르면 설정 파일이 무너짐
GIS지오메트리(geometry) — 지리정보 시스템, 비정형 특수 데이터 처리에 적합MySQL도 OpenGIS 기반 공간 데이터 타입·함수·공간 인덱스를 지원
Byte바이트 단위 저장 — PostgreSQL의 이진 타입명 bytea (칠판에 CLOB·BLOB도 함께)이미지·영상을 DB에 넣는 방식의 근거 (vectordb.html 5장)

클라이언트 설치와 기본 버전

# [호스트 리눅스 · root]
# 클라이언트 패키지만 설치 — 기본 스트림이 13이라 개발자가 요청한 버전보다 낮음
dnf install postgresql
항목내용주의·이유
기본 결과버전 13이 설치됨지금은 그냥 설치하면 안 되는 상태 — 13은 너무 낮음(요청 버전보다 낮아 이 과정에서 쓰지 않음)
개발자 요구특정 버전(예: 16)을 지정버전을 맞추지 않으면 이후 애플리케이션 연결에서 문제
선택지15·16·18 중에서 고름이 과정은 16으로 진행 (psql 16.8)

모듈 스트림으로 버전 맞추기

# [호스트 리눅스 · root]
# 설치 가능한 스트림 목록 — 15·16·18, 17은 없고 [d]가 기본(13)
dnf module list postgresql
# 설치 대상 스트림을 16으로 변경 (설치가 아니라 설치 환경 변경, 확인 질문에 y)
dnf module enable postgresql:16
# 바뀐 스트림 기준으로 설치 → 16.x
dnf install postgresql
# 모듈 설정 초기화 — 확인 질문에 y, 이후 install하면 다시 13
dnf module reset postgresql
항목내용주의·이유
enable의 의미설치가 아니라 설치 환경(스트림)이 바뀌는 동작enable만 하고 install을 하지 않으면 패키지는 그대로
reset의 결과모듈 설정 초기화 후 install하면 다시 13이 설치됨버전을 되돌릴 때 사용
화면 힌트list 출력에 enable을 넣으라는 안내가 나옴기본 스트림이 아닌 버전은 enable이 필요하다는 뜻
실수 방지확인 단계에서 n으로 중단이미 설치했다면 rpm -qa | grep postgres로 찾아 삭제 (linux.html 13장)
콜론 표기postgresql:16은 컨테이너 이미지의 이름:버전과 같은 구조모듈 이름과 스트림을 콜론으로 구분
가장 중요한 것버전 맞추기module을 모르면 구글에서 rpm 파일을 찾아 헤매게 됨
다른 계열우분투(APT)는 명령이 완전히 다름배포판별 패키지 관리 차이 (linux.html 13장)
list가 비어 보이는 사례환경에 따라 dnf module list에 아무것도 안 뜨는 경우가 있었음원인 미확인 — 저장소 설정과 dnf repolist를 함께 확인

둘 다 필요클라이언트 패키지 + 서버 패키지MySQL도 서버 패키지가 따로 설치됨 — rpm -qa | grep mysql로 확인 가능

가동 시점아직 start하지 않음초기화·환경설정 방식이 MySQL과 달라 순서를 지켜야 함 (2~3장)
버전 맞추기 — dnf module enable postgresql:16은 설치가 아니라 스트림 전환. 클라이언트와 postgresql-server를 둘 다 설치하고, 초기화 전에는 가동하지 않음

줄내용설명
113local all all peer유닉스 도메인 소켓(로컬 접속)용 — peer 인증 실패의 원인 줄

  • 컬럼 의미
    TYPE(local·host) · DATABASE · USER · ADDRESS · METHOD 다섯 항목
  • local과 host
    local = 서버 안에 들어가서 하는 접속(유닉스 소켓), host = IP로 들어오는 외부 접속(로컬호스트 아님) — 두 줄이 따로 존재
  • peer가 막는 지점
    PuTTY의 psql -U postgres는 113행 local 줄을 탐 — METHOD가 peer면 OS 사용자명과 DB 사용자명이 달라 인증 실패, md5(비밀번호 인증)로 바꿔야 접속 가능
  • peer의 정체
    peer는 암호화 방식이 아니라 OS 사용자명과 DB 사용자명의 일치를 확인하는 인증 방식(로컬 전용), md5는 MD5 또는 SCRAM-SHA-256 비밀번호 인증
  • DBeaver는 116행
    외부 도구는 호스트 줄(116행)을 풀어야 함 — 안 풀면 같은 인증 실패 에러가 계속 뜸
  • MySQL과의 차이
    MySQL도 'user'@'host' 계정 단위로 접속 가능한 위치를 따짐 — PostgreSQL은 local·host·IPv4·IPv6 규칙을 파일 하나에서 관리
  • 수정 후
    환경설정을 바꾸면 무조건 재시작 — 재시작 뒤 방향키 ↑로 직전 psql -U postgres를 불러 다시 실행

인증 방식 선택

방식동작주의·이유
identOS 사용자 이름을 DB 사용자에 대응시켜 인증pg_ident.conf 매핑과 다른 서버가 있어야 쓰는 방식이라 지금은 쓰지 않음
md5비밀번호를 md5로 검증이 과정의 기본 베이스 — 지금은 이 형태만 사용
scram-sha-256SCRAM(RFC 7677) 기반 비밀번호 인증PostgreSQL 비밀번호 인증의 선택지는 md5와 scram-sha-256 두 가지 — md5는 더 이상 안전하지 않다고 안내되며 기본값은 이미 scram-sha-256
pg_ident.conf와의 관계비밀번호 인증(md5·scram-sha-256)은 pg_ident.conf와 무관map= 옵션은 ident처럼 외부 사용자 이름을 쓰는 방식에 붙는 것
없는 방식base64는 인증 방식 목록에 없음SHA-1·SHA-2·SHA-3을 고르는 방식도 아니라 SCRAM이 그 역할
pg_ident.conf 내용설명 주석과 PG user name·system user name 매핑 항목이 # 주석으로 들어 있음나중에 맵핑을 쓸 때 사용
peerOS 사용자명과 DB 사용자명의 일치를 확인 — 로컬(유닉스 소켓) 전용PuTTY 로컬 접속의 기본값 — 사용자명이 다르면 인증 실패, 비밀번호는 묻지 않음
trust비밀번호 없이 엔터만 치면 접속비밀번호를 잊었을 때 임시로만 사용 — 남겨 두면 완전히 뚫림
pg_hba 5항목 — TYPE DATABASE USER ADDRESS METHOD. 0.0.0.0/0은 모든 IPv4, md5·scram-sha-256은 비밀번호 인증이며 pg_ident.conf와 무관

데몬 설정 (postgresql.conf)

# [호스트 리눅스 · /var/lib/pgsql/data/postgresql.conf 파일 안 · root]
# 60번 줄: 모든 곳에서 접속 허용 — 기본 'localhost'면 외부 접속 불가
listen_addresses = '*'
# 64번 줄: 서버 TCP 포트. 기본 5432, 다른 서비스가 쓰면 충돌
port = 5432
# 65번 줄: 최대 동시 접속 수. 1이면 한 명만 접속 가능
max_connections = 10
설정기본값·변경값주의·이유
listen_addresses기본 'localhost' → '*'기본값이면 로컬만 접속 가능해 외부·클라우드에서 접속 안 됨 — 반드시 바꿔야 하는 값
port5432 사용이미 쓰는 곳이 있으면 충돌로 기동 불가 → 여기서 변경 (MySQL 포트 변경과 같은 원리)
max_connections기본 100 → 실습 101이면 한 명만 접속하고 다른 접속은 기존이 끊겨야 함 — 서버 메모리에 맞춰 설정, 실습은 10~30이면 충분
메모리·시간 단위units 설정이 함께 있음데이터를 너무 많이 로드하면 문제가 되므로 할당량을 정하는 항목 — 지금은 건드리지 않고 AWS에서 조정
경로 설정hba_file·ident_file·data_directory는 # 주석 상태기본 경로가 아닌 곳에 두었을 때만 #을 풀어 지정 — 지금은 같은 경로라 건드리지 않음
범위모든 줄을 볼 필요 없고 중요한 줄 몇 개만나머지는 DBA가 환경을 바꿀 때 쓰는 항목, 인프라는 기본 베이스만 세팅

임시 trust → 비밀번호 설정 → md5 복귀

단계할 일주의·이유
1local 줄(113행)을 md5 → trust로 변경postgres 비밀번호를 설정한 적이 없어 md5로는 정식 접속 불가 — 호스트 줄은 그대로 둠
2저장 후 재시작설정은 재시작해야 반영
3psql -U postgres로 비밀번호 없이 접속프롬프트 postgres=# 확인
4alter user postgres with password ...로 비밀번호 설정성공하면 ALTER ROLE 메시지
5\q로 psql을 종료하고 local 줄을 trust → md5로 복귀trust를 남기면 비밀번호 없이 누구나 접속 — 실제 운영에서는 임시 방법 자체를 쓰지 않음
6재시작 후 psql -U postgres에 비밀번호 입력정상 접속되면 완료
# [호스트 리눅스 · /var/lib/pgsql/data/pg_hba.conf 파일 안 · root]
# 1) 113행 local 줄: md5 → trust 로 바꿔 비밀번호 없이 들어갈 통로를 임시로 엶 (호스트 줄은 그대로)
local   all   all                  trust
# 5) 비밀번호 설정이 끝나면 같은 줄을 trust → md5 로 되돌림 (trust 방치는 무인증 상태)
local   all   all                  md5
# [호스트 리눅스 · root]
# 2) 수정본을 저장한 뒤 재시작 → 설정 반영
systemctl restart postgresql.service
# 3) 비밀번호 없이 접속 (프롬프트 postgres=#)
psql -U postgres
-- [호스트 리눅스 · psql 프롬프트 · postgres]
-- 4) 비밀번호 설정 — a123456 은 연습값, 성공하면 ALTER ROLE
alter user postgres with password 'a123456';
-- psql 종료 (exit 도 같음)
\q
# [호스트 리눅스 · root]

# 7) 재시작해 설정 반영
systemctl restart postgresql.service
# 8) 비밀번호를 입력해 정상 접속 확인
psql -U postgres

DROP SCHEMA — 객체가 있으면 거부(RESTRICT), 강제 삭제는 CASCADE. CASCADE는 즉시 복구 불가이므로 백업이 있을 때만 최종 수단으로 사용

데이터베이스 삭제 (DROP DATABASE)

단계실행결과·이유
목적백업한 뒤 apink DB를 스키마까지 통째로 삭제 → 복구 실습계정과 DB 이름이 같아 apink가 계정·DB 둘 다를 뜻함
1apink 계정으로 drop database apink;에러 — 자기가 접속한 DB는 삭제 불가 → \q로 나감
2postgres(root)로 drop database apink;에러 — 다른 세션이 DB 사용 중 (DBeaver 연결 세션)
3DBeaver 연결 종료 후 다시 실행바로 삭제됨 — 접속이 하나라도 열려 있으면 삭제 불가
CASCADEDB 삭제에는 적용되지 않음CASCADE는 스키마 삭제에서만 쓰는 옵션
강제 삭제drop database 이름 with (force);로 접속을 종료시키며 삭제삭제는 소유자만 가능 — 접속 중이면 끊거나 FORCE. 소유권을 바꿔 지우는 방식이 아님
결과 확인\l에서 apink DB가 사라짐목록에서 확인하는 것이 삭제 완료의 증거
-- [호스트 리눅스 · psql 프롬프트 · apink]
-- 자기 DB는 자기 세션에서 삭제 불가 → 세션 종료
drop database apink;
\q
-- [호스트 리눅스 · psql 프롬프트 · postgres]
-- 복구 실습을 위해 DB를 스키마까지 통째로 삭제
drop database apink;
-- 접속 세션이 남아 에러가 나면 DBeaver 연결을 끊고 다시 실행하거나 강제 옵션 사용
drop database apink with (force);
-- 목록에서 삭제 확인
\l

옵션의미주의·이유
-U접속 사용자실행 권한의 주체가 바뀜 — apink와 postgres의 결과가 다름
-d복구 대상 DB관리자 복구 시 필수 — 없으면 접속한 기본 DB로 들어감
-f백업 .sql 파일 경로홈의 sample.sql — 다른 경로면 경로까지 지정
-d 생략 조건사용자·DB가 같은 이름이면 생략 가능apink 본인 복구가 이 경우 — 접속 규칙은 7장
실습 전 상태스키마 없이 public만 있는 DB, apink는 접속해 대기복구 후 DBeaver 새로고침으로 sample_schema·데이터 확인
DB가 없어도pg_dump -C로 받은 덤프에는 CREATE DATABASE가 포함되어 DB 없이도 복구 가능기본 평문 덤프는 DB 생성문을 포함하지 않아 대상 DB가 먼저 있어야 함
복구 명령 — 최고 관리자는 psql -U postgres -d DB명 -f 파일처럼 -d를 반드시 지정. 생략하면 접속한 기본 DB(postgres)로 복구됨

항목내용
접속 경로
  • docker exec -it rds_psql /bin/bash로 컨테이너 셸 → psql -U postgres
  • 컨테이너 셸은 처음부터 root → 프롬프트 root@컨테이너ID:/#, psql 프롬프트는 postgres=#
  • 한 줄 접속: docker exec ... env PGPASSWORD=... psql → 비밀번호를 명령행 환경변수에 넣는 건 실습용 (셸 기록·프로세스 환경 노출 주의)
  • 비밀번호를 넣는 방식은 여러 가지 — 로컬 소켓으로 바로 접속하는 방법도 있음
  • SQL 프롬프트 종료 \q 또는 exit
trust의 범위
  • psql -U postgres -W가 비밀번호를 물어도, 컨테이너 안 Unix 소켓 접속이 기본 pg_hba.conf의 trust 규칙에 걸리면 비밀번호를 검증하지 않을 수 있음
  • 모든 외부 TCP 연결이 무인증이라는 뜻은 아님 → 실습 화면의 host all all all scram-sha-256 규칙은 TCP 연결에 비밀번호 인증 요구
규칙 읽는 법위에서부터 먼저 일치하는 항목 적용 — local = Unix socket / host = TCP / 주소 = 허용할 클라이언트 범위. 5항목(TYPE DATABASE USER ADDRESS METHOD) 의미는 3장
주소 범위
  • 0.0.0.0/0 = 모든 IPv4 → 외부 노출 범위가 넓으므로 실습 외에는 접속 원본 제한
  • IPv6 loopback ::1/128도 별도 규칙 → 외부 IPv6로 들어오는 공격이 있어 IPv6 허용 여부도 따로 검토
md5로 바꿔 확인
  • 실습에서 로컬·TCP 규칙의 trust → md5로 바꿔 비밀번호 인증이 실제로 걸리는지 확인 (md5·SHA-256 기반 scram-sha-256·trust의 뜻과 권장 수준: 3장)
  • trust를 남긴 채 그대로 배포하면 안 됨 — 접속 규칙을 좁힐 때까지는 배포 금지
  • 결과로 확인: 틀린 비밀번호 → FATAL: password authentication failed for user "postgres", 맞는 비밀번호 → 접속

DB·사용자 지정

grant 의 반대 방향 — 회수는 from, 부여는 to. 범위는 테이블 < 스키마 < DB 순서로 넓어짐

DB 권한 — GRANT ↔ REVOKE

-- [rds_psql 컨테이너 · psql 프롬프트 · root(postgres)]
-- 준 권한을 회수 — grant 의 반대, 대상은 to 가 아니라 from
revoke all privileges on database mg from mg;
-- 다시 부여 — 순서는 on 데이터베이스명 to 사용자명
grant all privileges on database mg to mg;
-- Access privileges 칸의 변화 확인
\l
-- 접속 자체를 막으려면 CONNECT 권한을 PUBLIC 에서도 회수해야 함
revoke connect on database mg from public;
항목내용주의·이유
방향GRANT 는 to 사용자, REVOKE 는 from 사용자방향을 틀리면 문법 오류 — 순서는 대상(DB명) → 사용자명
확인\l 의 Access privileges 칸 변화변경 전후를 함께 보고 권한이 실제로 바뀌었는지 비교
접속 차단DB 의 CONNECT 권한은 기본으로 PUBLIC(모든 롤)에도 있음mg 에서만 회수하면 접속이 계속될 수 있음 → revoke connect on database mg from public; 까지 필요(GRANT)
MySQL 비교MySQL 도 revoke·grant 구조는 같음권한 테이블·호스트 단위 구분이 추가로 있는 차이(mysql.html 7장)

-- [rds_psql 컨테이너 · psql 프롬프트 · root(postgres)]
-- 스키마 단위로 부여

LIKE와 ILIKE — 대소문자 구분

-- [윈도우 · DBeaver SQL 스크립트 편집기 · mg]

-- [윈도우 · DBeaver SQL 스크립트 편집기 · mg]

CONCAT — 컬럼 합치기

-- [윈도우 · DBeaver SQL 스크립트 편집기 · mg]
-- 두 컬럼 값을 합쳐 한 컬럼으로 출력. as 는 결과 컬럼 별칭
select concat(custormer, id) from travel_payment;
select concat(custormer, id) as nm from travel_payment;
-- concat 안에는 문자열도 넣을 수 있음 — 아이디와 @도메인을 나눠 둔 경우

항목내용주의·이유

-- [윈도우 · DBeaver SQL 스크립트 편집기 · mg]
