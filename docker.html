1. VirtualBox 포트포워딩과 dnf 업데이트

항목내용
설정 위치[윈도우 · VirtualBox] VirtualBox > NAT 네트워크(CloudNetwork) > 포트 포워딩 > IPv4
규칙[윈도우 · VirtualBox] 이름 SSH, TCP, 호스트(내 윈도우 IP를 확인해서 입력, 22) → 게스트(리눅스 IP, 22) → 반드시 '적용'
접속[윈도우 · PuTTY] PuTTY로 윈도우 IP:22 → Accept → 일반 사용자 로그인 → root 전환
첫 작업[호스트 리눅스 · root] 제일 먼저 dnf update (AWS·GCP도 동일, 안 하면 이후 에러 발생)
동시 작업[윈도우 · PuTTY] 업데이트 중 다른 PuTTY 창 작업은 가능. 단 두 번째 dnf는 waiting (pid …)로 대기 → 완료까지 기다림

2. 방화벽·SELinux 영구 정지

# [호스트 리눅스 · root]
dnf install ntsysv        # 미니멀에 없어 먼저 설치
ntsysv                    # firewalld 등 방화벽 해제
setenforce 0              # SELinux 즉시 정지(메시지 없으면 성공). 재부팅하면 원복 → 아래 config 수정이 영구 설정
vi /etc/selinux/config    # :set number 후 22번 라인 SELINUX=enforcing → SELINUX=disabled (재부팅 후 적용)
cat /etc/redhat-release   # OS 이름·버전 확인(컨테이너에서도 동일)
항목내용
방화벽 원칙무조건 정지. AWS·GCP도 서버를 처음 만들면 이 작업부터 해야 통신이 막히지 않음

3. 저장소(repo) 개념과 Docker Engine 설치

항목내용
위치레드햇 계열(Rocky·CentOS·RHEL·Fedora): /etc/yum.repos.d (우분투는 경로·형식이 완전히 다름). 로키 관련 .repo 파일(예: vi 로키.repo)에 name·서버 URL이 기재됨
정체Git 같은 버전관리 시스템이 아니라 패키지 저장소 정보. dnf가 패키지를 받을 서버 URL(.repo 파일의 baseurl 등)이 적혀 있음 (출처: Red Hat 문서 'Managing custom software repositories')
주의기본 .repo 파일을 지우면 업데이트가 전혀 안 됨 → 함부로 삭제 금지
Docker기본 저장소에 없음 → Docker repo 먼저 등록 후 설치. repo 없이 dnf install docker를 하면 패키지를 받아올 곳을 못 찾아 에러
중요도클라우드 환경에서 repo는 필수이고 앞으로 많이 씀 → 필요한 것은 repo를 등록해서 설치
repo 없이 설치하면 — Docker는 기본 저장소에 없어 dnf install docker만 하면 받아올 곳을 못 찾음 → 도커 repo 먼저 등록. /etc/yum.repos.d의 기본 .repo는 지우면 업데이트가 전혀 안 되므로 삭제 금지

# repo 파일 위치로 이동. 여기 .repo 파일(name·서버 URL 기재)이 dnf의 패키지 공급원이며 삭제 금지
cd /etc/yum.repos.d
docker -v                                     # 버전이 뜨면 설치된 것(가동 여부와는 별개), 미설치 시 command not found

ls -a /etc/yum.repos.d                        # 도커 repo 파일 생성 확인

/bin/bash 방식으로 띄웠을 때 생긴 일

  1. /sbin/init으로 실행 → 이미지 안에 INIT 실행 파일이 없다는 에러 → 컨테이너가 Created 상태로만 남고 docker ps에 안 뜸
  2. 우회책으로 /bin/bash로 실행 → PID 1 = bash (프롬프트가 bash-5.1#로 뜸: minimal 이미지의 정상 셸 프롬프트이며 패키지가 없을 뿐, '안전모드'는 Docker 개념이 아님 — 출처: forums.docker.com)
  3. systemctl start sshd(service 명령도 마찬가지) 실행 시 오류
    • System has not been booted with systemd as init system (PID 1). Can't operate.
    • Failed to connect to bus: Host is down
  4. 결국 /usr/sbin/sshd를 직접 실행하고, ps 후 kill해야 하는 불편 (데몬을 전부 직접 켜고 꺼야 하고 자동 시작도 안 됨)

2단계: Dockerfile 작성 및 새 이미지 빌드

# [호스트 리눅스 · root]
# 작업 폴더 (이름 자유). Dockerfile 작성·빌드는 root에서만
mkdir /root/docker && cd /root/docker
# Dockerfile = shell 스크립트 비슷한 형태로 원하는 이미지를 정의하는 파일 (기본 이미지를 분해해 재구성)
# 파일명은 Dockerfile 고정 (docker build가 이 이름을 찾음)
vi Dockerfile

# [호스트 리눅스 · /root/docker/Dockerfile 파일 안]
# 베이스 이미지 지정. docker images의 이름:버전을 한 글자도 틀리지 않게 그대로 씀
FROM moongeun/centos9:latest
# 로키 빌드 시 위 FROM 줄 앞에 # 주석 후 아래 줄 사용
# FROM rockylinux:9
# 빌드 중 실행할 명령. 인터넷 미러 서버(공식 저장소 복사본)에서 패키지를 받아 옴
# -y: 설치 질문에 자동 승낙 / systemd: systemctl 사용을 위한 핵심 데몬 / dnf clean all: 설치 후 캐시 정리 (&&로 같은 줄에 이어 씀)
RUN dnf install -y systemd && dnf clean all
# 컨테이너 안에서 도커 환경임을 인식시키는 환경변수. = 대신 - 를 쓰면 빌드 에러
ENV container=docker
# 컨테이너 시작 시 기본으로 실행할 명령 (윈도우 cmd가 아님). /sbin/init를 실행해야 systemctl로 관리 가능 (bash 방식의 /bin/bash 대체)
CMD ["/sbin/init"]

# [호스트 리눅스 · root]
# -t 이름:버전 (버전 생략 시 latest). 맨 끝 . = 현재 디렉터리의 Dockerfile (다른 경로면 /root/docker처럼 명시)
# 빌드 에러가 나면 해당 줄만 고쳐 저장하고 다시 빌드
# 결과 849MB / 224MB: 원본(747MB / 191MB)보다 커진 것은 systemd 등을 추가했기 때문
docker build -t cs:9 .
# 로키 빌드: FROM을 rockylinux:9로 바꾼 뒤 실행. 결과 307MB / 78.1MB (원본 260MB / 68.9MB)
docker build -t rocky:9 .
항목내용
정상 확인빌드 중 Step이 단계별로 올라가며 RUN 단계에서 systemd가 설치되고 금방 끝남 → docker images에 새 이미지가 보임
결과새 이미지로 만든 컨테이너는 init가 있어 systemctl 사용 가능 → 정통 리눅스처럼 동작
Dockerfile 4줄 규칙 — FROM → RUN dnf install -y systemd && dnf clean all → ENV container=docker(반드시 =) → CMD ["/sbin/init"]. root에서만 작성, 파일명 Dockerfile 고정, 빌드는 docker build -t 이름:버전 . / 줄별 의미: FROM은 docker images의 이름:버전 그대로, -y는 자동 승낙, systemd는 systemctl용 핵심 데몬, clean all은 설치 후 캐시 정리, ENV는 컨테이너 안에서 도커 환경임을 인식, CMD는 시작 시 실행 명령

정상 확인docker ps에 Up으로 뜨고, 컨테이너 안에서 systemctl 입력 시 목록이 뜨면 성공 (start/stop 관리 가능). 컨테이너가 하나도 없으면 출력이 비어 있음(컨테이너 ID 열도 없음). 컨테이너 ID는 사람마다 다르므로 NAMES 열의 이름을 씀 (rm·exec 모두 이름 가능, 탭키 자동완성)
포트 매핑 원칙 — -p 호스트:컨테이너 (앞 호스트, 뒤 컨테이너). 생성 후 변경 불가. 컨테이너마다 호스트 포트를 다르게 해야 충돌 없음
# [호스트 리눅스 · root]
# 용도: 로키 = 웹 + FTP + SSH, 센트OS(cs:9) = DB. 옵션은 한 줄로 쓰고 사이는 한 칸 띄움
# 1) 웹·FTP·SSH 컨테이너 (로키 9). bash 방식의 /bin/bash 대신 /sbin/init → PID 1 = systemd
docker run -it -d --privileged -p 9022:22 -p 80:80 -p 9021:21 --name megaweb rocky:9 /sbin/init

# 2) DB·백업FTP·SSH 컨테이너 (센트OS 9) — 호스트 포트는 컨테이너마다 반드시 다르게!
#    웹이 9022·9021을 쓰므로 DB는 SSH 10022 · DB 3306 · FTP 10021 (DB는 80 불필요, FTP는 백업용)
docker run -it -d --privileged -p 10022:22 -p 3306:3306 -p 10021:21 --name megadb cs:9 /sbin/init

# 3) 실무 방식: CPU·메모리·디스크 자원 제한 적용. 나머지 옵션은 앞의 run과 같고, 연습용이라 포트는 8080 하나만
# 연습 전 호스트 자원 확인: 이 서버는 free -m total 10477MB(약 10GB), swap 5431MB
free -m                            # 메모리 사용량(MB) 확인
lscpu                              # CPU 노드·L2·L3 캐시·코어 수. 이 화면은 On-line CPU 0-3 (4개)
# 연습용 컨테이너는 만들어 확인하고 바로 지움
docker run -it -d --privileged --cpus="1.5" --memory="2g" --storage-opt size=8G -p 8080:8080 --name test rocky:9 /sbin/init
docker ps -a                       # PORTS 열에서 8080:8080 매핑 확인
# 정지 → 삭제 (systemd 컨테이너는 서비스 종료 때문에 stop에 시간이 꽤 걸림)
docker stop test
docker rm test
옵션 기능 주의사항 · 오류 해결
-it / -d -it: 가상 터미널(pseudo-TTY) + 표준입력
-d: 백그라운드(--detach) 실행
  • -d 없이 -it /bin/bash로 들어가면 exit 시 컨테이너 종료 → docker start로 재가동 후 한 번 들어갔다 나와야 정상 작동
  • -d는 모든 컨테이너에 필수는 아님
  • -itd 동시 사용 가능
  • bash 셸을 쓰려면 표준입력·터미널 필요 → -it(또는 -itd)
  • -t는 포트 개방(-p 전용)과 무관
  • docker run에는 -f 옵션 없음 (출처: docs.docker.com docker run 참조)
--privileged 호스트 장치·커널 기능 접근 권한 확대 (특권 모드)
  • 예전에는 필수로 쓰던 옵션이며 최신 서버에서는 생략해도 무방
  • 컨테이너 안에서 init 0을 해도 호스트는 안 꺼짐
  • /sbin/init과 무조건 짝은 아님
-p 호스트:컨테이너 포트 매핑 (앞 = 호스트 포트, 뒤 = 컨테이너 내부 포트)
  • 호스트 포트 중복 시 충돌
  • 생성 후 수정 불가 (MySQL 3306 등을 빠뜨리면 재생성)
  • 예: 컨테이너 안 sshd 포트를 3022로 바꿔도 접속 안 됨 → 바꾸려면 -p 9922:22처럼 새로 생성
  • 포트를 안 열면 소용없음: MySQL을 설치해도 3306 매핑이 없으면 서비스 불가
  • -p 80:80은 웹(8080 등 다른 포트로 바꿔도 됨), -p 10021:21은 FTP(원래 21번이라 겹치지 않게 호스트만 10021)
--name 이름 컨테이너 고유 이름 (대시 2개)
  • -name(대시 1개) → unknown shorthand flag: 'n' 에러
  • 에러로 남은 Created/Exited 컨테이너를 docker rm해야 같은 이름으로 재생성 가능
이미지명 · /sbin/init 사용할 이미지(rocky:9, cs:9) + 컨테이너에서 최초로 실행할 프로세스(PID 1)
  • 마지막 값에 따라 완전히 다른 동작 (프롬프트도 다름: /sbin/init이면 [root@컨테이너ID /]#, /bin/bash이면 bash-5.1#)
  • 정상 컨테이너는 프롬프트에 호스트명 대신 컨테이너 ID가 표시됨
  • init 방식은 운영체제 이미지에만 해당, 데이터베이스 이미지는 약간 다름
  • 명령에 오타를 내지 말 것: 오타 나면 컨테이너를 지우고 다시 만들어야 함
--cpus="1.5" 최대 CPU 코어 수 제한 ("0.5", "1", "1.5" = 0.5·1·1.5코어. EC2·GCP 인스턴스의 0.5·0.8코어 선택이 같은 개념)
  • 한도를 넘어도 죽지 않고 속도 제한(throttling)
  • 호스트가 24코어여도 2코어 정도는 호스트용으로 남김
  • 추후 YML(docker compose)로 관리
--memory="2g" 최대 메모리 사용량 제한
  • 한도 초과 시 OOM으로 컨테이너 안 프로세스 강제 종료(kill)
  • 미제한 시 호스트 메모리 고갈 → PuTTY 접속 불가·서버 마비
--storage-opt size=8G 디스크 용량 제한 (AWS 30GB 지정과 같은 개념)
  • 한도 초과 시 쓰기 오류(No space left)
  • 앞 옵션과 한 칸 띄어쓰기
  • 로그 기록 용량에도 원래 limit을 걸지만 이번 연습은 디스크만 8G로 잡음
  • 호스트가 overlay2 + xfs(pquota 마운트)가 아니면 --storage-opt is supported only for overlay over xfs with 'pquota' mount option 에러가 날 수 있음 (보충 · 표준 동작)
자원 할당 3종 — --cpus(코어) · --memory(메모리) · --storage-opt size(디스크, xfs pquota 필요). 안 걸면 호스트 자원 전부 소진 → 자원 관리 없이 쓰다 로컬 디스크가 꽉 차 서버 정지
-p 변경 불가의 실제 — 컨테이너 안 sshd 포트를 3022로 바꿔도 접속 안 됨(매핑은 22 기준) → 바꾸려면 -p 9922:22처럼 컨테이너를 새로 생성. 서비스 포트(3306 등)를 안 열면 설치해도 서비스 불가

Docker Compose로 서비스 정의·관리

항목내용
개념
  • 여러 컨테이너를 파일 하나(compose.yaml)로 정의 → 한 번에 생성·관리. docker run의 옵션을 파일 속성으로 옮긴 형태 → compose 파일을 여러 개 만들어 두고 필요할 때 실행
  • 파일이 잘못돼도 파일 하나를 고쳐 다시 올리면 되므로 되돌리기 쉬움
  • 실무에서 매우 많이 쓰는 방식 → 서비스 묶음과 포트·환경변수를 파일로 관리
파일명
  • compose.yaml = 기본·권장 파일명
  • 기본 탐색 대상: compose.yaml, compose.yml, docker-compose.yaml, docker-compose.yml / 다른 이름은 -f 옵션으로 지정
  • composerize 안내가 compose.yml이어도 실습은 compose.yaml로 통일 — 확장자 오타 주의
명령 형식
  • 입력은 docker compose — 플러그인 방식이라 하이픈 없이 띄어 씀 (옛 단독 실행 파일 docker-compose와 구분)
  • 설치 확인 명령 rpm -qa | grep docker의 목록에 docker-compose-plugin이 있으면 이 방식
YAML
  • "YAML Ain't Markup Language"(초기 명칭 "Yet Another Markup Language")의 재귀 약어 → 마크업이 아니라 데이터 직렬화 형식
  • 들여쓰기는 탭 금지, 스페이스만 (탭이 있으면 실행 시 라인 에러)
  • 같은 레벨은 칸 수를 똑같이 맞춤 → 한 단계 들어갈 때마다 한 칸씩 늘리고, 속성은 서비스명보다 한 칸, 속성 안 항목은 또 한 칸 (칸 수 자체는 자유, 정리본의 4칸은 보기 좋게 단순화한 예)
  • 목록 항목은 -(하이픈)으로 시작
version 속성
  • 최상위 version은 obsolete → Compose v2가 무시하므로 생략 권장. 실습 파일은 첫 줄을 # 주석으로 두고 진행 (그대로 둬도 경고만 나오고 실행은 됨)
  • 실습의 version: 'cloud Server 1.1'은 Compose 실행 버전 설정이 아니며 GitHub pipeline과도 무관 (아무 값이나 가능, 3.8 같은 버전 형식도 무시됨)
서비스·속성services: 아래에 자유로운 서비스명 → 그 아래 image, ports, container_name, environment, tty, stdin_open, privileged, command 등을 들여 씀. 서비스 사이는 빈 줄로 구분, 항목을 끄려면 # 주석
작성 도구
  • 서버의 vi는 주석·한글 입력이 불편 → VS Code로 작성 후 서버에 올리거나 붙여넣기
  • 파일명이 compose.yaml이면 VS Code가 도커(고래) 아이콘으로 인식 → 어떤 파일인지 바로 구분
  • 주석은 #
  • 윈도우 메모장으로 작성해 붙여넣는 방법도 씀 — 들여쓰기 칸을 눈으로 맞추기 쉬움
자동완성편집기 자동완성 제안을 그대로 믿으면 틀림 — command 제안값이 /sbin/init이 아니어서 직접 고침. 제안은 후보일 뿐 실제 값은 이미지·docker run 검증 결과로 확정
직접 검증 후 Compose이미지·포트·실행 명령을 먼저 docker run으로 한 항목씩 확인 → 같은 옵션으로 Compose 작성. 하드웨어·이미지를 모르는 AI에 통째로 맡기지 않음 (실무 원칙)
AI 사용 주의AI는 내 하드웨어·이미지 정보를 몰라 컨테이너 환경에서 에러가 반복되고, 결국 보안을 다 풀어 작동시키는 사고로 이어짐 → 강사 회사는 이 영역에 AI를 쓰지 않음
composerize.com
  • docker run 문장 → Compose YAML 변환 도구 (실무자가 사용)
  • Docker Compose version(CommonSpec 등)·들여쓰기(4 spaces 등) 선택 가능
  • docker run 문장을 그대로 붙여 넣고 프로젝트·컨테이너 이름만 바꾸면 나머지 옵션은 동일하게 유지 (실습: mariadb11과 겹치지 않게 testdb)
  • 결과를 처음부터 끝까지 복사해 파일로 만들면 다운로드·시작까지 자동 처리 가능
  • 결과를 그대로 믿지 말고 이미지·포트·권한·비밀값 검토

Compose 속성의 권한·cgroup·tmpfs

항목내용
privileged컨테이너 권한·장치 접근을 크게 넓힘 → 호스트에 위험. root를 컨테이너 안에 가두는 보안 경계가 아님 → 꼭 필요한 실습에서만, 운영 서비스에는 원칙적으로 부여 안 함
cgroup namespace
  • cgroup = control group(컨트롤 그룹) — 프로세스 묶음의 자원(CPU·메모리)을 관리하는 커널 기능, 기준은 호스트 전체
  • cgroup: private = docker run --cgroupns=private → 컨테이너가 보는 cgroup 계층 격리
  • 유효한 값은 host 또는 private (public 없음), 생략하면 Docker 데몬 기본값
  • cgroup 격리가 privileged 권한을 무력화하거나 호스트 root 접근을 막지는 않음
systemd용 tmpfs
  • PID 1을 /sbin/init(systemd)으로 쓰는 실습에서 /run·/run/lock을 임시 파일시스템으로 제공 가능
  • /run/lock = 프로세스가 잠금 파일(lock)을 만드는 경로 → 같은 서비스의 중복 실행을 막음 (예: nginx가 80을 쓰는 중에 apache를 포트만 바꿔 또 띄우는 식의 중복 기동)
  • 필수 설정 아님, tmpfs가 하위 경로 읽기를 막는다는 뜻도 아님
# [호스트 리눅스 · /root/yaml/compose.yaml 파일 안 · webserver 서비스]
# 장치·커널 기능 접근 확대 (실습 전용, 보안 경계 아님)
    privileged: true
# cgroup 계층 격리 (= --cgroupns=private). 값은 host 또는 private
    cgroup: private
# systemd가 쓰는 /run, /run/lock을 메모리 기반 임시 파일시스템으로 제공 (에디터가 init 줄을 제안해도 쓰지 않음)
    tmpfs:
      - /run
      - /run/lock
# PID 1 = systemd
    command: /sbin/init
privileged·cgroup — privileged: true는 보안 경계가 아님(운영 금지). cgroup 값은 host/private뿐이고, cgroup 격리가 privileged 위험을 막아 주지 않음

항목내용

  • Visibility settings: public ↔ private 전환
  • Upgrade plan: 유료, 패스
  • Delete repository 등 아래쪽 항목: 더 이상 안 쓸 때만, 지금은 하지 말 것

# 레포 이름에 맞춰 tag → push. 1) 연습용 임시 태그(tagname)로 먼저 올려 허브에서 태그 생성 확인

docker push mzleejh/apink_rocky:tagname
# 2) 원래는 버전을 태그로 씀 (다음 버전은 9-1 식). 압축되어 올라가 5초도 안 걸림

항목내용
push 대상올리는 것은 이미지이지 컨테이너가 아님. 처음부터 레포 이름으로 이미지를 만들었다면 tag 없이 바로 push 가능. push가 끝나면 tag로 만든 이름과 원본 이미지는 지워도 됨(허브에 올라간 이미지는 그대로). 이번에는 웹(로키)만 올리고 DB는 아직 안 올림
버전 관리레포 이름에 맞춰 tag → push하는 것이 버전 관리 = 파이프라인 구조 (Git과 비슷). 허브 태그 상세에는 레이어·run·container 설정, 총 용량, Linux AMD64, pull 명령이 표시되고 Upgrade는 유료
복원 확인브라우저 접속 시 기존에 만든 mega 웹 페이지까지 그대로 복원. 같은 이미지를 집(로키 + docker)에서 pull → run 하면 여기 환경이 그대로 재현됨 = 실무 배포 방식
허브 레포 화면레이어·용량·Linux AMD64·Pulls(다운로드 횟수) 표시. public 레포는 주소만 알면 누구나 pull — 아마존 같은 클라우드가 내부 구성을 외부에 보여주지 않는 것과 반대. 이번 실습 범위는 배포(push) → 받아서 설치(pull + run)까지
tag → push → pull 복원 — 허브 안내 그대로 push하면 에러 → docker tag로 이미지 이름을 레포 이름과 일치 → push(배포) → pull + run(복원). Settings의 Tag mutability는 기본 Mutable 유지, 회사는 무조건 Private + 그룹

docker network inspect spark-net        # 서브넷·게이트웨이·연결 컨테이너·IP 확인

docker network rm spark-net             # 미사용 네트워크 삭제 (연결 컨테이너가 있으면 먼저 분리)

구분내용주의·이유
파일 구조{"Binds":…,"PortBindings":…} 형태의 JSON 객체배열이 아니라 이름:값 쌍의 묶음 — PortBindings 항목 안에 "포트/tcp":[{...}] 블록이 포트마다 들어 있음
수정 요령쓰지 않는 포트 블록을 쉼표까지 통째로 복사 → 컨테이너 포트와 HostPort를 새 값으로쉼표·따옴표·괄호 하나만 틀려도 컨테이너가 아예 뜨지 않음

정지 직후docker ps가 처음엔 아무것도 안 보이고 소켓 관련 메시지 뒤에 정상 출력소켓이 연결을 받아 데몬을 올리는 과정 — 실패가 아님

정상 결과마스터·워커 모두 Up, 웹 UI에서 워커 ALIVE, 새 포트가 docker ps에 표시포트가 보이지 않으면 JSON 문법·컨테이너 디렉터리 선택을 먼저 확인

# 기존 7077 블록을 쉼표까지 그대로 복사해 8080 블록 앞에 붙이고, 복사본의 컨테이너 포트와 HostPort만 8888로 수정
"PortBindings":{"7077/tcp":[{"HostIp":"","HostPort":"7077"}],"8888/tcp":[{"HostIp":"","HostPort":"8888"}],"8080/tcp":[{"HostIp":"","HostPort":"8080"}]}
포트 추가 — 컨테이너 정지 → hostconfig.json 백업 → PortBindings에 새 포트 블록 추가 → docker·docker.socket 둘 다 정지 → 붙여넣기 → docker ps로 소켓 재연결 → start. 소켓을 살려 두면 수정이 원복되고, JSON 한 글자 오타는 컨테이너 미기동으로 이어짐

구분역할동작
docker.service도커 데몬 — 컨테이너 실행·포트 게시·이미지 관리정지하면 컨테이너가 모두 멈춤
docker.socket/var/run/docker.sock에서 연결을 기다리는 systemd 소켓 유닛연결이 오면 데몬을 대신 시작시킴 — 그래서 데몬을 멈춰도 docker ps 한 번에 다시 올라옴
정지 순서systemctl stop docker docker.socket처럼 한 줄에 함께데몬만 멈추면 소켓이 곧바로 다시 띄워 설정 수정이 무효가 됨
복구docker ps·docker start 등 도커 명령 한 번소켓이 연결을 받아 데몬을 자동 기동 — systemctl start docker를 따로 쓸 필요 없음
서비스 vs 소켓 — docker.service=데몬 본체, docker.socket=연결을 받아 데몬을 깨우는 유닛. 설정 파일을 고칠 때는 둘 다 정지해야 원복을 막을 수 있음
